# コンテナの脆弱性スキャン結果のうち実際に動いているパッケージの見分け方

公開日：2026年9月16日

## はじめに

Trivyは、コンテナで実際には使われていないパッケージも含めて、大量の脆弱性を検出します。
実際に使われているパッケージの検出結果を優先して対応するには、どのパッケージが使われているかを見分ける必要があります。
Trivyの検出結果だけでは見分けられないため、実行時の情報が必要です。

例えば、`nginx:1.27`のスキャンでは72パッケージに616件の脆弱性が検出され、153件がHIGHまたはCRITICALでした。
実行時のサンプリングで、対応するパッケージのファイルが読み込まれていることを確認できたのは、この153件のうち9件でした。[^measurements][^harness]

この記事では、次のことを記載します。

- Trivyの検出結果だけでは分からないこと
- パッケージの読み込みを示す証拠から分かることと、分からないこと
- 配布イメージ、自作イメージ、実運用ホストでの計測結果
- 実行時証拠をKEV・EPSSと組み合わせる方法
- Dockerホストで同じ対応関係を手動確認する簡単な手順

## Trivyの検出結果だけでは分からないこと

この比較では、検出結果の1件を、検出したソフトウェアと脆弱性情報を照合して得られる、パッケージ・インストール済みバージョン・CVEの組として扱います。
件数はCVE×パッケージで数えるため、同じパッケージに複数の検出結果が対応する場合があります。[^trivy]
件数はこの組み合わせの数を、深刻度は報告された脆弱性の重大さを表します。

検出結果には、次の限界があります。

- そのパッケージがこのコンテナで実際に使われているかは分からない
- 脆弱な機能に到達したかは分からない
- KEVやEPSSを加えても、この環境で対象パッケージが使われているかは分からない
    - CISAのKEVは実環境での悪用の証拠があるCVEを示す（[KEV Catalogの基礎と使い方](kev-known-exploited-vulnerabilities-ja.md)を参照）[^kev]
    - FIRSTのEPSSは今後30日以内の悪用確率を推定する（[EPSSの基礎とスコアの確認方法](epss-exploit-prediction-scoring-system-ja.md)を参照）[^epss]

そのため、実際に動いているパッケージを見分けるには、観測したプロセスと、このコンテナ内のパッケージおよびバージョンを紐づける実行時証拠が必要です。
実行時証拠は、対応する検出結果の優先順位を上げる根拠として使います。
優先順位を上げた理由が分かるよう、実行時証拠はKEV・EPSSとは分けて保持します。

## 「実際に動いている」の意味

この記事でいう「実際に動いている」とは、稼働中のプロセスがそのパッケージの実行ファイルまたは共有ライブラリを読み込んでいることです。
読み込みの有無はprocfsの`/proc/<pid>/exe`と`/proc/<pid>/maps`で観測します。[^proc][^exe][^maps]

この定義で分かることは次のとおりです。

- サンプル取得時点で、プロセスがそのファイルを実行またはマッピングしていたこと
- そのファイルの所有パッケージとバージョンが、検出結果のパッケージとバージョンに一致すること

分からないことは次のとおりです。

- 脆弱な関数が実行されたか
    - 読み込みは確認できても、どの関数が呼ばれたかは分からない
- 観測に現れなかったパッケージが使われていないこと
    - 別のリクエストやワーカー、サンプル取得の合間に読み込まれる可能性がある

したがって、実行時証拠は利用を裏付ける肯定的な証拠としてだけ使い、対応する検出結果の優先順位を上げる根拠にします。
未観測を理由に優先順位を下げません。[^harness]

観測したパス・所有元・バージョンの扱いの詳細は、[procfsで稼働中コンテナのプロセスをOSパッケージに紐づける方法](procfs-process-to-package-mapping-ja.md)を参照してください。

## 計測方法

Trivyの検出結果1件ごとに、対応するパッケージのファイルを稼働中のプロセスが読み込んでいたかを調べ、確認件数÷検出件数を確認率としました。主な分母はHIGH/CRITICALとし、全重大度も補助的に集計しました。

- **対象**
    - 配布イメージは`nginx:1.27`、`postgres:16`、`nginx-unprivileged:1.27-alpine`
    - 自作イメージは、特定の状況を再現する小さなプログラムを公式のベースイメージに追加したもので、cryptographyのwheel入り`python:3.12-slim`、静的Goサーバー入り`debian:12-slim`、短命プロセス・一時的な`dlopen`を再現するDebianベースのケース
    - 実運用は別のUbuntuホストの4コンテナ(静的Go、JDK同梱JVM、Node.js×2)をAppArmor有効・rootで1回計測
    - 主環境はWSL2ホスト1台(Linux 6.6.114、Docker Engine 29.1.3)、Trivy v0.71を使用
- **手順**
    - 稼働中コンテナのイメージIDをスキャン
    - `docker top`で得たホスト側PIDの`/proc/<pid>/exe`と`maps`の実行可能なマッピングを定期観測
    - コンテナ内のdpkg・apkデータベースでファイルの所有元を特定し、パッケージ名・バージョンを検出結果と照合
- **条件と判定**
    - 基準はrootで30秒ごとに300秒間の10サンプル
    - 短命プロセスの捕捉確認に、間隔・期間・開始タイミングを変えた7条件を比較
    - 確認済みにはスキャン対象イメージとパッケージ名・バージョンの一致が必要で、所有元不明のパスは推測で割り当てない
- **正しさの確認**
    - 自作イメージはプログラム自身の利用記録と照合し、記録対象の見逃しと誤判定を確認
    - 公式イメージは常駐プロセスの利用ファイルを手作業で照合し、見逃しだけを確認
    - いずれも脆弱な処理そのものの実行は確認しない

各計測の内容は[公開されている計測結果](../development/runtime-prioritization.md#2026-09-12)に、
収集手順は計測用ハーネスに記載されています。[^measurements][^harness]
以下はこれらの計測についての結果であり、別のワークロードで同じ確認率を保証するものではありません。

## 配布イメージと自作イメージでの計測結果

Debianベースの配布イメージでは、Trivyが検出したHIGHまたはCRITICALの脆弱性のうち、そのパッケージのファイルを稼働中プロセスが読み込んでいたことを確認できたのは、nginxで153件中9件、PostgreSQLで113件中5件でした。
次の表は、配布イメージと自作イメージ（cryptography入りPython、静的Go）について、Trivyが検出した脆弱性のうち、そのパッケージのファイルの読み込みを確認できたもの（確認済み）の件数と割合です。

| イメージ | Trivyが検出したHIGH/CRITICALの脆弱性（確認済み / 検出） | 同パッケージ数（確認済み / 検出） | 全重大度の脆弱性（確認済み / 検出） |
| --- | ---: | ---: | ---: |
| `nginx:1.27`、Debian | 9/153 (5.9%) | 2/43 | 66/616 |
| `postgres:16` | 5/113 (4.4%) | 3/34 | 71/409 |
| `nginx-unprivileged:1.27-alpine` | 16/34 (47%) | 4/10 | 42/109 |
| cryptographyのwheelを追加した`python:3.12-slim` | 0/54 | 0/19 | 22/180 |
| 静的リンクのGoサーバーを追加した`debian:12-slim` | 0/56 | 0/17 | 0/222 |

結果は次のとおりです。

- Debianベースのnginxとpostgresでは、Trivyが検出したHIGH/CRITICALの脆弱性のうち読み込みを確認できたのは、それぞれ153件中9件と113件中5件にとどまった
    - nginxの確認済み9件は、HIGH/CRITICALの脆弱性がある43パッケージのうち、OpenSSLとzlibを提供する`libssl3`と`zlib1g`の2パッケージに対応し、いずれもサーバーが読み込む共有ライブラリ
    - 全重大度では、検出結果がある72パッケージのうち`libc6`・`libssl3`・`zlib1g`・`libcrypt1`の4パッケージで読み込みを確認
    - マッピングを確認できた`nginx`と`libpcre2-8-0`には検出結果がなく、確認済み件数には加算されなかった[^harness]
- Alpineのnginxは検出結果があるパッケージ数が少なく、確認済みの割合は47%になるが、これは危険度の差ではなく、検出結果と観測したパッケージの利用との重なりの差
- Pythonでは、Trivyが検出したHIGH/CRITICALの脆弱性54件はOSパッケージのもので、稼働中のPythonが読み込んだOSライブラリに対応するものがなく、未観測のため確認済みは0件
    - 全重大度では22件が確認済みで、pipパッケージの検出結果は全重大度にのみ含まれ、OSパッケージの所有情報による紐づけの対象外（「この計測方法の限界」で説明）
- 静的Goでは、Trivyが検出したHIGH/CRITICALの脆弱性56件は、静的リンクの実行ファイルが共有ライブラリを読み込まないため未観測で、確認済みは0件（「この計測方法の限界」で説明）
- 合成ケース全体では、3条件で計測したnginxを1回だけ数えるとHIGH/CRITICALの脆弱性627件中33件、5.3%が確認済みとなり、残り594件は未観測であって未使用ではない[^measurements]

パッケージ列はHIGH/CRITICALの脆弱性があるパッケージの「確認済み / 検出」を示し、公開開発ログに記録しているのは脆弱性の件数で、パッケージ数は同じ計測から集計しています。[^measurements][^harness]
利用記録との照合で誤判定は0件でしたが、対象は各ケース1〜2パッケージに限られ、スキャン対象全体の精度は未判定です。[^measurements]
合成ケース全体の割合も、選定したケースの結果であり、コンテナ環境全体で脆弱性のあるソフトウェアが利用されている割合の推定ではありません。

## 実運用ホストでの計測結果

実運用ホストの4コンテナでは、Trivyが検出したHIGHまたはCRITICALの脆弱性103件のうち、そのパッケージのファイルの読み込みを確認できたものは0件でした。
この計測では、OSパッケージの実行時証拠はHIGH/CRITICALの対応の優先順位付けに何も加えられませんでした。

対象は別のUbuntuホストにある静的Goサービス、JDK同梱JVM、Node.jsサービス2つで、AppArmor有効の環境でrootとして30秒ごとに300秒間、1回計測しました。[^measurements]

| Trivyが検出したHIGH/CRITICALの脆弱性の分類 | 確認済み / 検出 | 結果の解釈 |
| --- | ---: | --- |
| 言語パッケージ | 0/84 | OSパッケージの所有情報では紐づけ不可 |
| OSパッケージ | 0/19 | 読み込みを確認できる観測なし |
| 合計 | 0/103 | HIGH/CRITICALの読み込み確認なし |

結果から分かることは次のとおりです。

- 103件のうち84件はGoモジュール・JAR・npmなどの言語パッケージで、OSパッケージの所有情報では紐づけられない
- 残り19件はOSパッケージだが読み込みを観測できず、未使用と確認できたわけでもない[^measurements]
- 言語ランタイム中心のホストでは、サンプリング頻度を上げるだけでは足りず、ファイルや実行ファイルと言語パッケージを紐づける別の方法が必要

これは1ホスト1回の標本であり、実運用環境一般でOSパッケージの証拠が役立たないという意味ではありません。

## この計測方法の限界

この方法では、短命なプロセスや一時的なライブラリの読み込みを見落とすことがあります。
また、言語パッケージ、静的リンクの依存関係、パッケージデータベース外の実行ファイルは、OSパッケージの所有情報では紐づけられません。

### 短命なプロセス

サンプリングは、実行時間が短く、サンプル取得時には終了しているプロセスを見落とします。
捕捉できるかは、観測間隔だけでなく開始タイミングにも左右されます。

- 5秒ごとに約0.1秒実行するcurlは、300秒間を10秒間隔で観測した30サンプルのうち1回だけ捕捉
- 基準の開始タイミングで300秒間を30秒間隔または60秒間隔で観測した場合、curlの捕捉は0回
- Gitは試した7条件すべてで捕捉0回[^measurements]

これらはプロセスを捉えたサンプル数であり、実行回数に対する捕捉率ではなく、一般的な見逃し率も求められません。

### 一時的なライブラリの読み込み

`dlopen`による一時的な読み込みは、サンプル取得の合間に始まって終わることがあります。

- SQLiteを7秒間読み込み、7秒間解放するテストでは、7条件すべてで利用を確認でき、基準条件（300秒間を30秒間隔で観測）では10サンプル中3回捕捉[^measurements]

一時的な読み込みも観測できる場合があるため計測が必要ですが、読み込み時間がさらに短い場合の捕捉は保証しません。

### 言語パッケージ

Python拡張・Goモジュール・JAR・npmはOSパッケージの所有情報では識別できず、拡張機能のファイルが見えても、スキャナーが報告した言語パッケージとバージョンを特定できるわけではありません。
PythonやNode.jsの観測だけでも、その依存パッケージの利用確認にはなりません。[^harness]

- cryptographyのwheel入りPythonでは、pipパッケージの検出結果はOSパッケージの所有情報で紐づけられず、Python本体と拡張にもOSパッケージの所有元がなかった
    - Trivyが検出したHIGH/CRITICALの脆弱性54件はOSパッケージのもので、対応するパッケージの読み込みは未観測
    - 全重大度では180件中22件が読み込まれたOSパッケージに紐づいた[^measurements]

ディストリビューションがパッケージ化した言語ソフトウェアも、所有情報で特定できるのはディストリビューションのパッケージまでで、別途報告される言語パッケージの検出結果との対応には追加の紐づけが必要です。

### 静的リンク

静的リンクの実行ファイルには共有ライブラリのマッピングがなく、組み込まれた依存関係を個々のライブラリのパスと所有情報から検出結果へ紐づけられません。

- Debianベースの静的Goテストでは、実行ファイル自体は観測できたがOSパッケージデータベースに所有元がなく、Trivyが検出したHIGH/CRITICALの脆弱性56件中0件が確認済み[^harness]

確認済み0件は、脆弱性がないことを意味しません。

### パッケージデータベースに含まれない実行ファイル

OSパッケージデータベースに含まれない実行ファイルは、読み取り可能でも所有パッケージを特定できません。

- 実運用ホストの`/usr/local/bin/node`、同梱JDK、静的Go実行ファイルはOSパッケージデータベースの対象外[^harness]

ファイル名やディレクトリから所有元を推測せず、対応関係が得られなかったことを、プロセス情報の読み取り失敗と区別して記録します。

## 対応の優先順位付けにおける実行時証拠の使い方

実行時証拠は検出結果の優先順位を上げる根拠にだけ使い、未観測を理由に下げません。
KEV・EPSSとは別の判断材料として保持します。

| 判断材料 | 分かること | 分からないこと |
| --- | --- | --- |
| KEV | このCVEの悪用が確認されているか | このコンテナが対象パッケージを読み込むか[^kev] |
| EPSS | 予測期間内に悪用される可能性はどの程度か | この特定のコンテナが侵害されるか[^epss] |
| 実行時証拠 | この環境で、実行ファイルやマッピングを通じて該当バージョンのパッケージを観測できたか | 脆弱な関数に到達したか[^harness] |

すべての検出結果を対応対象として保持し、procfsによる紐づけの記事と同じ次の分類で観測結果を添えます。

| 分類 | 意味 |
| --- | --- |
| 確認済み（`confirmed`） | 有効なサンプルで、実行ファイルまたはマッピングを、検出結果のOSパッケージ名とバージョンに紐づけられた |
| 不明（`unknown`） | 読み取りの失敗、メタデータの欠落、所有元の曖昧さ、識別情報やバージョンの問題により、信頼できる結論を出せなかった |
| 未観測（`unobserved`） | 有効な収集を行ったものの、利用を確認できる証拠が得られなかった場合で、言語パッケージの紐づけに未対応の場合も含む |

分類は証拠の状態であり、深刻度ではありません。
観測時刻、成功したサンプル数、照合できなかった理由を併せて保持します。[^harness]

扱い方は次のとおりです。

- 確認済みのHIGHの検出結果には、ほかに優先順位を引き上げる情報がなくても、速やかに調査するための環境固有の根拠が加わる
- KEVに登録されたCVEのHIGHの検出結果は、未観測でもサンプリングでの不在が悪用の証拠を打ち消すわけではないため、引き続き緊急性が高い
- 不明の検出結果は、既存の対応の優先順位を維持しながら、収集上の問題を調査する
- 未観測の言語パッケージの検出結果には、ランタイムが一度も読み込まなかったという判断ではなく、適切な紐づけの証拠が必要である

確認済み件数を修正対象の全部として示さず、「このインストール済みパッケージのこのバージョンが、この時刻に、このプロセスにマッピングされていた」という説明を検出結果に添えます。

## 自分のホストでの確認方法

スキャン結果のパッケージを稼働中プロセスが読み込んでいるかを、1つのコンテナで手動確認する手順です。

以下のコマンドは、Linux上のDocker Engineホストで実行します。
実行前に、山かっこで囲んだプレースホルダーを置き換えてください。
所有元を調べる例は、Debianベースのコンテナと、ホストで`dpkg-query`を使えることを前提としています。
最後のコマンドではTrivyと`jq`を使用します。

コンテナのプロセスを一覧表示し、返されたホスト側PIDを1つ選びます。[^docker-top]

```bash
docker top '<container>' -eo pid,ppid,user
```

そのPIDについて、実行可能なファイルのマッピングからパスを抽出します。
この式は、固定列を取り除いた後のパス名を保持します。[^maps]

```bash
sudo awk '$2 ~ /x/ && $5 != 0 && $6 ~ /^\// {
  for (i = 0; i < 5; i++) sub(/^[^[:space:]]+[[:space:]]+/, "")
  print
}' '/proc/<host-pid>/maps'
```

出力例:

```text
/usr/sbin/nginx
/usr/lib/x86_64-linux-gnu/libc.so.6
/usr/lib/x86_64-linux-gnu/libssl.so.3
```

プロセスのルート経由で、コンテナのdpkgデータベースを照会します。
この例では、データベースに記録されたlibcのパスを使います。
マッピング上の`/usr/lib`のパスが、データベースでは`/lib`以下の項目に対応する場合があります。[^root][^dpkg-query]

```bash
sudo dpkg-query --admindir='/proc/<host-pid>/root/var/lib/dpkg' \
  -S /lib/x86_64-linux-gnu/libc.so.6
```

最後に、そのコンテナが使用しているイメージIDをスキャンし、OSパッケージの検出結果を識別する情報をJSONから抽出します。[^reporting]

```bash
trivy image --scanners vuln --format json '<running-image-id>' |
  jq -r '.Results[] | select(.Class == "os-pkgs") |
    .Vulnerabilities[]? |
    [.PkgName, .InstalledVersion, .VulnerabilityID] | @tsv'
```

特定したパッケージを`PkgName`と比較し、続いてコンテナのパッケージメタデータから取得したバージョンを`InstalledVersion`と照合します。
所有元の照会だけでは、バージョンの確認は完了しません。

これは手動での抜き取り確認です。
コンテナで観測されたパッケージについて結論を出す前に、コンテナ内の各プロセスで収集を繰り返します。
`/usr`統合によるパスの別名、シンボリックリンクの所有関係、権限、信頼できるバージョン照合については、
[procfsによる紐づけの詳しい手順](procfs-process-to-package-mapping-ja.md)を参照してください。
