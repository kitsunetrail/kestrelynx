# Go modules の修正 PR の開発

- **状態:** 実装済み(検証用のリポジトリで PR の作成、検証用のホストの Kubernetes で作業用 Pod の動作を確認)
- **開始日:** 2026年10月29日
- **最終更新:** 2026年10月30日

## 目的

npm・pnpm・pip・uv を対象にしていた言語パッケージの修正 PR を、Go modules に広げる。
稼働イメージの Go のバイナリを Trivy が `gobinary` として検出した所見から、対応付けたディレクトリの `go.mod`・`go.sum` を更新する PR を作る。

## 方針

- 既存の言語パッケージと同じく、作業用コンテナで公式ツールの `go` コマンドを動かす
- 作業用コンテナの結果は未信頼として扱い、KestreLynx で検査する

## 決定事項

### バイナリとの対応

- メインモジュールのパスが、対応付けた `go.mod` の `module` と一致するバイナリの所見だけを扱う
  - ベースイメージに含まれる別の Go のツールの所見は、修正計画に出さない
- バイナリに組み込まれた依存の版が `require` と一致しない場合は、手動対応にする

### Go 自体の所見

- 標準ライブラリの `stdlib` の所見は、PR にしない
  - `go.mod` の更新では直らない
  - 修正計画の別の項目で「この版以上の Go でビルドし直すと直る」と案内する

### 更新と go の行

- すべての対象を1回の `go get` で更新し、`go mod tidy` は実行しない
  - `go` の行は、更新後のモジュールの `go.mod` が宣言する版まで上がることがある
- 更新後の `go` の行が、稼働バイナリをビルドした Go の版を超える場合は手動対応にする
  - ビルドに必要な Go の版を、利用者が使っている版より上げる判断は任せる

### 別の対象が高い版を要求する場合

- 別の対象からより高い版を要求される対象は `go get` の指定から外し、依存の要求によって版を上げる
  - 対象それぞれの修正版を `go get` に正確に指定すると、ある対象の新しい版が別の対象をより高い版で要求する場合に失敗する
    - 例えば、`golang.org/x/net v0.60.0` は `golang.org/x/text v0.42.0` を要求するため、`x/text` の修正版である `v0.41.0` を同時に指定できない
  - 上がった版は、ほかの付随する更新と同じ検査で確かめる

### 検査で確かめる版

- 更新の前後で脆弱性を比べるのは、`go.mod` の `require` に書かれている版
  - 例えば今回の検証の PR では、更新前の `golang.org/x/net v0.20.0`・`golang.org/x/text v0.14.0` と、更新後の `x/net v0.60.0`・`x/text v0.42.0` を比べる
  - 比べ方は npm・uv と同じく、モジュールと脆弱性の組
- `go.mod` に書かれている版だけを見れば足りる
  - `go build` は既定の `-mod=readonly` で、`go.mod` に書かれている版のモジュールだけを使う
  - 必要なモジュールが `go.mod` にない場合や、書かれている版が必要な版より低い場合は、`go` コマンドが別の版を選ばず、`updates to go.mod needed` でビルドが止まることを `go1.26.0` で確認
  - そのため、作業用コンテナが不完全な `go.mod` を返しても、確かめていない版がビルドに入ることはなく、ビルドが失敗するだけになる
- 依存先の `go.mod` をたどって見つかる版までは調べない
  - 各モジュールの `go.mod` は古い版の依存も要求しているため、たどるとビルドで使われない古い版が大量に集まる
  - 例えば `x/net` を `v0.20.0` から `v0.23.0` に上げるだけでも37版が集まり、2019年の `golang.org/x/crypto` や `x/text v0.3.0` など、使われない版の既知の脆弱性88件で必ず手動対応になった
- この確認は、利用者が `go build` を既定のまま実行することを前提にする
  - ビルドの前に `go get`・`go mod tidy`・`-mod=mod` のビルドを実行すると、`go` コマンドが別の版を選ぶため、確認の範囲から外れる
  - PR 本文に、この前提と CI で実行する `go build -mod=readonly ./... && go test -mod=readonly ./...` を書く

### 付随する更新と go.sum

- 付随する更新は、対象の修正版の `go.mod` の要求からたどれるものだけを認める
- `go.sum` は `sum.golang.org` の記録と照合する
  - 足りない行は KestreLynx が補って PR 本文に書く

## 検証方法

### 単体テスト

- `go.mod` の解析とバイナリとの対応を確認
- `go` の行の変更と `go.sum` の照合を確認
- 付随する更新の説明と PR 本文を確認

### 結合テスト

手元の Docker で、公式 `golang` イメージの Go 1.26・1.27、`proxy.golang.org`・`sum.golang.org`・Trivy を使った。
`golang.org/x/net v0.20.0` を使うモジュールの更新を、次の観点を含む5通りで確認した。

- 直接依存だけの更新
- `golang.org/x/text` も上がる更新
- `go` の行が `1.22` から `1.25.0` に上がる更新
- Go 1.26 と Go 1.27 の作業用イメージでの更新

5通りすべてが PR の候補になった。

### 実環境

手元の Docker で KestreLynx を動かし、検証用のリポジトリに置いた Go のアプリケーションを対象にした。
修正計画から GitHub の PR の作成までを確認した。

| 項目 | 構成 |
| --- | --- |
| ビルドに使った Go | Go 1.26.10 |
| 使用するモジュール | `golang.org/x/net v0.20.0`・`golang.org/x/text v0.14.0` |

| 確認項目 | 結果 |
