# Java 本体の脆弱性照合の開発

- **状態:** 実装済み(本番運用環境と検証用のホストで確認)
- **開始日:** 2026年11月24日
- **最終更新:** 2026年11月25日

## 目的

Trivy が検出しない JDK 本体の脆弱性を通知と修正計画に出す。
公式の maven・gradle を含む Temurin ベースのイメージと、Elasticsearch のように JDK を同梱するイメージを扱う。

## 背景

今回調べたイメージでは、Temurin、Corretto、Zulu などの主要な JDK ディストリビューションを使うイメージでも、JDK を同梱する Elasticsearch のイメージでも、Trivy 0.76.2 は JDK の脆弱性を報告しない。
Temurin は tarball を展開して配置するため、OS パッケージにも言語パッケージにも該当しない。
本番運用環境の Elasticsearch に同梱された Oracle の OpenJDK ビルド 27.0.1.0.3 は、2026年11月17日の OpenJDK アドバイザリで影響を受ける版に該当するが、通知には出ていなかった。

## 方針

- **JDK の版の読み取りと OpenJDK アドバイザリとの照合**
    - 環境変数からは、Temurin 形式の `JAVA_VERSION` の値を読む
    - イメージの層からは、JDK の `release` ファイルにある版を読む
- **公開データの取得と KestreLynx 内での判定**
    - 公開データを取得し、スキャン対象のイメージ情報を外へ送らずに KestreLynx 内で照合する
- **版番号の体系による配布元の絞り込み**
    - 上流の OpenJDK と同じ版番号の体系を使う配布元だけを照合する

## データ源

JDK の照合に使う公開データと、それぞれの用途を次の表に示す。

| データ源 | 用途 |
| --- | --- |
| OpenJDK のアドバイザリ | 系列ごとに影響を受ける最後の版と、CVE、CVSS を取得する |
| Adoptium の Temurin リリース一覧 | 修正版を決める |
| Adoptium の系列一覧 | LTS とサポート終了を判定する |

## 決定事項

- **照合する配布元**
    - Temurin、Oracle の OpenJDK ビルド、配布元の記載がない JDK(`jlink` で作ったものなど)を照合する
    - Corretto・Zulu・SapMachine・Microsoft・Liberica・Semeru・Oracle JDK 商用版は照合対象外
    - Zulu 独自の版番号や Oracle JDK 11 と上流との版番号の食い違いによる誤検知や見逃しを避けるため、配布元を絞る
    - OS ディストリビューションの JDK の脆弱性は Trivy が報告する
- **読むイメージと読み方**
    - `JAVA_HOME`、`JAVA_VERSION`、`java`・`jdk`・`jre`・`jvm` のいずれかを含む `PATH` の要素、Trivy が報告した `jar` パッケージのいずれかがあるイメージの層を読む
    - Docker では Docker Engine から、Kubernetes と修正計画の候補イメージではレジストリから層を取得する
    - 読んだ層はキャッシュし、同じ層の再読み取りを省く
- **読み取りの上限と次の回への繰り越し**
    - 1回のスキャンで読む量の上限は、レジストリからは 2 GiB、Docker からは 8 GiB
    - 上限を超えるイメージの読み取りは次の回に繰り越す
    - 繰り越したイメージの前回の所見は解消扱いにせず保持する
- **修正計画**
    - JDK がベースイメージに由来するかを層ごとに判定する
    - JDK を同梱するイメージの新しいタグを読み直し、脆弱性が解消することを確認できた場合だけ修正 PR を作る

## 検証方法

- 取得した実データと実物の `release` ファイルを使って単体テストを行う
- 手元の Docker で、digest を固定したイメージの JDK を照合する
- Docker が稼働する本番運用環境で、Elasticsearch の所見と修正 PR を確認する
- Kubernetes の検証用のホストで、レジストリからの層の読み取りと JDK の照合を確認する

## 検証結果

### 手元の Docker

次の表は、手元の Docker でイメージごとに照合した JDK と、重大度を絞らずに数えた Java の所見を示す。

| イメージ | 照合した JDK | Java の所見 |
| --- | --- | --- |
| distroless の Java 21 | Temurin 21.0.10(環境変数からは読めない) | 69件 |
| maven(Java 21) | Temurin 21.0.12.1 | 49件(環境変数から版を読んだ場合と同じ) |
| maven の JDK から `jlink` で `java.base` だけを残した JRE | 21.0.12.1(配布元の記載なし) | 33件(含まれないモジュールの16件を除く) |
| Corretto 21 | 照合対象外の配布元 | 0件(配布元と場所をログに出す) |
| Elasticsearch 9.5.7 | Oracle の OpenJDK ビルド 27.0.1.1 | 0件(影響を受けない版) |

スキャン時間は1回目が約4分半、層を読み直さずに済んだ2回目が22秒である。

### 本番運用環境の Elasticsearch 8.19.25

KestreLynx は、Elasticsearch に同梱された JDK について、Trivy が報告しなかった脆弱性を検出し、修正 PR を自動で作成した。
同梱の Oracle の OpenJDK ビルド 27.0.1.0.3 で既定の重大度(`HIGH`・`CRITICAL`)に該当したのは CVE-2026-114938〜CVE-2026-114942 の5件で、いずれも `HIGH`、修正版は 27.0.1.1 である。
Dockerfile の元イメージを JDK 27.0.1.1 同梱の Elasticsearch 8.19.26 に更新する PR を反映した後のスキャンでは、JDK の5件が解消し、元イメージに由来する所見は guava の1件だけが残った。

### Kubernetes の検証用のホスト

Docker Engine を使わない Kubernetes 環境でも、KestreLynx はレジストリからイメージの層を読んで JDK を検出できた。
digest を固定した maven(Java 21)イメージを使う Pod で Temurin 21.0.12.1 を検出し、既定の重大度で Java の所見を8件報告した。
読み取りはすべて成功し、次のスキャンに繰り越したイメージはなかった。

### 浮動タグの Temurin イメージ

Dockerfile が `FROM eclipse-temurin:21-jre` で浮動タグを使っているため修正 PR を作れない場合でも、修正計画には再ビルドで脆弱性が解消する見込みが示された。
手元の Docker で `eclipse-temurin:21.0.10_7-jre` から作ったイメージを動かすと、JDK は Temurin 21.0.10 で、重大度を絞らずに数えた Java の所見は69件だった。
1回目と2回目のスキャンで、再ビルドすると JDK が現在の `eclipse-temurin:21-jre` に含まれる 21.0.13.1 に上がり、69件すべてが解消する見込みを示す同じ行が修正計画に出た。

## 既知の制約

- **照合対象の範囲**
    - 照合する配布元に含まれない JDK は対象外
    - Java の手がかりがないイメージは対象外
        - `jlink` で作った JRE を `PATH` に入れず、起動スクリプトから直接実行するイメージが該当する
- **Oracle の OpenJDK ビルドで示す修正版**
    - 修正版を Temurin のリリース一覧から決めるため、上流で脆弱性が直った最初の版より新しい版を示す場合がある
- **アドバイザリの影響範囲**
    - アドバイザリには影響が始まった版の記載がないため、同じ系列の古い版も該当として出る場合がある
- **層の圧縮形式**
    - zstd で圧縮された層は読み取り対象外
