# 通知の送信条件

## スキャン通知の送信条件 {#notification-conditions}

スキャン通知は、通知モードと、その回の検出結果・差分に応じて送信します。
送ると決まった回には、設定したすべての通知先（Slack・汎用Webhook・メール）に送ります。
通知モードの設定は[通知モード](configuration.md#notify-mode)を参照してください。

### diffモードの送信 {#diff-delivery}

`diff`モードでは、前回からの変化と現在の未解決状態を通知します。
以下の表では、通常のパッケージ、EOLパッケージ、EOLのベースOSを「検出項目」と呼びます。

Kubernetesでは、ノードがdigestを報告しない場合に、スキャンした中身を確かめられず前回の記録を残すことがあります（[イメージのdigest確認](scan-logic.md#identity-verification)）。

| 状態 | スキャン通知 |
| --- | --- |
| 変化あり | 新規検出、解消などの変化を通知 |
| 変化なし | 検出項目が残っていれば、変化がないことと現在の未解決状態を通知 |
| 検出項目も変化もなし | `notify.notify_on_clean`が`true`の場合だけ通知 |
| 最後の検出項目が解消 | 現在の検出項目がなくても、解消を通知 |
| スキャン失敗 | 検出項目や差分がなくても通知 |
| 保持中 | Kubernetesでdigestを確認できず、前回のパッケージの検出結果（通常・EOL）を残していれば、変化がなくても通知 |
| digestの変更・イメージ名の更新 | パッケージの変化がなくても通知 |

ベースOSのEOLの記録だけを残している場合は、保持中という理由だけでは通知しません。

差分の成立条件は[差分と履歴の判定](diff-logic.md#comparison-baseline)、結果を保持する条件は[スキャン失敗時の扱い](scan-logic.md#scan-failures)を参照してください。

### fullモードの送信 {#full-delivery}

`full`モードでは差分の履歴を使わず、現在のレポートを送信します。

| 現在の状態 | スキャン通知 |
| --- | --- |
| パッケージの検出結果またはEOLのベースOSあり | 毎回送信 |
| スキャン失敗あり | 毎回送信 |
| 検出結果もスキャン失敗もなし | `notify.notify_on_clean`が`true`の場合だけ送信 |

スキャン通知の条件を満たさない回でも、[修正計画の送信条件](#remediation-delivery)を満たせば修正計画を通知します。

### 週次レポートの送信 {#weekly-report}

`diff`モードでは、設定した週次レポートの曜日にスキャン通知を送る場合、その通知にSlackの全体レポートを加えます。

週次レポートの曜日でも、次の場合は全体レポートを送りません。

- スキャン通知を送る条件を満たさない回（例：検出項目も変化もなく、`notify.notify_on_clean`が`false`の回）
- 修正計画だけを送る回

曜日や無効化の設定は[設定](configuration.md)、全体レポートの表示範囲は[チャンネルのレポート](slack-display.md#channel-display)を参照してください。

## Slackスレッドの投稿条件 {#slack-thread-delivery}

Slack Botによる`diff`モードのスキャン通知では、チャンネルにメッセージを投稿し、条件を満たす回には、その1通目への返信として未解決の所見の全体を投稿します。
チャンネルには要約だけを流し、所見を1件ずつ確認したいときに返信を開いて一覧を見られるようにします。

次の図は、2日続けてスキャンしたときの投稿の例です。

```text
11月8日（前回から変化あり）
チャンネル: 🛡️ KestreLynx — 2026-11-08 09:00のスキャン結果
  前回のスキャンからの変化 …
  📌 現在の未解決: 🚨 今すぐ対応1件 / 👀 要監視3件 / 🔕 低優先度25件
  📊 未解決の所見の全体はこのメッセージのスレッド ↓
  └ 返信: 📊 未解決の所見の全体 — 2026-11-08 09:00
      🚨 今すぐ対応 (1件) — 悪用あり、または悪用の可能性が高い
      イメージ: example/app:1.0
      ◆ openssl
        現在: 3.0.13-r0
        修正版: 3.0.15-r0
      …

11月9日（前回から変化なし、週次レポートの曜日ではない）
チャンネル: 🛡️ KestreLynx — 2026-11-09 09:00のスキャン結果
  前回のスキャンから変化なし
  📌 現在の未解決: 🚨 今すぐ対応1件 / 👀 要監視3件 / 🔕 低優先度25件
  🔗 前回のレポート時点の未解決の所見の全体 → スレッド
    → リンク先: 11月8日の返信（新しい返信なし）
```

最新のスキャンのレポートに検出項目があり、次のいずれかに該当すると返信を投稿します。

- 前回からの差分がある
- 週次レポートの曜日に当たる
- 初回通知などで有効な前回レポートへのリンクがない
- 通知先チャンネルを変更し、前回レポートへのリンクを引き継げない

返信の投稿条件を満たさない回は、新しい返信を付けず、チャンネルのメッセージ1通目の末尾に前回の返信へのリンクを載せます。
有効なリンクがない場合やリンクを表示できない場合は、リンクの案内を省略します。

最新のスキャンのレポートに検出項目がなければ、スキャン失敗や履歴の保持があっても、返信は投稿しません。
修正計画だけを送る回にも、返信は投稿しません。

`full`モードでは、返信や前回の返信へのリンクを付けず、未解決の所見をチャンネルのメッセージに直接載せます。
Slack Incoming Webhookは返信の投稿に対応しません。

返信の表示位置と前回の返信へのリンクは[スレッドのレポート](slack-display.md#thread-display)、接続設定は[設定](configuration.md)を参照してください。

## スキャン通知の再送 {#scan-redelivery}

`diff`モードでは、必要な通知の送信がすべて成功してから、次回の比較に使う履歴を保存します。

| 送信結果 | 履歴と次回の扱い |
| --- | --- |
| 全通知先への送信に成功 | 最新のスキャン後の状態を保存し、次回の比較に使用 |
| 一部または全部の送信に失敗 | 比較用の履歴を更新せず、次回も以前の履歴と比較 |
| 通知が不要 | 最新のスキャン後の状態をそのまま保存 |
| 送信後の履歴保存に失敗 | 次回も以前の履歴と比較するため、同じ変化を再通知する場合あり |

一部の通知先で失敗しても、ほかの通知先への送信は試みます。
そのため、次回は成功済みの通知先にも同じ変化が届く場合があります。

Slackの分割投稿やスレッド投稿が途中で失敗した場合、投稿済みのメッセージは残ります。
保存済みのレポートへのリンクは更新せず、次回の通知で重複して投稿される場合があります。

## 修正計画の送信条件 {#remediation-delivery}

修正計画は、スキャン通知とは別に送信の要否を判定します。
計画の生成やPR操作の判断は[修正計画の処理の流れ](remediation-logic.md#processing-flow)を参照してください。

### 通知先ごとの送信条件 {#remediation-destination-conditions}

修正計画は、通知先ごとに次の条件のいずれかに当たると送ります。
「—」の条件は、その通知先の判定には使いません。

| 条件 | Slack | メール | Webhook |
| --- | --- | --- | --- |
| 前回送った内容から変わった | 送る | 送る | 送る |
| `diff`モードの週次レポートの曜日で、表示する内容がある | 送る | 送る | — |
| まだ通知していないPR操作がある | — | — | 送る |
| PRの書き込みを止める問題が続いている | — | — | 送る |

PRの書き込みを止める問題は、続く間は毎回Webhookで通知します。

Slackとメールでは、通知に表示する修正計画やPRの情報（表示内容）を、それぞれ前回送った内容と比較します。
Webhookでは、計画内容・計画の利用可否・計画の保存失敗の状態を、前回送った内容と比較します。
どの通知先でも、計画の生成時刻は比較の対象から除外します。
表示の読み方は[Slackの修正計画](remediation-results.md#reading-results-in-slack-and-webhooks)を参照してください。

### 週次レポートの曜日の送信内容 {#remediation-weekly-content}

Slackとメールでは、週次レポートの曜日に送るPRの範囲を、表示内容に変化があるかどうかで決めます。
表示内容が変わっていない場合は、マージ済み・未マージでクローズ済みのPRを除外し、表示する内容が残らなければ送りません。
表示内容が変わった場合は、週次レポートの曜日に限らず、終了したPRも含めて通知します。

### Slackとメールの配信記録 {#remediation-email-delivery}

Slackとメールでは、前回何を送ったかを示す配信記録を別々に保持します。
メールの修正計画には、Slackと同じ表示内容を使います。
Slackへの配信成功だけでは、メールの修正計画を配信済みにはしません。

### Webhookに計画を含める回 {#remediation-webhook-delivery}

Webhookでは、スキャン通知やSlackの修正計画を送る回にも、現在の修正計画を含めます。
この場合は、計画に変化がなくても含めます。
データ形式は[修正計画の共通フィールド](webhook-remediation-reference.md#remediation-fields)を参照してください。

### 修正計画の再送 {#remediation-redelivery}

送った修正計画は通知先ごとに記録し、次回はこの記録と比べて送るかどうかを決めます。
記録しなかった内容は、次回もう一度送ります。

通知先ごとに、次のタイミングで記録します。

| 記録 | 記録するタイミング |
| --- | --- |
| Webhookの計画とPR操作 | すべての通知先への送信に成功したとき |
| Slackの修正計画の表示内容 | Slackの修正計画をすべて投稿できたとき |
| メールの修正計画の表示内容 | 修正計画を載せたメールを送れたとき |

Slackとメールは、ほかの通知先への送信が失敗しても、それぞれ上の条件を満たせば記録します。
記録の保存に失敗した場合は、送った内容をもう一度送ることがあります。
通知を再送しても、作成済みのPRを作り直すことはありません。
保存内容は[保存ファイル](remediation-pr-logic.md#stored-records)、PRの確認は[既存PRとの照合](remediation-pr-logic.md#existing-pr-matching)を参照してください。
