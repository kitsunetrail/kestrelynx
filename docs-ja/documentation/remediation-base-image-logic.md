# ベースイメージの更新候補の選定

固定タグでは、`FROM`のタグを変更するPRの候補を選びます。
浮動タグでは、再ビルドの案内を行います。

このページでは、更新対象の`FROM`の選び方、ベースレイヤーの照合、再ビルドの見込みを説明します。
このページで使う用語は[用語](remediation.md#terms)を参照してください。

## ベースイメージの特定 {#base-image-selection}

選んだビルドステージから`FROM`の継承をたどり、更新対象の外部イメージを特定します。
Dockerfileの場所とステージの指定は、次の情報から確認します。

- Dockerfileの対応付けを使う場合は、その`target`をステージの指定として使う
- Composeの`build:`から変更先を決められる場合は、そのcontext・Dockerfile・`build.target`を使う
- 同じリポジトリ・ベースブランチのDockerfileの対応付けとComposeの`build:`を併用する場合は、Dockerfileのパスと`target`が一致することを確認する
- Kubernetesでは`dockerfile`の対応付けで対象を指定し、Podのspecにあるイメージ名と稼働イメージの名前の一致も確認する

取得した`target`が指定するステージを使い、省略されている場合は最後のステージを使います。

次の架空のDockerfileの抜粋では、`FROM build`による継承と`COPY --from=build`によるコピーの違いを示します。

```dockerfile
FROM golang:1.22.1 AS build
FROM build AS test
FROM debian:12.5.1-slim AS runtime
COPY --from=build /out /out
```

選んだステージによって、タグを変更する候補の`FROM`は次のように変わります。

| `target` | たどる経路 | タグを変更する候補の`FROM` |
| --- | --- | --- |
| `test` | `test` → `build` → 外部イメージ | `FROM golang:1.22.1 AS build` |
| 省略または`runtime` | `runtime` → 外部イメージ | `FROM debian:12.5.1-slim AS runtime` |

`COPY --from`の参照先は、ベースを特定する経路に含めません。
最後の`runtime`を選んだ場合、`build`の`FROM`は更新対象になりません。

タグによって、候補の比較と案内を分けます。
ここでの「現在のベース」は、現在のDockerfileの`FROM`のタグが今レジストリで指しているイメージです。

| ベースのタグ | 処理 |
| --- | --- |
| 固定タグ | 同じ系列の最新パッチを比較する |
| 浮動タグ | 現在のタグが指すベースと稼働イメージのレイヤーを照合する |

固定タグの候補の採用には、ベースの修正対象を1件以上解消し、新しい所見を増やさないことが必要です。
判定条件と検証する範囲は、[対象別の検証範囲](remediation-logic.md#verification-scope)を参照してください。

同じ系列の候補で解消しない場合は、[新しい系列の確認](remediation-image-logic.md#newer-series-check)へ進めるかも調べます。

浮動タグでは、タグ更新PRや更新前後の脆弱性件数の比較は行いません。
変更先を特定できる入力の条件は、[Dockerfileの入力条件](remediation-source-formats.md#dockerfile-formats)を参照してください。

## ベースレイヤーの照合 {#base-layer-matching}

現在のベースイメージが稼働イメージの土台になっているかを、レイヤーの並びで確かめます。
ベースのレイヤー列と稼働イメージの先頭のレイヤー列を、順序も含めて照合します。

照合結果によって、次のように処理を分けます。

| 照合結果 | 処理 |
| --- | --- |
| 固定タグで一致 | ベースの修正対象の選定と候補の比較へ進む |
| 不一致 | そのベースの比較が稼働イメージを表すとは判断しない |
| レイヤー情報が空または利用不能 | 「比較不能」として扱う |
| 浮動タグで一致 | 現在のタグが指すベースからは更新を確認できないと判断する |

浮動タグで不一致の場合も、改善を確認した候補としては採用しません。
再ビルドの案内に添える見込みは、[浮動タグの再ビルドの見込み](#rebuild-check)で確認します。

!!! note "レイヤーの一致とビルド来歴"

    一致が示すのは、ファイルシステムのレイヤーの対応です。
    後の命令で同名・同版のパッケージを入れ直しても、Trivyがベースのレイヤーに属すると報告する場合があります。

### ベースの所見の選び方 {#base-findings}

所見のうち、ベースの修正対象に使うものを選びます。
スキャナのTrivyが報告するレイヤーによって、次のように扱います。

| 所見が属するレイヤー | ベースの修正対象としての扱い |
| --- | --- |
| 一致したベースレイヤー | 対象に含める |
| ベースより後のレイヤー | 対象に含めない |
| レイヤー情報がない | ランタイム本体の条件を満たす場合を除き、対象に含めない |
| 同じレイヤーIDがベース内外に現れ、区別できない | ランタイム本体の条件を満たす場合を除き、対象に含めない |

### ランタイム本体の扱い {#base-runtime-findings}

Node.jsやPythonの本体である言語ランタイムの所見は、版の環境変数も使ってベース由来として扱うかを判断します。
これはベース由来として扱うための判定であり、ビルド来歴を証明するものではありません。

固定タグでは、次の条件をすべて確認します。

1. 現在のベースのレイヤー列と稼働イメージの先頭が一致する
2. 稼働イメージと現在のベースのイメージ設定の両方に、対象ランタイムの版の環境変数がある
3. 環境変数の値が、稼働イメージと現在のベースで一致する

変数はNode.jsでは`NODE_VERSION`、Pythonでは`PYTHON_VERSION`です。
同名の環境変数が複数ある場合は、最後の値を使います。

条件をすべて満たすと、レイヤーに割り当てられなかったランタイム本体の検出結果を、ベースの修正対象に含めます。
現在のベースと候補の比較でもランタイムを照合し、どちらかで比較対象のランタイムを照合できなければ、判定不能として候補を採用しません。

## 浮動タグの再ビルドの見込み {#rebuild-check}

現在のベースと稼働イメージを突き合わせ、再ビルドの案内に添える見込みを調べます。
通常の候補比較によるPRの採用判定とは別の処理で、イメージはビルドしません。

対象は、浮動タグの`FROM`で、現在のベースのレイヤーが稼働イメージの先頭と一致しない場合です。
このレイヤー不一致の判定を、`floating_base_unconfirmed`と記録します。

パッケージの場所とCVEで突き合わせ、結果を`rebuild_check`に記録します。

修正計画の1項目は、1つのDockerfileの1つの`FROM`を対象とします。
同じ`FROM`を使ってビルドした複数の稼働イメージの結果を、その項目にまとめます。

ランタイム本体については、次の条件を満たす場合に再ビルドの見込みを求めます。

1. 稼働イメージにランタイム本体の検出結果がある
2. 現在のベースのイメージ設定から、そのランタイムの版を照合できる

条件を満たすと、再ビルドでベースの版を引き継いだ場合に出なくなる見込みの件数を求め、`rebuild_runtimes`に記録します。
対象は検出中の同じランタイムのCVEで、新しい版で増えるCVEは数えません。

完成イメージの比較ではないため、判定は`not_comparable`（「比較不能」）のままです。

項目全体の案内は、同じ`FROM`を使う全稼働イメージについての見込みをまとめたものです。
対象の全稼働イメージが`floating_base_unconfirmed`の場合だけ、項目全体の見込みを載せます。

たとえば、同じ`FROM`を使う2つの稼働イメージのうち、現在のベースとレイヤーが不一致なのは一方で、もう一方は一致する場合です。
不一致のイメージの`rebuild_runtimes`は個別の記録に残しますが、項目全体の見込みは載せません。

!!! note "ランタイム本体の既知の制約"

    - 後のレイヤーで`node`や`python`の実行ファイルだけを差し替えていても、版の環境変数が同じなら区別できない
    - Dockerfileでランタイムを入れ直す場合や、`ENV`で版を上書きする場合は、再ビルドの見込みが外れることがある

スキャンの準備では、比較条件とスキャン数の上限を確認します。

| 準備するもの | 処理 |
| --- | --- |
| 現在のベース | タグが現在指す内容をレジストリから、[スキャンの比較条件](remediation-logic.md#comparison-conditions)でスキャンする |
| 稼働イメージ | スキャン条件が比較に使う条件と違う場合は再スキャンする |
| スキャン数 | `baseline_rescans_per_cycle`の残りを使う |
| 同じベースの内容 | 1サイクルに1回だけスキャンする |

実行順序は、計画・言語パッケージの更新・新しい系列の確認のあと、計画の保存の前です。
[上限とPR処理の分の確保](remediation-image-logic.md#newer-series-limits)と同じ仕組みで、PR処理のための時間とレジストリ要求を残します。

PR処理の分を確保するために確認を止めた場合は、`newer_series_reserved`を記録します。

### 突き合わせの方法 {#rebuild-check-matching}

同じ場所にあるパッケージについて、現在のベースにも対象のCVEが残っているかを確かめます。

パッケージの`status`は、Trivyが報告する脆弱性の修正状態です。
`fixed`は修正版の公開を示し、稼働イメージでの解消を示す値ではありません。

突き合わせに使う所見は、次のように選びます。

| 対象 | 使う所見 |
| --- | --- |
| 稼働イメージ | 深刻度の範囲内で、statusが`fixed`かつ修正版がある所見 |
| 現在のベース | 修正版のない所見も含め、深刻度の範囲内のすべての所見 |
| 言語ランタイム本体 | [浮動タグの再ビルドの見込み](#rebuild-check)で求める`rebuild_runtimes`の所見 |

パッケージは、種類・分類（OSか言語パッケージか）・名前と場所で照合します。
`PkgPath`と`Target`は、スキャナのTrivyが報告するパッケージの場所の情報です。

種類ごとに、照合に使う場所と、場所の照合ができず未判定にする条件を示します。

| パッケージの種類 | 照合に使う場所 | 照合できない条件 |
| --- | --- | --- |
| OSパッケージ | パスを使わず、パッケージ名で照合する | ベースのOSを判別できない |
| `node-pkg` | `PkgPath`をそのまま使う | `PkgPath`が空 |
| `python-pkg` | `PkgPath`の`.dist-info`か`.egg-info`の要素から、パッケージ自身の版を除いて使う | `PkgPath`が空 |
| `jar` | `PkgPath`のファイル名の末尾が`-<版>.jar`の場合に、パッケージ自身の版を除いて使う | `PkgPath`が空 |
| その他の種類 | `PkgPath`を使い、空なら`/`を含むパスとしての`Target`を使う | `PkgPath`が空で、`Target`に`/`がない |

たとえば、pip自身の版だけが違う次のパスは、同じ場所として照合します。

| pipの版 | Trivyが報告する`PkgPath` |
| --- | --- |
| `25.0.1` | `usr/local/lib/python3.12/site-packages/pip-25.0.1.dist-info/METADATA` |
| `25.3` | `usr/local/lib/python3.12/site-packages/pip-25.3.dist-info/METADATA` |

次のいずれかに当てはまる所見も、未判定にします。

- ベースの同じ場所に複数の版がある
- ベースの同じ場所に同じ版があるのに、CVEが報告されていない
- 言語ランタイム本体の所見が、検出された版の`rebuild_runtimes`に含まれない

OSパッケージ・`node-pkg`・`python-pkg`・`jar`以外の種類では、ベースの同じ場所に対応するパッケージも対象CVEもない場合に別の場所を確認します。
別の場所に同じ種類・分類・名前のパッケージがあれば、未判定にします。

### 突き合わせの結果 {#rebuild-check-results}

`rebuild_check`は、所見が消える見込み、残る所見、未判定の件数などを表します。
Webhookの[現在のベースとの突き合わせ](webhook-remediation-dockerfile-reference.md#dockerfile-rebuild-check)で使うフィールドは、次のとおりです。

| フィールド | 意味 |
| --- | --- |
| `gone` | ベースの同じ場所に別の版があり、対象のCVEがないパッケージの記録 |
| `remaining` | ベースの同じ場所に同じCVEがあるパッケージの記録 |
| `not_in_base` | ベースの同じ場所にないOSパッケージまたはグローバルな`node_modules`のパッケージの記録 |
| `other_not_in_base` | アプリの依存など、`not_in_base`の対象以外でベースの同じ場所にないパッケージの数 |
| `only_in_base` | ベースの深刻度の範囲内でstatusが`fixed`かつ修正版があり、稼働イメージの同じ場所に対象の所見がないパッケージの記録 |
| `undetermined` | 判定できなかった所見の数 |

確認の状態は、`rebuild_check.status`に記録します。
複数の稼働イメージがある場合は、個別の状態から項目全体の状態を決めます。

| 状態 | 意味 | 項目全体がその状態になる条件 |
| --- | --- | --- |
| `checked` | 対象の所見をすべて判定した状態 | 全稼働イメージが`checked` |
| `partial` | 未判定の所見がある状態 | `not_checked`がなく、`partial`が1つ以上ある |
| `not_checked` | 比較しておらず、`reason`と`detail`に説明を記録する状態 | `not_checked`が1つ以上ある |

同じ`FROM`を使う2つの稼働イメージが、どちらも`floating_base_unconfirmed`の場合の例です。

| 稼働イメージAの状態 | 稼働イメージBの状態 | 項目全体の状態 |
| --- | --- | --- |
| `checked` | `partial` | `partial` |

複数の稼働イメージの結果を項目全体にまとめる際は、次の規則も使います。

- 項目の`rebuild_check`は、全稼働イメージが`floating_base_unconfirmed`の場合だけ付ける
- `gone`には、その所見を持つすべての稼働イメージで消えるものだけを含める
- プラットフォームによってベースの版が違う場合は、版ごとに別の記録にする

浮動タグの案内の読み方、通知の分岐、見込みの制約は、[再ビルドの案内](remediation-update-results.md#rebuild-guidance)を参照してください。

## マージ済みのPRが反映されていない場合 {#base-update-not-deployed}

ベース更新のPRはマージされたが、稼働中のイメージはまだ古いベースから作られている場合を知らせるための判定です。
PR処理の記録を使うため、`pull_requests`の設定によるPR処理が動いているときだけ行います。

`base_layers_mismatch`の項目について、次の5条件をすべて確認します。

- 最新の修正計画の処理で対象のリポジトリをGitHubから確認でき、記録のリポジトリIDと一致する
- KestreLynxが作ったDockerfileのPRがマージ済みで、同じリポジトリ・ベースブランチ・ファイル・ステージを対象としている
- PRのブランチやベースが他者に変更されず、KestreLynxが作った内容のままである
- PRで変更したあとの`FROM`と、現在のDockerfileの`FROM`が、同じイメージの同じタグを指定している
- すべての稼働イメージのイメージIDが、PRの作成時に記録した稼働イメージのIDと一致する

たとえば、同じイメージのタグを説明用にA・Bとすると、PRでAからBへ変更し、現在のDockerfileもBを指定している場合です。
イメージ名は、`python`と`docker.io/library/python`などの表記ゆれを含めて照合します。

条件をすべて満たす場合、項目の理由を`base_update_not_deployed`に変えます。
該当するPRが複数あれば、番号が最も大きいものを使います。

項目の区分は`not_comparable`のまま、稼働イメージごとの判定は`base_layers_mismatch`のままです。

## 再ビルドの手順の案内 {#rebuild-commands}

再ビルドの案内には、イメージのビルド方法に応じたコマンドを示します。
Composeの`build:`と`container/<名前>`の対応付けが同じDockerfileを使う場合は、`docker compose build --pull`と`docker build --pull`の両方を示します。

それぞれ再ビルドしたイメージでコンテナを作り直します。
