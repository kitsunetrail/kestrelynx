# 修正版に上げられないときの案内の仕組み

修正版に上げられないときに案内を出す条件、確認する公開版、修正版を使えるかの判定、公開版情報の読み込みの上限を説明します。
表示の読み方は[修正版に上げられないときの案内](remediation-fix-hints.md)、用語は[用語](index.md#terms)を参照してください。

## 案内を出す条件 {#fix-hints-conditions}

案内の対象は、更新が修正版に届かなかった理由や、計画で手動対応になった理由を確認できたパッケージです。

### npm・pnpm・uv・pip

npm・pnpm・uvの[依存元からの再解決](remediation-reresolution-logic.md#dependent-reresolution)では、プロジェクトの指定範囲内で依存元（対象パッケージを使うパッケージ）の版を選び直し、対象を含む依存関係を解決し直します。
依存元の公開版を調べる対象になり得る再解決の結果は、次の3つです。

| 再解決の結果 | 条件 |
| --- | --- |
| `not_fixed` | 指定範囲内で解決し直しても対象が修正版に届かない |
| `rejected` | 検査などで更新結果を採用できないか、新たに使う版の公開後の待機で再解決が3回連続して保留になり、再試行を停止する |
| `not_tried` | 扱える範囲や処理の上限などを理由に再解決を見送る |

公開版を調べるには、対象パッケージと、版指定で更新を妨げた依存元の記録が必要です。
公開後の待機が3回に達した回は`rejected`を記録しても公開版を調べないため、結果コードだけでは公開版の行の有無は決まりません。

pipでは、`requirements.txt`の固定版を書き換えた後に依存を解決できず、更新先の版を許さない依存元を特定できた場合に案内を出します（`dependents_hold_back`）。

### Go

Goでは、プロジェクトの`go.mod`で必要なGoを指定する`go`の行と、使用を推奨するGoツールチェーンを指定する`toolchain`の行を確認します。
次の表のビルド版の上限は、対象の稼働中のバイナリをそれぞれビルドしたGoの版のうち、最も低い版です。

| 条件 | 理由コード |
| --- | --- |
| 変更後の`go`の版がビルド版の上限を超える | `go_line_raised_too_far` |
| 変更後の`toolchain`の版がビルド版の上限を超える | `go_line_raised_too_far` |
| ビルドしたGoが不明なまま`go`または`toolchain`の版が変わる | `go_line_raised_too_far` |
| 更新に使えるGoの中に、必要な版以上のものがない | `go_runtime_unavailable` |

必要なGoを宣言する依存モジュールと版を特定できたときに詳しい案内を出し、`toolchain`の変更だけが原因の場合はモジュール名を添えた案内を省きます。
`go_line_raised_too_far`の案内でビルドしたGoが不明な場合に限り、末尾に`・稼働中のバイナリをビルドした Go は不明）`と表示します。

記録条件は[Goの更新結果の検査](remediation-go-logic.md#go-update-validation)と[Goの選定](remediation-go-logic.md#go-runtime-selection)、PR本文の記載は[GoのPR](remediation-pr-results.md#go-pull-requests)を参照してください。

現在のモジュールパスのままでは更新目標のメジャー版を使えない場合（`fix_in_other_major_version`）は、計画で手動対応になったパッケージも[別のメジャー版の調査](#fix-hints-go-lookup)に含めます。
`v0`から`v1`への更新のように現在のパスで更新目標に届く場合は、別のメジャー版の案内の対象外です。

### Maven・Gradle

Maven・Gradleでは、更新できない版の指定元、更新後に古い版が残る依存経路、または別のメジャー版の修正版を案内します。
pomはMavenの依存や設定を記述するファイルで、プロジェクトは親pomから設定を引き継いだり、依存の版をまとめて指定するpom（BOM）を取り込んだりします。

案内の種類は、次の条件と理由コードで決まります。

| 条件 | 理由コード |
| --- | --- |
| 自動更新で指定を書き換えられず、対象の版を決める外部の親pom・BOM・Spring BootのBOMを特定できた | Mavenは`maven_version_source_unsupported`、Gradleは`gradle_version_source_unsupported` |
| 更新後も対象がMaven Central（公開パッケージの配布元）から選んだ版に届かない | `target_not_updated` |
| 対象の脆弱性について、稼働版より新しい別メジャー版の修正版が脆弱性情報にあり、稼働版のメジャー版には今回の更新に使える修正版が見つからない | `maven_fix_in_other_major` |
| 稼働版のメジャー版に修正版が報告されていても、Maven Centralでそのメジャー版に更新目標以上の使用可能な公開版が見つからない | `maven_release_not_found` |

`target_not_updated`では古い版を持ち込む依存元が分かれば依存元を示し、Gradleで依存元がなく構成（用途別の依存のまとまり）が直接指定していれば構成名を示します。
指定元の記録条件は[Mavenの版の出所と書き換え](remediation-maven-logic.md#maven-version-sources)と[Gradleの版の宣言と書き換え](remediation-gradle-logic.md#gradle-version-sources)、更新後の記録条件は[Mavenの更新結果の検査](remediation-maven-logic.md#maven-update-validation)と[Gradleの更新結果の検査](remediation-gradle-logic.md#gradle-update-validation)を参照してください。

### Rust

`cargo_fix_in_other_series`では、稼働イメージの勧告が挙げる修正版を比較し、共通の版を案内できるかを計画時に判定します。
案内のためにcrates.ioの公開版を追加で問い合わせることはありません（[crateの目標版](remediation-cargo-logic.md#cargo-target-versions)）。

## npm・pnpm・uv・pipで確認する公開版と判定 {#fix-hints-dependent-lookup}

依存元の正式版（ベータ版などのプレリリースでない公開版）のうち、現在使っている依存元の版以上のものを確認します。
確認する版は、マネージャーと、プロジェクトが依存元を直接指定しているかどうかで決まります。

| マネージャー | 依存元 | 確認する正式版 |
| --- | --- | --- |
| npm・pnpm | 直接依存 | `package.json`の指定範囲内の最新と全体の最新 |
| uv | 直接依存 | `pyproject.toml`の指定範囲内の最新と全体の最新 |
| npm・pnpm・uv | 直接依存以外 | 全体の最新 |
| pip | 直接指定の有無を問わない | 全体の最新 |

公開版の選び方と、対象パッケージへの版指定をどこから読むかは次のとおりです。

| 対象 | 規則 |
| --- | --- |
| npm・pnpm・uv | 範囲内の最新と全体の最新が一致すれば、全体の最新の行を省く |
| uv・pipの公開版 | Pythonパッケージの配布元PyPIの一覧から、取り下げられていない配布ファイルがある版を選ぶ |
| npm・pnpmの依存元の新しい版 | npmレジストリから対象への依存の指定を読む |
| uv・pipの依存元の新しい版 | PyPIの公開版情報の`requires_dist`（依存要件の一覧）を読み、環境によって要件を切り替える条件にかかわらずすべての要件を確認する |
| npm・pnpm・uvで選んだ版が依存元の現在の版と一致 | 更新を妨げたときの指定を使い、ほかの修正版を許すかは調べ直さない |

pipで依存元の最新が現在の版と一致する場合だけは、公開版の要件を読み直さず、pipが依存を解決した環境で有効だった、依存元から対象への要件をすべて使います。

依存元の指定で修正版を使えるかは、次の順で判定します。

1. 対象の公開済みの正式版から、対象の脆弱性をすべて直す版を探す
2. 見つかった修正版の少なくとも1つが依存元の要件をすべて満たせば、`修正版の … を使える`と表示する

比較する候補には、対象パッケージの先頭行にある更新目標以外の修正版も含みます。

npm・pnpm・uvでは、確認した依存元の版と再解決の結果に応じて次の文言を表示します。

| 表示する条件 | Slackの表示 |
| --- | --- |
| 直接依存の指定範囲内の最新が修正版を許し、プロジェクト全体の再解決は`not_fixed`になった | `修正版の … を使えるが、今回の更新では上げられなかった` |
| 直接依存でない依存元の最新が修正版を許すか対象を直接要求しなくなり、経路となる直接依存の名前が分かる | 最新の行の下に`… のどの版でこの … が入るかは未確認` |

再解決にはほかのパッケージやPythonの版などの条件もかかるため、`not_fixed`の表示だけでは修正版に届かなかった具体的な制約までは特定できません。

## Goの案内で確認する情報 {#fix-hints-go-lookup}

別のメジャー版の案内では、プロジェクトの依存を変更せずに、修正版と現在のモジュールパス（モジュールを識別する名前）を要求する依存元を調べます。
確認する情報と取得先は次のとおりです。

| 確認するもの | 確認方法 |
| --- | --- |
| 案内する修正版 | 脆弱性情報にある修正版のうち、対象の脆弱性をすべて直す最も低い版を選ぶ |
| プロジェクトの直接指定 | GitHubから`go.mod`と`go.sum`を読み、`go.mod`の依存宣言を確認する |
| 直接指定でない対象の依存元 | プロジェクトが要求するほかの各モジュールの`go.mod`をGoモジュールプロキシ（公開モジュールの配布元）から読む |
| 依存元の最新の版 | プロキシの`@latest`で版を取得し、現在の版より新しければ最新版の`go.mod`を読む |

プロジェクトの宣言と依存元の要求に応じて、次のように案内を決めます。

- プロジェクトの`go.mod`が対象を`// indirect`なしで要求していれば、直接指定として依存元を探すプロキシの読み込みを省く
- 直接指定でなければ、対象を要求するモジュールの名前と版、要求している対象の版を記録する
- 依存元の最新版が現在のモジュールパスを要求しなければ`… を直接は使っていない`、要求していれば`修正版の … を使えない`と表示する
- 最新版が依存元の現在の版と一致すれば記録済みの要求を使い、現在より古い版や比較できない版の行は省く
- 新しい版の`go.mod`がプロキシの自動生成によるものなら、または必要な情報をプロキシから読めなければ、該当する公開版の行を省く

## Maven・Gradleの修正の判定 {#fix-hints-maven-judgement}

Maven・Gradleでは、依存元や版を決めるpomの公開版が修正版を指定するかを、次の順で判定します。

1. 依存元または版を決めるpomについて、確認する公開版を選ぶ
2. 選んだ公開版のpomから、対象パッケージに指定する版を読む
3. 指定された版を更新目標と比べ、対象の脆弱性ごとに修正版と比べる

### 確認する公開版の選び方

依存元または版を決めるpom自身の現在の版を基準に、現在の版以上の正式版を選びます。
メジャー・マイナー版の組み合わせ（`2.13`など）を「系列」と呼び、次の2つの範囲で最新の版を探します。

- 現在の版と一致する系列の最新（現在の版も候補に含む）
- 系列を問わず全体の最新（系列内の最新と一致すれば`最新`の行を省く）

### pomから対象パッケージの版を読む方法

選んだ公開版のpomと親pomをたどり、`dependencies`（直接使う依存の宣言）と`dependencyManagement`（依存に適用する版などの指定）を調べます。
版を読む場所はpomの役割で異なります。

| 確認するpom | 対象の版の読み方 |
| --- | --- |
| 親pom | 最も近い`dependencies`の宣言に版があれば使い、宣言または版がなければ`dependencyManagement`を調べる |
| 依存元のpom | 最も近い`dependencies`の宣言に版がなければ`dependencyManagement`を調べ、宣言自体がなければ対象を指定していないと判定する |
| BOM | `dependencyManagement`で指定した版を読む |

`dependencyManagement`に対象の指定が見つからなければ、取り込んだBOMを順に調べ、最初に対象を管理するBOMの指定を使います。
親pomは10段まで、取り込んだBOMは最初のpomから4段先の指定まで確認し、深さの上限で版を確定できなければ公開版の行を省きます。

プロファイル（条件に応じて使うpomの設定）が、確認するpom・親pom・取り込んだBOMのいずれかで次の条件をともに満たす場合も、該当する公開版の行を省きます。

- 既定で有効になる指定（`activeByDefault`）か、Javaの版（`jdk`）、OS（`os`）、設定値（`property`）、ファイル（`file`）による有効化条件がある
- 依存、`dependencyManagement`、プロパティ（pomで参照する設定値）、親pomのいずれかを変える

名前で明示的に選んだときだけ有効になるプロファイルは、判定を止めません。

### 脆弱性ごとの比較と表示

`-jre`・`-android`のような版の末尾の区分を「系統」と呼びます。
脆弱性ごとに、pomが指定する版と系統が一致する修正版と、系統の指定がない修正版を比較の対象にします。

比較に使う下限は、表を上から順に読んで最初に当てはまる行で決まります。

| 適用できる修正版 | 指定された版に必要な条件 |
| --- | --- |
| 指定された版の系列に修正版がある | 該当する系列の最も高い修正版以上 |
| 指定された版の系列にはなく、メジャー版が一致する修正版がある | 該当するメジャー版の最も高い修正版以上 |
| メジャー版が一致する修正版はなく、ほかのメジャー版に修正版がある | 適用できる修正版全体のうち最も高い版以上 |
| 適用できる修正版がない | 脆弱性が直るとは判定しない |

修正版が`2.12.7`と`2.13.4`の脆弱性では、pomが指定する版の系列によって比較先が変わります。

| 指定された版 | 系列が一致する修正版 | 脆弱性の判定 |
| --- | --- | --- |
| `2.13.2` | `2.13.4` | `2.13`系列の修正版に届かないため直らない |
| `2.12.8` | `2.12.7` | `2.12`系列の修正版以上なので直る |

修正版が`2.5.15`・`2.6.15`・`2.7.12`・`3.0.7`の脆弱性について、pomが`2.8.0`を指定する場合は、`2.8`系列に修正版がありません。
メジャー版が一致する修正版のうち最も高い`2.7.12`と比べます。

系統を指定した版と系統の指定がない修正版の扱いを、`-android`と`-jre`の例で示します。

| 脆弱性情報の修正版 | 指定された版 | 比較に使うか |
| --- | --- | --- |
| `33.7.2-android` | `33.8.0-jre` | 系統が違うため使わない |
| `33.7.2` | `33.7.2-jre` | 修正版に系統の指定がないため使う |

公開版のpomから確認できた内容に応じて、Slackの文言を選びます。

| 判定の条件 | Slackの表示 |
| --- | --- |
| 指定された版が更新目標以上で、対象の脆弱性をすべて直す | `修正版を指定している` |
| 版を指定しているが、更新目標に届かないか、対象の脆弱性の少なくとも1件で修正を確認できない | `修正版を指定していない` |
| 依存元のpomでは対象の直接宣言がないか直接宣言に適用する版の指定がなく、親pom・BOMでは対象の版を設定していない | `… を指定していない` |

別のメジャー版を案内する場合も、対象の脆弱性ごとに系統と系列を確かめ、すべてを直す候補のうち最も低い版を選びます。
候補の取得先と条件は、[目標版とMaven Centralの版](remediation-maven-logic.md#maven-target-versions)の規則で決まります。

- `maven_fix_in_other_major`では、脆弱性情報にある稼働版より新しい別メジャー版のうち、プレリリースを除き、稼働版と系統が一致するか系統の指定がない修正版を候補にする
- `maven_release_not_found`では、Maven Centralにある更新目標以上の別メジャー版の正式版のうち、稼働版と系統が一致する公開版を候補にする

条件を満たす版を特定できた場合の表示は、[修正版が別のメジャー版にしかない場合](remediation-fix-hints.md#fix-hints-maven-other-major)を参照してください。

## 公開版情報の読み込み時期と上限 {#fix-hints-lookup-limits}

依存元や版を決めるpomの公開版は、計画での扱いとPRに含める更新が決まった後に調べます。
更新を試す項目では、次の順に処理します。

1. 更新を試す
2. 更新結果をPRに含めるか決める
3. 依存元や版を決めるpomの公開版の情報を読む
4. 結果を通知する

Maven・Gradleの`maven_release_not_found`では、対象パッケージ自身の現在のメジャー版から更新先を選べなかった場合に限り、更新中にMaven Centralから取得した対象パッケージの版の一覧を使って、その場で別のメジャー版の候補を探します。

案内の有無や内容は、計画やPRに影響しません。
公開版の情報を読めなくても、確認できている依存元や版を決めるpomの情報は残します。

表の「1項目」は、リポジトリ・ブランチ・ディレクトリが一致する依存ファイルを言語ごとにまとめた修正計画の1件です。

| マネージャー | 読む先 | 依存元との組み合わせ | 確認する公開版 | 読み込み件数の上限 | 時間の上限 |
| --- | --- | --- | --- | --- | --- |
| npm・pnpm | npmレジストリの公開版と依存の指定 | 1項目あたり3件 | 依存元ごとに最大2版 | — | 1項目あたり合計30秒 |
| uv | PyPIの公開版と`requires_dist` | 1項目あたり3件 | 依存元ごとに最大2版 | — | 1項目あたり合計30秒 |
| pip | PyPIの公開版と`requires_dist` | 1項目あたり3件 | 依存元ごとに最新1版 | — | 1項目あたり合計30秒 |
| Goの別メジャー版の案内 | GitHubの`go.mod`・`go.sum`とGoモジュールプロキシの`@latest`・`go.mod` | 1項目あたり3件 | 依存元ごとに最新1版 | プロキシの`go.mod`を1項目あたり200件 | 1項目あたり合計30秒 |
| Maven・Gradle | Maven Centralの版の一覧とpom・親pom・取り込むBOM | 依存元について1項目あたり3件 | 依存元または版を決めるpomごとに最大2版 | 対象パッケージあたり12件 | 1項目あたり合計30秒 |

対象パッケージの名前と、依存元の名前・現在の版で1組と数えます。
依存元の公開版を2つ確認しても、組み合わせは1件です。

ファイルなどの読み込み件数は次のように数えます。

- Goの200件には、依存元を探すための`go.mod`と、依存元の最新版で読む`go.mod`を含める
- Maven・Gradleの12件には版の一覧も含め、対象パッケージの依存元すべてで読み込み件数を合算する
- Maven・Gradleの12件は案内のための追加の読み込みに適用し、`maven_release_not_found`で再利用する版の一覧は更新時の読み込みとして数える

### 公開版の行を省く条件 {#fix-hints-omitted-lines}

公開版の指定から結論を出せない場合は、該当する公開版の行を省きます。
対象パッケージの1行目にある原因の表示は残り、行を省いた公開版で修正版を使えるかは未確認です。

npm・pnpmの`peerDependencies`は利用側で一緒に使うパッケージへの要件、別名指定はパッケージを公開名と異なる名前で使う指定です。
shrinkwrapは、配布するパッケージの依存の版を固定するファイル（`npm-shrinkwrap.json`）です。

新しい公開版の指定を読む場合や、必要な情報を取得できない場合には、次の条件で行を省きます。

| 対象 | 行を省く条件 | 公開版にある指定の例 |
| --- | --- | --- |
| npm・pnpmのpeer依存 | 対象が`peerDependencies`にあるか、pnpmで`peerDependenciesMeta`だけに任意のpeer依存として記録されている | `peerDependencies`に`"multer": "^2.5.0"` |
| npm・pnpmの別名指定 | 対象を別名で宣言している | `"upload": "npm:multer@^2.5.0"` |
| npm・pnpmの異なる範囲 | 通常の依存（`dependencies`）と任意の依存（`optionalDependencies`）で対象への指定が異なる | `multer`の通常の依存は`^2.4.0`、任意の依存は`^2.5.0` |
| npm・pnpmの評価できない指定 | 対象への指定を数値の版の範囲として評価できない | `"multer": "latest"` |
| npm・pnpmのshrinkwrap | 公開版にshrinkwrapが含まれる | `npm-shrinkwrap.json` |
| uv・pipの異なる指定 | 公開版の要件に、対象への異なる版指定がある | `urllib3<1.27; python_version < "3.10"`と`urllib3<3; python_version >= "3.10"` |
| uv・pipの読めない要件 | パッケージ名と版の指定として読み取れない要件がある | `urllib3 @ https://example.com/urllib3.whl` |
| uv・pipの評価できない指定 | 対象への版の条件を評価できない | `urllib3===2.2.2` |
| 情報の取得失敗 | 配布元などから必要な情報を読めない | — |
| 調査の上限 | 読み込み件数または時間の上限で確認を終えられない | — |
