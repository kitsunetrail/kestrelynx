# Goの更新

KestreLynxは、稼働イメージのGoバイナリに組み込まれた依存モジュールの脆弱性を修正するため、`go.mod`・`go.sum`の更新をPRで提案します。
稼働イメージへの反映には、利用者によるバイナリの再ビルドと、そのバイナリを含むイメージの配置が必要です。

更新は次の順に進みます。

1. アプリケーションのGoバイナリから更新対象を選ぶ
2. モジュールの目標版を決め、公開と撤回の有無を確かめる
3. 更新を実行する作業用のGoを選ぶ
4. 選んだGoで`go get`を実行する
5. ファイルの差分、ハッシュ、依存の要求、スキャン結果を検査する

詳しくは、[Goの候補選定](#go-package-selection)、[Goの選定](#go-runtime-selection)、[Goの実行設定](#go-worker-settings)、[Goの更新結果の検査](#go-update-validation)を参照してください。
このページで使う用語は[用語](remediation.md#terms)を参照してください。

## Goの候補選定 {#go-package-selection}

更新対象は、アプリケーションのGoバイナリに組み込まれた依存モジュールです。
TrivyがGoバイナリから検出した所見の種類は、`gobinary`です。

対応付けた`go.mod`とバイナリを、次の条件で照合します。

| 照合する内容 | 扱い |
| --- | --- |
| バイナリのメインモジュールのパスが`go.mod`の`module`と一致する | 更新対象として選ぶ |
| メインモジュールのパスが一致しない | そのバイナリの所見を計画に含めない |
| 組み込まれた依存の版が`require`と一致しない | `go_binary_not_from_source`で手動対応にする |
| パッケージ一覧が切り詰められている | `go_binary_not_from_source`で手動対応にする |

たとえば、ベースイメージに含まれるツールのバイナリは、メインモジュールのパスが一致しなければ計画に含めません。

必要なファイルと手動対応になる入力は、[Goの依存ファイル](remediation-dependency-formats.md#go-inputs)を参照してください。

### モジュールの目標版 {#go-target-versions}

モジュールの目標版は、修正版から選び、公開情報で確かめます。

撤回とは、モジュールの作者が`go.mod`の`retract`で、その版を使わないよう指定することです。
選定と確認は、次の順で進めます。

1. CVEごとに稼働版より新しい最小の修正版を選び、その中の最大値を更新目標にする
2. `proxy.golang.org`の`.info`で、目標版の存在と`+incompatible`を含む正規の表記を確かめる
3. `@latest`で得た最新版の`go.mod`にある`retract`を調べ、目標版が撤回されていないか確かめる
4. 目標版が撤回されていたら、`@v/list`から代わりの修正版を探す

代わりの修正版には、次の条件をすべて満たす版のうち、最も低い版を選びます。

- 撤回された版と同じメジャー版である
- モジュールパスに合う
- プレリリースではない
- 撤回された版より新しい
- すべての対象脆弱性を直せる
- 撤回されていない

選んだ代わりの版も`.info`で正規の版と照合して更新に使います。
撤回された版の代わりに選んだことを、更新の注記に残します。

自動で目標版を決められない場合は、次のように扱います。

| 状況 | 扱い |
| --- | --- |
| 修正版が別のメジャー版の別モジュールパスにしかない | `fix_in_other_major_version`で手動対応にする |
| 撤回された版に代わる条件を満たす版がない | `go_release_retracted`で手動対応にする |
| 代わりの版を探すための版一覧を取得できない | `go_release_retracted`で手動対応にする |

別のメジャー版が必要な場合は、更新段階で[修正版に上げられないときの案内](remediation-fix-hints.md#fix-hints)を確認します。
修正版の下限に関する共通規則は、[修正版の下限](remediation-package-logic.md#fix-lower-bound)を参照してください。

### 標準ライブラリの再ビルド案内 {#go-stdlib-rebuild}

標準ライブラリの`stdlib`の所見は、`go.mod`の更新PRに含めません。
修正計画の別項目で「この版以上のGoでビルドし直すと直る」と案内します。

案内するGoは、ビルドに使われたGoと同じ系列（Go 1.26のようにmajor・minorが同じ版のまとまり）で、全CVEを直せる最小の版です。
同じ系列に該当する版がなければ、全CVEを直せる新しい系列の版を案内します。

## Goの選定 {#go-runtime-selection}

作業用のGoは、依存ファイルの更新を実行するために選びます。
Goを選ぶ前に、更新対象の目標版の`go.mod`を読み、ほかの更新対象に目標より高い版を要求していないか調べます。

目標より高い版が必要な場合は、その要求された版の`go.mod`も確認します。
必要なGoの版は、次の宣言が示す版のうち、最も高い版です。

| 宣言を読むファイル | 確認する行 |
| --- | --- |
| 入力の`go.mod` | `go`・`toolchain` |
| 更新対象モジュールの目標版の`go.mod` | `go` |
| 目標より高い版を要求された対象モジュールの、その要求版の`go.mod` | `go` |

必要な版を満たす実行環境を、KestreLynxに組み込まれた対応版の一覧から選びます。
一覧は[対応する実行環境](remediation-reference.md#supported-runtimes)を参照してください。

| 選ぶ内容 | 規則 |
| --- | --- |
| 作業用の系列 | 対応版の一覧にある実行版が必要な版以上となる、サポート中の最小の系列を選ぶ |
| 実行する版 | 選んだ系列の一覧の版を含む、digestで固定した公式`golang`イメージのGoを使う |
| 条件を満たす実行版がない場合 | `go_runtime_unavailable`で手動対応にする |

作業用のGoには、稼働中のバイナリをビルドしたGoの版による上限を設けません。
`go.mod`の`go`・`toolchain`の変更には、別途[ファイルと版宣言の変更](#go-file-changes)の条件を適用します。

依存モジュールの要求で作業用Goを選べない場合は、必要なGoの版と、それを要求するモジュールのパス・版を案内します。
案内の表示は[修正版に上げられないときの案内](remediation-fix-hints.md#fix-hints)を参照してください。

案内に使う`packages[].fix_hint.go_line`は、次の条件で記録します。

- 目標版またはGoの選定前に確認した要求版の`go.mod`の`go`の行が原因なら、モジュールのパスと版、必要なGoの版を記録する
- プロジェクト自身の`go`・`toolchain`の行が原因なら、`fix_hint.go_line`を記録しない

## Goの実行設定 {#go-worker-settings}

更新は、作業用コンテナ（Kubernetesでは作業用Pod）で行います。
Goの実行時には、次の環境変数を固定して渡します。

| 環境変数 | 値・扱い |
| --- | --- |
| `GOPROXY` | `https://proxy.golang.org` |
| `GOSUMDB` | `sum.golang.org` |
| `GOPRIVATE`・`GONOPROXY`・`GONOSUMDB`・`GOINSECURE` | 空 |
| `GOFLAGS` | `-mod=mod` |
| `GOTOOLCHAIN` | `local` |
| `GOENV` | `off` |
| `GOWORK` | `off` |
| `CGO_ENABLED` | `0` |
| `GOPATH`・`GOMODCACHE`・`GOCACHE` | `/tmp`配下のメモリ上の一時領域のパス |

コマンドとキャッシュは、次のように扱います。

- `go`コマンドは公式イメージに含まれるものを使い、別のtoolchainを自動取得しない
- Docker・Kubernetesともに、モジュールとビルドのキャッシュを`/tmp`配下のメモリ上の一時領域に置く
- Dockerでは、さらに`/go`をtmpfsで覆う
- すべての対象を1回の`go get <module>@<version> ...`で更新する
- `go mod tidy`は実行しない

直接依存では`go.mod`の`require`を更新し、推移的依存では`// indirect`コメント付きの`require`を追加・更新します。
依存元からの再解決は適用せず、付随して変わったモジュールは[付随するモジュールの更新](#go-collateral-validation)で検査します。

共通の制限は[作業用コンテナの制限](remediation-worker-logic.md#worker-restrictions)、通信先は[依存パッケージの取得](outbound-communication.md#dependency-downloads)を参照してください。

## Goの更新結果の検査 {#go-update-validation}

更新結果は、ファイルの変更、`go.sum`、依存の要求、スキャン結果の条件をすべて満たした場合だけ採用します。
Goでは、一部の更新対象を外して残りだけを更新する分割は行いません。

共通の採用規則と部分PRの適用範囲は、[更新結果の採用](remediation-package-logic.md#update-method-and-partial-pull-requests)を参照してください。

### ファイルと版宣言の変更 {#go-file-changes}

ファイルの差分と採用版を検査し、次の条件を満たす変更だけを採用します。

| 検査対象 | 採用条件 |
| --- | --- |
| 変更するファイル | `go.mod`と`go.sum`に限られること |
| `go.mod`の変更箇所 | `require`と`go`・`toolchain`の行に限られること |
| 既存の`require` | 削除・版下げ・`// indirect`コメントの有無の変更がないこと |
| ほかの指令 | `module`・`replace`・`exclude`・`retract`・`godebug`などの意味が変わらないこと |
| 更新対象の採用版 | すべてが目標版以上となり、各CVEの修正条件を満たすこと |

作業用のGoの版と、稼働中のバイナリをビルドしたGoの版は別に扱います。
宣言の変更を判定するときは、必要な引き上げ先と、超えてはいけない上限を区別します。

| 判定に使う版 | 決め方 |
| --- | --- |
| `go`の行の必要な引き上げ先 | 版が上がった・追加されたモジュールの新しい`go.mod`が要求するGoの最大値 |
| 変更する`go`・`toolchain`の版の上限 | 対象バイナリをビルドしたGoの版の最小値 |

`go`の行を数値として上げる場合は、必要な引き上げ先とちょうど一致する版にします。
宣言の変更に対する扱いは、次のとおりです。

| 変更 | 扱い |
| --- | --- |
| `go`の版が下がる | 拒否する |
| `go`の引き上げ先が必要な引き上げ先より低い | `unexplained_dependency_diff`で拒否する |
| `go`の引き上げ先が必要な引き上げ先より高い | `unexplained_dependency_diff`で拒否する |
| `go`・`toolchain`のうち高い方の版が下がる（`toolchain`の削除を含む） | 拒否する |
| 変更した`go`・`toolchain`の版が対象バイナリのビルド版の最小値を超える | `go_line_raised_too_far`で手動対応にする |
| 対象バイナリのビルド版が不明なまま、行の版が変わる | `go_line_raised_too_far`で手動対応にする |
| 拒否・手動対応の条件に該当しない変更 | ほかの検査も満たせば採用する |

Go 1.26がサポート中の最小の系列である架空の例で、作業用Goと版宣言の上限を比べます。

| 比較する内容 | 版 |
| --- | --- |
| 入力の`go.mod`の`go`の行（`toolchain`なし） | `1.22` |
| 更新対象の新しい`go.mod`が要求するGo | `1.24` |
| 作業用Goの版 | `1.26.10` |
| 稼働中のバイナリをビルドしたGo | `1.22.5` |
| 更新後の`go.mod`の`go`の行 | `1.24` |

作業用Goは要求の`1.24`以上でも、変更後の`go`の行はビルド版の`1.22.5`を超えるため、`go_line_raised_too_far`で手動対応になります。

採用条件とは別に、次の条件をすべて満たす場合は、`go`の引き上げを妨げた理由を案内するための情報を記録します。

- 上がった`go`の行が、版が上がった・追加されたモジュールの宣言するGoの最大値と一致する
- 上がった`go`の版が対象バイナリのビルド版の最小値を超えるか、ビルド版が不明である

必要なGoの最大値を宣言するモジュールが複数ある場合は、パス順で最初のものを選びます。
`packages[].fix_hint.go_line`には、選んだモジュールとその版、必要なGoの版、既知のビルド版、更新で要求した対象の版を記録します。

`toolchain`の行だけが原因の場合は、`fix_hint.go_line`を記録しません。
案内の表示は[修正版に上げられないときの案内](remediation-fix-hints.md#fix-hints)、`go`の行の引き上げに伴うPR本文の記載は[GoのPRとCIでの確認](remediation-pr-results.md#go-pull-requests)を参照してください。

### go.sumの照合と補完 {#go-sum-validation}

`go.sum`のハッシュを`sum.golang.org`の記録と照合し、次の条件で必要な行を補います。

- 追加された行と、版が上がった・追加されたモジュールのzipと`go.mod`のハッシュを照合する
- 版が上がった・追加されたモジュールのハッシュは、既存の行を使う場合も照合する
- 更新した版の行が足りなければ、KestreLynxが`sum.golang.org`の記録から補う
- 元の行の削除やハッシュの変更を拒否する
- 同じモジュール・版・ハッシュの種類で値が食い違う結果を拒否する

補った行のPR本文への記載は、[GoのPRとCIでの確認](remediation-pr-results.md#go-pull-requests)を参照してください。

### 付随するモジュールの更新 {#go-collateral-validation}

対象の更新に伴って版が上がった・追加されたモジュールが、対象の新しい版の要求で説明できることを確かめます。
`proxy.golang.org`で確認した対象の目標版を起点に、その`go.mod`の要求からたどれる必要な追加・版上げだけを認めます。

| 確認する内容 | 扱い |
| --- | --- |
| 対象が目標版を超えて上がり、ほかの要求の経路では説明できない | `unexplained_dependency_diff`で拒否する |
| 要求で説明できた対象の版が目標版を超える | 最新版の`go.mod`の`retract`と照合する |
| 目標版を超えた対象の版が撤回されている | `go_release_retracted`で手動対応にする |
| 版が上がった・追加された依存モジュールの`go.mod`が要求する依存の版 | プロジェクトの更新後の`go.mod`に記録された依存の版が、その要求以上であることを確かめる |
| 新しい版に独自の`go.mod`がなく、proxyが合成したものしかない | 手動対応にする |
| 依存の要求を確かめるために読むモジュールの版が2,000件を超える | `go_dependencies_uncheckable`で手動対応にする |

確認する版は、モジュールパスと版を合わせて1件と数えます。
同じパス・同じ版は重複して数えず、同じモジュールでも版が違えば別に数えます。

### スキャンと利用者のビルド {#go-scan-validation}

更新前後の`go.mod`を、同じTrivy・脆弱性データベース・重大度でスキャンして比較します。
古い版の行を依存として数えないよう、`go.sum`はスキャンに渡しません。

対象のCVEが消え、付随して変わったモジュールも含めてモジュールごとに新しく検出された脆弱性がないことを確かめます。

スキャンするのは`go.mod`に書かれた版で、利用者のビルドはGoの既定の`-mod=readonly`を使うことを前提にします。
`-mod=readonly`では書かれた版だけを使い、必要なモジュールがない場合や版が低い場合はビルドが止まります。

マージ前のCIの実行例とPR本文の記載内容は、[GoのPRとCIでの確認](remediation-pr-results.md#go-pull-requests)を参照してください。
