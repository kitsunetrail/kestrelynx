# 修正計画と修正PRの処理の流れ

KestreLynxが修正計画を作り、更新結果を検査し、修正PRを管理して通知する順序を説明します。
検査で確かめる範囲と、利用者が確認する範囲は[確かめる範囲](#checked-scope)にまとめています。

Kubernetesでは、修正PRを有効にしてnpm・pnpm・pip・uv・Go・Gradleの言語パッケージを更新する場合に、[作業用Pod](remediation-worker-logic.md#kubernetes-work-pods)を使います。

対象ごとの詳しい規則は、次のページで説明します。

| 知りたいこと | ページ |
| --- | --- |
| 配布イメージの候補選定 | [イメージ候補の選定](remediation-image-logic.md#image-selection) |
| Kubernetesのタグ更新PR | [Kubernetesのタグ更新PRの条件](remediation-kubernetes-logic.md) |
| ベースイメージの特定と比較 | [ベースイメージの特定](remediation-base-image-logic.md#base-image-selection) |
| 言語パッケージに共通する選定・採用の規則 | [言語パッケージの候補選定](remediation-package-logic.md#package-selection) |
| npm・pnpm・uv・pipの更新と検査 | [Node.js・Pythonのパッケージ](remediation-node-python-logic.md) |
| 依存元の更新による再解決 | [依存元からの再解決](remediation-reresolution-logic.md#dependent-reresolution) |
| Goの更新と検査 | [Goの候補選定](remediation-go-logic.md#go-package-selection) |
| Mavenの更新と検査 | [Maven](remediation-maven-logic.md) |
| Gradleの更新と検査 | [Gradle](remediation-gradle-logic.md) |
| パッケージマネージャーを実行する環境 | [作業用コンテナの実行](remediation-worker-logic.md#worker-execution) |
| PRの管理と記録 | [PRの管理](remediation-pr-logic.md#pr-management) |

入力の対応範囲は[対応する入力](remediation-reference.md#supported-inputs)、判定に付くコードは[理由コード](remediation-reason-codes.md#reason-codes)を参照してください。

このページで使う用語は[用語](remediation.md#terms)を参照してください。

## 処理の流れ {#processing-flow}

修正計画が有効なサイクルでは、次の順で処理します。

1. 稼働イメージをスキャンし、所見を集める
2. 候補を選び、設定したGitHub上のソースを読み、イメージ候補の比較結果を含む計画を作る
3. 修正PRが有効な場合、言語パッケージを更新し、更新結果を検査する
4. 通常の候補で所見が解消しない対象について、minor・majorが新しいタグを確認する
5. 浮動タグのベースレイヤーが稼働イメージと一致しない対象について、現在のベースと稼働イメージをパッケージの場所とCVEで突き合わせる
6. 計画と、実行した言語パッケージ更新の検査結果を保存する
7. 修正PRが有効な場合、既存PRと照合し、条件を満たす変更のPRを作成・管理する
8. 送信条件に従って結果を通知し、配信後に配信済みの情報を記録する

次の表は、各段階の詳しい説明へのリンクを示します。

| 段階 | 詳しい説明 |
| --- | --- |
| 1. 稼働イメージのスキャン | [スキャンの比較条件](#comparison-conditions) |
| 2. 候補の選定と計画の作成 | [ソースの確認](#source-verification)、[イメージ候補の選定](remediation-image-logic.md#image-selection)、[ベースイメージの特定](remediation-base-image-logic.md#base-image-selection)、[言語パッケージの候補選定](remediation-package-logic.md#package-selection) |
| 3. 言語パッケージの更新と検査 | [更新結果の採用](remediation-package-logic.md#update-method-and-partial-pull-requests) |
| 4. 新しい系列の確認 | [新しい系列の確認](remediation-image-logic.md#newer-series-check) |
| 5. 浮動タグのベースの照合 | [浮動タグの再ビルドの見込み](remediation-base-image-logic.md#rebuild-check) |
| 6. 計画と検査結果の保存 | [記録の保存順序](remediation-pr-logic.md#record-order) |
| 7. PRの作成と管理 | [PRの管理](remediation-pr-logic.md#pr-management) |
| 8. 結果の通知と配信記録 | [スキャン通知の送信条件](notification-conditions.md#notification-conditions)、[記録の保存順序](remediation-pr-logic.md#record-order) |

計画を保存できなかったサイクルは、PR処理へ進みません。
PR処理後に計画を再保存せず、PR処理の結果は通知と継続管理用のPR記録に反映します。

### 計画とPRの実行範囲 {#plan-and-pr-execution}

修正PRの有効・無効によって、計画後に更新を実行するかどうかが変わります。
次の表は、計画だけを使う場合と修正PRも使う場合の違いを示します。

| 実行範囲 | KestreLynxが行う処理 |
| --- | --- |
| 修正計画のみ | 稼働イメージの所見から候補を選び、設定したソースを読み、イメージ候補を比較する |
| 修正PRを有効化 | 計画の処理に加え、言語パッケージの更新と検査を行い、条件を満たす変更のPRを作成・管理する |

PRの対象は、Compose・Kubernetesマニフェスト・Kustomize・Helmのvaluesのタグ更新、Dockerfileのベースイメージ更新、言語パッケージ更新です。
対応する対象と入力の条件は[対応する入力](remediation-reference.md#supported-inputs)を参照してください。

計画のみの場合には、次の制限があります。

- パッケージマネージャーを実行せず、作業用コンテナも作成しない
- GitHubへ書き込まず、計画と配信の記録はローカルに保存する

有効化の設定は[基本設定](configuration.md#remediation-basics)、結果の読み方は[更新結果の解釈](remediation-update-results.md#interpreting-updates)を参照してください。

### 確かめる範囲 {#checked-scope}

KestreLynxの検査は、読み取ったソース、比較するイメージ、更新前後の依存ファイルを対象にします。
検査で分かることと、利用者による確認が必要なことを次の表に示します。

| 検査 | 確かめること | 確かめないこと |
| --- | --- | --- |
| ソースの照合 | 計画の入力や検出したパッケージとの一致 | 稼働イメージが指定したソースからビルドされたという証明 |
| ベースイメージの比較 | 現在のベースと候補のベースの所見 | 変更後のDockerfileからビルドする完成イメージ |
| 依存ファイルの比較 | 更新前後の依存ファイルの所見 | 実際の依存のインストール、アプリケーションの動作、配置後の稼働コンテナ |

修正PRを有効にしても、KestreLynxはPRをマージせず、アプリケーションの完成イメージをビルド・配置しません。
変更内容の確認、マージ、ビルド、動作確認、配置は利用者が行います。

### ソースの確認 {#source-verification}

ソースの確認では、修正先のファイルが計画の入力として使えるか、PR作成時にも同じ入力を使えるかを確かめます。

ソースを読み取るときとPRを作るときには、次を確認します。

- 設定したブランチが指すコミットを確定し、そのコミットからソースを読む
- PR作成時にベースブランチが進んでいれば、更新に使ったファイルや確認対象の設定ファイルの状態を再確認する
- 言語パッケージとDockerfileの更新では、計画時に確かめたファイルの変更を検出すると、PRの作成を保留する
- Compose・Kubernetesマニフェスト・Kustomize・Helmのvaluesのタグ更新では、ファイルのイメージ名が稼働イメージ名と一致しないと手動対応にする

保留した更新については、PR用のコミットやブランチも作成しません。
言語パッケージとDockerfileの変更は、同じリポジトリ・ベースブランチの中で、次の範囲ごとにPRへまとめます。

| 更新の種類 | 同じPRにまとめる範囲 |
| --- | --- |
| 言語パッケージ | 同じ依存ディレクトリで同じパッケージマネージャーが一緒に更新するパッケージとファイル |
| Dockerfile | 同じDockerfileの同じ`FROM`を変更する対象 |

入力の変更で保留になる例として、同じ依存ディレクトリのnpm更新では、同じPRに含めるすべてのパッケージの変更が止まります。
別の依存ディレクトリの更新は、使う入力に変更がなく、ほかの条件も満たせば進められます。

別のPRでも、同じ変更済みファイルを入力に使う場合は保留します。

言語パッケージでは、次の情報を照合します。

- 稼働イメージで検出したパッケージの名前・版と、依存ファイルの記録
- 更新時に読み直したファイルの内容・版宣言と、計画時に記録した内容

グローバルにインストールされたnpmパッケージは、依存ファイルと照合せず手動対応にします。
イメージ内のパスが`<prefix>/lib/node_modules`配下で、最初の`node_modules`の親が`lib`なら、この扱いにします。

公式nodeイメージのnpm・corepackに含まれるパッケージも、この扱いに含めます。

たとえば、コンテナ名が`example-api`なら、対応付けには`container/example-api`を使います。

`container/<名前>`の対応付けでは、次の範囲を確かめます。

| 確認する関係 | 扱い |
| --- | --- |
| スキャンしたイメージと稼働イメージ | スキャンしたイメージのdigestと稼働イメージのIDが一致することを確認 |
| Dockerfileと稼働イメージ | ベースレイヤーを照合 |
| 依存ファイルと稼働イメージ | 検出したパッケージの名前・版を照合 |
| コンテナと指定したリポジトリ | 設定の対応付けを信頼し、そのリポジトリから作られたことは未確認 |

ソースの対応付けやパッケージ名・版の一致は、ソースからビルドされたことの証明にはなりません（[確かめる範囲](#checked-scope)）。

ワークロードキーが`container/<名前>`のPR（`docker run`で起動したコンテナを対象にするPR）の本文には、修正先との対応が設定に基づき、KestreLynxでは確かめていないことを注記します。
本文の長さの上限により注記を残せない場合は、PRを作成しません。

対応付けの設定仕様は[ソースの対応付け](configuration.md#remediation-mappings)を参照してください。

## 比較と採用の条件 {#comparison-and-adoption}

比較では所見の解消・残存・新規発生を調べ、採用条件を満たす更新を提案します。

### スキャンの比較条件 {#comparison-conditions}

更新前と更新後を比べるスキャンには、同じスキャナ、同じ内容の脆弱性データベース、同じ深刻度の範囲とスキャン設定を使います。
対象ごとに比較するイメージやファイルは[対象別の検証範囲](#verification-scope)を参照してください。

所見には、脆弱性のIDに加えてパッケージの名前・版・検出場所などの情報があります。
イメージの比較では、パッケージの種類（Alpine・npmなど）、OSパッケージか言語パッケージかの分類、名前を使って、同じ脆弱性を別に扱うか決めます。

同じCVEが複数のパッケージや場所で見つかった場合は、次のように数えます。

| 検出の違い | イメージの比較での扱い |
| --- | --- |
| パッケージの種類・分類・名前のいずれかが違う | 別々に解消・残存を判定 |
| 種類・分類・名前が同じで、版や場所が違う | 出現箇所として区別し、同じCVEの解消・残存はまとめて1件と判定 |
| 同じパッケージのいずれかの出現箇所にCVEが残る | 解消とは数えず、残存と判定 |

比較条件をそろえるために、次を確認します。

- データベースの同一性などの条件を確認できない稼働イメージのスキャンは再利用せず、上限の範囲内で再スキャンする
- 比較用のスキャン後にもデータベースを照合し、条件が変わっていれば比較を成立させない
- イメージの比較では、更新前・更新後のそれぞれで、スキャン対象として指定したdigestと実際にスキャンしたイメージが一致することを確認する
- 更新前と更新後のイメージで、OS・CPUアーキテクチャが一致することを確認する

所見が消えた理由を判断するには、パッケージの解析結果も必要です。
次の状態では、比較による解消を判断しません。

| スキャン結果の状態 | 判断できない理由 |
| --- | --- |
| パッケージ一覧がない | 何を解析したかを確認できない |
| パッケージ一覧が途中で省略されている | 解析したパッケージの全体を確認できない |
| 対象のパッケージ種別が解析されていない | 一覧があっても、対象の種類について解析結果がない |

パッケージを解析して脆弱性が検出されなくなった場合と、パッケージの種類自体を解析できなかった場合は区別します。
対象の種類の解析結果がなければ、所見が消えていても解消とは判断しません。

依存ファイルの比較には検査対象のファイルだけを渡し、リポジトリ独自のTrivy設定・ignoreファイル・VEX文書は読み取りません。
設定した深刻度の範囲外は、解消や新規発生の評価対象に含めません。

### 対象別の検証範囲 {#verification-scope}

対象によって、比較するものと更新を採用する条件が異なります。
修正を狙う対象所見は、スキャンの状態が`fixed`で修正版の情報がある所見から選びます。

対象に選ばなかった所見と更新で新しく検出された所見は、対象所見の解消・残存とは分けて扱います（[比較結果の解消](remediation-pr-results.md#verification-results)）。
次の表では、修正を狙う所見と、新しい所見を調べる範囲を分けています。

| 対象 | 比較するもの | 修正を狙う所見 | 新しい所見を調べる範囲 |
| --- | --- | --- | --- |
| 配布イメージ | 稼働イメージと候補イメージ | 稼働イメージから選んだ対象所見 | 設定した深刻度の範囲内のイメージ全体 |
| ベースイメージ | 照合できた現在のベースと候補のベース | ベースに属すると確認できた対象所見 | 設定した深刻度の範囲内のベース全体 |
| 言語パッケージ | 更新前後の依存ファイル | 採用するパッケージの対象所見 | 設定した深刻度の範囲内で、対象外のパッケージも含む依存ファイル全体 |

更新の種類に応じて、次の採用条件を適用します。

- 配布イメージとベースイメージは、対象所見に解析不能がなく、1件以上解消すれば、一部が残っていても改善として提案する
- 言語パッケージは、採用するパッケージの対象所見を更新前に確認でき、更新後のどの出現箇所にも残らないことを求める
- いずれの更新も、表の「新しい所見を調べる範囲」に新しい所見がないことを求める

採用の判断には、次の規則も適用します。

- 言語パッケージは、更新後のファイルに記録された対象パッケージの版がスキャンでも解析されていることを確認する
- 更新前になく更新後に検出された所見は、解消件数と相殺しない
- 更新で新しく検出された所見が、CISAの悪用確認済み脆弱性の一覧（KEV）に載っていれば、区別して記録する
- 同じDockerfileの変更を共有する複数の稼働イメージは、まとめて採用できることを確認する

完成イメージやアプリケーションの検証との違いは[確かめる範囲](#checked-scope)、比較結果の読み方は[比較結果の解消](remediation-pr-results.md#verification-results)を参照してください。
