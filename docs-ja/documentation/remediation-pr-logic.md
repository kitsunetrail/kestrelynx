# 修正PRの管理と記録

このページでは、修正PRの重複作成を防ぐ仕組み、閉じたPRの扱い、古いPRの置き換えを説明します。
記録ファイルの内容と復旧、GitHubへの書き込みを停止する条件も説明します。

このページで使う用語は[用語](remediation.md#terms)を参照してください。

## PRの管理 {#pr-management}

KestreLynxは、PR処理の記録とGitHub上の状態を照合して、PRの新規作成や置き換えを判断します。
次のサイクルでの扱いは、PRの状態によって異なります。

| PRの状態 | 次のサイクルでの扱い | 詳しい節 |
| --- | --- | --- |
| 開いているPR | 同じ更新なら既存PRに結び付け、重複作成を抑止する | [既存PRとの照合](#existing-pr-matching) |
| マージ済みのPR | 同じ更新の再作成を抑止するが、稼働環境への配置済みとは判断しない | [閉じたPRの扱い](#closed-prs) |
| 未マージで閉じたPR | ブランチ削除後も同じ更新の再作成を抑止する | [閉じたPRの扱い](#closed-prs) |
| 利用者が変更したPR | 変更を検出したPRは重複作成の抑止に使い、自動置き換えには使わない | [既存PRとの照合](#existing-pr-matching)・[古いPRの置き換え](#pr-replacement) |
| 識別マーカーだけから復旧したPR | 重複作成の抑止に使い、再実行の省略や自動置き換えの根拠にはしない | [記録の復旧](#record-recovery) |

### 既存PRとの照合 {#existing-pr-matching}

既存PRとの照合は、同じ更新のPRを重複して作らないための処理です。
開いているPR、マージ済みのPR、閉じたPRの記録を使います。

依存元からの再解決では、直接依存も更新して、間接依存の版を選び直します。
処理の詳細は[依存元からの再解決](remediation-reresolution-logic.md#dependent-reresolution)を参照してください。

同じ更新かどうかは、更新の種類、変更先、更新内容で判断します。

| 区分 | 照合する情報 |
| --- | --- |
| 更新の種類 | Compose・Dockerfile・言語パッケージ・Kubernetesマニフェスト・Kustomize・Helmのvalues |
| 変更先 | リポジトリ、ベースブランチ、ファイル、編集箇所 |
| イメージの更新内容 | 更新前のイメージ名、更新先のタグ・digest |
| Kubernetesマニフェスト・Kustomize・Helmのvaluesの更新内容 | タグの変更で影響を受けるコンテナ |
| 言語パッケージの更新内容 | パッケージと依存ファイル内の位置、採用版、依存ファイルの版指定の変更 |
| 依存元からの再解決を伴う変更 | あわせて更新した直接依存の名前・変更前後の版、対象パッケージが経由した直接依存の情報 |

依存元からの再解決を伴う更新は、採用版が同じでも通常の更新とは別に照合します。

言語パッケージ更新の再実行を省略するかは、変更先・パッケージマネージャーと、入力の一致で判断します。
省略に使うのは、KestreLynxがPR作成後に保存した記録か、更新を再実行して入力を検証した記録です。

入力ファイルの内容や対象パッケージの版などが同じで、条件を満たす記録があれば、更新を再実行せずに既存PRへ結び付けます。
識別マーカーだけから復旧した記録との違いは、[記録の復旧](#record-recovery)を参照してください。

ベースコミットと変更前後のファイル内容は、PR作成時の入力として別に記録します。
ベースコミットの一致は、重複作成の抑止にも、言語パッケージ更新の再実行の省略にも必要ありません。

言語パッケージ更新では、同じlockfileに開いているPRがない対象を優先します。
新しい更新は新しいPRとして作成し、既存ブランチの上書きやforce更新は行いません。

同じlockfileにKestreLynxが管理するPRが開いている場合は、古いPRと新しい更新が解消する所見を比べます。
古いPRが解消するとしていた所見を新しい更新ですべて解消できなければ、新規PRを保留（`deferred`）にします。

修正内容を引き継ぐ条件は、[古いPRの置き換え](#pr-replacement)を参照してください。

利用者による変更は、GitHub上のPRと作成時の記録を比べて検出します。
通常の照合では、次の値を確認します。

| 検出する変更 | 作成時の記録と比較する値 |
| --- | --- |
| PRのブランチへのコミット追加やコミットの書き換え | PRの先頭コミットのSHA |
| PRのベースブランチの変更 | ベースブランチ名 |
| PRの取り込み先リポジトリの変更 | 取り込み先リポジトリのID |

PR本文には、KestreLynxが作ったPRであることを示す情報をHTMLコメントに入れています。
この情報を識別マーカーと呼びます。

通常の照合では、PR本文だけの編集は利用者による変更の判定対象にしません。
作成結果が未確定とは、GitHubへのPR作成要求の結果を確認できず、PRが作られたか判断できない場合などを指します。

作成結果が未確定のPRを確認するときは、識別マーカーの欠落・不一致や、同じブランチに複数のPRがある場合も変更として扱います。

KestreLynxが作成したブランチに、KestreLynxが作成したと確認できない別のPRを見つけた場合も、利用者による変更として扱います。
記録の復旧に使う識別マーカーの検証は、[記録の復旧](#record-recovery)を参照してください。

変更を検出したPRや識別マーカーだけから復旧したPRは、同じlockfileへの別の更新を保留する根拠には使いません。
ただし、同じ更新の重複作成を防ぐ記録としては使います。

### 閉じたPRの扱い {#closed-prs}

未マージで閉じたPRの記録は、同じ更新の再作成を抑止するために使います。
ブランチを削除した後も抑止を維持します。

再作成の抑止には、次の方針を適用します。

- ベースブランチが進んでも、更新内容が同じなら再作成を抑止する
- マージ済みのPRも、同じ更新の重複作成を抑止する
- PRと再作成抑止の記録には、有効期限を設けない

GitHub上で再開されたPRは、次の照合で開いているPRとして記録します。
マージ済みという状態から、変更が稼働環境へ配置されたとは判断しません。

### 古いPRの置き換え {#pr-replacement}

置き換えは、新しいPRが古いPRの修正内容を引き継ぐ場合に、古いPRを閉じる処理です。
PR数の上限を空けるためだけに、古いPRを閉じることはありません。

どの更新にも、次の共通の条件を適用します。

- 変更先のリポジトリ、ベースブランチ、ファイル、編集箇所が一致する
- 新旧のPRで、タグの変更で影響を受けるコンテナが一致する
- 古いPRが解消するとしていた所見を、新しいPRがすべて解消する
- 新旧のPRが開いている
- 新旧のPRに、利用者による変更を検出したPRや、識別マーカーだけから復旧したPRを使わない

新旧のPRを作成時の記録と比べる項目は、[既存PRとの照合](#existing-pr-matching)にある利用者による変更の検出条件と同じです。
ベースブランチにコミットが追加されただけでは、作成時との不一致にはなりません。

更新の種類による条件は、次のとおりです。

| 更新の種類 | 種類ごとの条件 |
| --- | --- |
| イメージ更新 | 同じイメージリポジトリ・タグ系列の、より新しいパッチであること |
| ベースイメージ更新 | イメージ更新の条件に加え、古いPRが対象にした各稼働イメージの修正を引き継ぐこと |
| 言語パッケージ更新 | 共通の条件を満たすこと |

イメージ更新では、置き換え時にも候補タグが比較時と同じ内容を指すことを確認します。

条件を満たしたPRは、次の順序で置き換えます。

1. 新旧のPRを再確認し、古いPRに置き換え先を知らせるコメントを付ける
2. 新旧のPRを再確認し、古いPRを閉じる

各書き込み前の再確認で条件が崩れた場合は、置き換えを中止します。
一度でも利用者による変更を検出したPRは、元の状態に戻っても自動置き換えに使いません。

## 記録 {#pr-records}

修正計画、通知の配信状況、PR処理の記録は、用途ごとに分けて保存します。

### 保存ファイル {#stored-records}

記録ファイルとツールのキャッシュは、`remediation.storage_dir`の下に保存します。
保存する内容は、次のとおりです。

| ファイル・ディレクトリ | 内容 |
| --- | --- |
| `plan.json` | 最新の計画、ソースの場所、比較に使ったスキャン、実行した依存更新の検査結果（PR処理後の結果は含まない） |
| `delivered.json` | 配信した計画と、Slack・メールに表示した内容をそれぞれ識別する情報 |
| `prs.json` | PRの識別情報、状態、作成試行、再作成の抑止、GitHub操作の記録 |
| `tools` | 取得・照合したnpm・pnpm・uvのキャッシュ |

依存元からの再解決について、`prs.json`には次の記録も保存します。

| 記録する内容 | 次のサイクルでの扱い |
| --- | --- |
| 公開後の待機を終える時刻 | 記録された時刻まで再試行を待つ |
| 公開後の待機や上限到達など、理由の種類ごとの連続保留数 | 再解決の再試行を続けるか、停止するかを判断する |
| 再解決を停止した入力と理由 | 同じ入力では依存元からの再解決を再試行しない |

待機・保留・停止の記録は、リポジトリ・ベースブランチ・依存ファイルごとに分けます。
同じ入力かどうかは、ファイルの内容や対象パッケージの稼働版・更新目標などで判断します。

入力が変われば、以前の入力に対する停止記録は適用しません。
再試行や停止の詳しい条件は、[公開後の待機と再試行](remediation-reresolution-logic.md#dependent-reresolution-waits)を参照してください。

最新の修正計画のPR処理結果は通知で、継続して管理する記録は`prs.json`で確認できます。

保存先の設定は[基本設定](configuration.md#remediation-basics)を参照してください。

### 記録の保存順序 {#record-order}

計画と依存更新の検査結果を保存してから、PRの作成や既存PRとの照合を行います。
計画を保存できなかったサイクルは、PR処理へ進みません。

保存する時点は、次のとおりです。

| 保存する時点 | 記録先と保存する情報 |
| --- | --- |
| 依存更新の処理後 | `prs.json`の待機・保留・停止の記録 |
| PR処理の前 | `plan.json`の計画と依存更新の検査結果 |
| PRの処理・照合時 | `prs.json`のPRの状態など |
| GitHubへの各書き込みの前 | `prs.json`の操作予定 |
| GitHubへの各書き込みの後 | `prs.json`の操作結果 |
| 通知の配信後 | `delivered.json`の配信済みの情報と、`prs.json`の操作履歴の配信状況 |
| ツールの取得時など | `tools`のキャッシュ |

PR操作イベントの読み方は[PR操作イベントのフィールド](webhook-remediation-pr-reference.md#remediation-operation-fields)を参照してください。

### 記録の復旧 {#record-recovery}

記録の復旧は、`prs.json`がないときに、GitHub上のPRからPR処理の記録を作り直す処理です。
書き込み前に、設定されたリポジトリの開いているPRと閉じたPRを調べます。

同じリポジトリの`kestrelynx/`ブランチを対象に、PR本文の識別マーカーを読み取ります。
マーカーの識別情報を再計算し、リポジトリとブランチの対応も確認します。

Kubernetesマニフェスト・Kustomize・HelmのvaluesのPRは、次の情報で区別します。

| PRの種類 | ブランチ名の先頭 | 識別マーカーの種別 |
| --- | --- | --- |
| Kubernetesマニフェストのタグ更新 | `kestrelynx/kubernetes/` | `kubernetes` |
| Kustomizeのタグ更新 | `kestrelynx/kustomize/` | `kustomize` |
| Helmのvaluesのタグ更新 | `kestrelynx/helm/` | `helm_values` |

PRの種類をサポートしていない版のKestreLynxでは、その種類の既存PRを認識できません。

書き込みを始める前の確認には、次の方針を適用します。

- `prs.json`がない状態からの復旧では、すべての対象リポジトリを確認できるまでGitHubへ書き込まない
- 新たに設定されたリポジトリも、最初の書き込み前に既存PRを確認する
- 識別マーカーだけから復旧した記録は重複作成の抑止に使い、自動置き換えには使わない

識別マーカーだけでは、言語パッケージ更新の実行と検査が済んだ証拠にはしません。
再実行の省略には、KestreLynxが作成した記録、または更新を再実行して入力を検証した記録を使います。

## 書き込みの停止 {#write-stops}

記録やGitHub上の状態を確認できない場合は、問題の範囲に応じてGitHubへの書き込みを止めます。
破損した計画・PRの記録や、サポートしていないバージョンの記録を、空の記録に置き換えて処理を続けることはありません。

停止条件と範囲は、次のとおりです。

| 停止条件 | 停止する範囲・扱い |
| --- | --- |
| 計画の保存失敗 | そのサイクルのPR処理全体 |
| PR記録の読み取り・保存失敗、記録のロック取得失敗 | そのサイクルの全リポジトリへの書き込み |
| 既存PR一覧・記録中のPR・未確定の操作結果を読み取れない | 影響するリポジトリ全体への書き込み |
| PR作成用ブランチが記録と異なるコミットを指す、同じブランチに複数のPRがある | 同じリポジトリ・ベースブランチ・更新の種類・ファイル・編集箇所への新規作成と置き換え |
| GitHubへの書き込み結果が不明 | そのサイクルの全リポジトリへの以後の書き込み |
| リポジトリ名や識別情報が設定・記録と不一致 | 該当リポジトリへの書き込み |
| 操作履歴に新しいイベントを記録する余裕がない | そのサイクルの全リポジトリでの新しいGitHub操作 |
| 要求数や処理時間などの上限に到達 | 以後の対象処理を保留 |

変更先だけの停止は、ファイル全体の停止ではありません。
たとえば、PR作成用ブランチが記録と異なるコミットを指す場合でも、別の変更先や別のリポジトリは、ほかの停止条件がなければ処理を続けられます。

`prs.json`がない状態で復旧を完了できない場合は、[記録の復旧](#record-recovery)のとおり、全対象リポジトリへの書き込みを止めます。
リポジトリ名や識別情報が一致しなくても、移転先などへ自動で書き込み先を切り替えません。

結果不明の書き込みは、次のサイクルに読み取りで結果を確認します。
確認せずに同じ書き込みを再送することはありません。

操作履歴は、GitHub操作の結果を後から確認し、操作イベントを通知するために保持します。
新しい操作を始める前に、操作イベント1,000件の保持上限内に必要な件数を追加できるか確認します。

整理で削除するのは、配信済みで、未確定の操作や処理中の置き換えに必要でないイベントだけです。
たとえば、未配信のイベントだけで1,000件に達すると、削除できるイベントがないため新しい操作を開始できません。

停止の報告は[書き込み停止のフィールド](webhook-remediation-pr-reference.md#remediation-problem-fields)、理由コードは[PR処理の理由](remediation-update-reason-codes.md#pr-reasons)と[保存処理の理由](remediation-update-reason-codes.md#storage-reasons)を参照してください。
上限の設定は[処理の上限](configuration.md#remediation-limits)、確認と対処は[記録を照合できない場合の確認](remediation-troubleshooting.md#check-record-failure)を参照してください。
