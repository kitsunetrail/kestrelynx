# 更新結果と再取得・再ビルドの案内の読み方

このページでは、更新目標と採用版、部分PR、依存元からの再解決の結果を読み分けます。
「再pull」「再ビルド」の案内で分かることと、まだ確認できていないことも説明します。

通知の各行の意味は[Slackの修正計画](remediation-results.md#reading-results-in-slack-and-webhooks)を参照してください。
このページで使う用語は[用語](remediation.md#terms)を参照してください。

## 更新結果の解釈 {#interpreting-updates}

更新結果は、提案した版、実際に依存ファイルで確認した版、PRに含められなかった対象を区別して読みます。

### 更新目標と採用版 {#target-and-adopted-version}

Slackのパッケージ更新で、`→`の右に表示する版は処理段階によって異なります。

| 表示と処理段階 | `→`の右に出る版 |
| --- | --- |
| 更新候補：依存更新をまだ実行していない計画 | 更新目標 |
| 更新候補：依存更新の検査を通った候補 | 採用版 |
| 更新：PRが提案する変更 | PRに記録された採用版 |

「更新候補」という見出しだけでは、更新目標と採用版を区別できません。
Webhookまたは`plan.json`で、該当する`language_items[]`の`category`と`packages[]`を確認します。

| `category` | 矢印の右側を確認するフィールド |
| --- | --- |
| `dependency_update_candidate` | `packages[].selection_lower_bound` |
| `pr_candidate` | `packages[].adopted_version` |

詳細データの確認先は[詳細な結果の確認先](remediation-results.md#detailed-results)、フィールドの仕様は[言語パッケージのフィールド](webhook-remediation-language-reference.md#remediation-language-fields)を参照してください。

更新目標は、パッケージマネージャーが実際に選んだ版とは限りません。
計画だけの場合は依存更新を実行しないため、更新目標を検証済みの採用版として読まないでください。

更新後の依存ファイルに同じパッケージの複数の版が残る場合は、最小の版を採用版として表示します。
最小の採用版だけから検査内容のすべては分からないため、[比較結果の解消](remediation-pr-results.md#verification-results)も確認してください。

下限の求め方は[修正版の下限](remediation-package-logic.md#fix-lower-bound)、実行範囲は[計画とPRの実行範囲](remediation-logic.md#plan-and-pr-execution)を参照してください。

### 部分PR {#partial-pull-requests}

部分PRは、計画したパッケージのうち、検査を通った更新だけを含むPRです。
npm・pnpm・uv・pip・Maven・Gradleでは、部分PRになる場合があります。

PRに含まれる更新と残る対応は、次のように区別します。

| 結果 | 読み方 |
| --- | --- |
| PRの「更新」にあるパッケージ | 表示されたPRに含まれる変更 |
| 「要判断」「ため除外」と表示されたパッケージ | PRで行う更新から外れ、別の対応が必要な対象 |
| 目標の版に上げられず、元の版のままと表示されたパッケージ | 修正版に届かなかった対象 |
| PRがオープン中で、除外情報も表示される結果 | 既存PRが提案する更新にも対応が残るパッケージがある状態 |

修正版に届かなかった結果は、上がらない原因まで特定できたとは限りません。
「除外」は、パッケージをイメージから削除したという意味ではありません。

また、項目全体がPR候補でも、すべてのパッケージが更新されたとは限りません。
Goの更新は部分PRに分けません。

pipの固定版更新では、依存元が更新を妨げているパッケージ（`dependents_hold_back`）を除き、残りを更新し直す場合があります。
残りの更新が検査を通れば、残りだけのPRを作ります。

成立条件は[部分PRの成立条件](remediation-package-logic.md#partial-pr-selection)・[Mavenで対象を外して残りを更新する条件](remediation-maven-logic.md#maven-update-exclusions)・[Gradleで対象を外して残りを更新する条件](remediation-gradle-logic.md#gradle-update-exclusions)を参照してください。
PRの確認は[修正PRの内容とマージ前の確認](remediation-pr-results.md)、残る対象の確認は[更新を実行できない場合の確認](remediation-troubleshooting.md#check-update-failure)を参照してください。

### 依存元からの再解決の結果 {#dependent-reresolution-results}

依存元からの再解決は、あるパッケージを修正版に上げるために、それを古い版に留めている依存元もあわせて更新する処理です。
依存元は、プロジェクトが指定している範囲内で更新します。

次は、`package.json`が`mkdirp ^0.5.1`を指定する場合の、更新前後の依存関係です。
`mkdirp`経由の`minimist`は依存元の更新が必要ですが、`rc`経由では通常の更新で修正版を選べます。

更新前の依存関係です。

```text
project
|-- mkdirp 0.5.1                 # minimist 0.0.8ちょうどを要求
|   `-- minimist 0.0.8           # 依存元の指定で更新できない
`-- rc 1.2.8                     # minimist ^1.2.0を要求
    `-- minimist 1.2.0           # 通常の更新で修正版を選べる
```

通常の更新だけでは、`mkdirp`経由の`minimist`を修正版に上げられません。
更新後の依存関係は、次のとおりです。

```text
project
|-- mkdirp 0.5.6                 # minimist ^1.2.6を要求
|   `-- minimist 1.2.x           # 修正版を採用
`-- rc 1.2.8                     # 依存元の版は変更しない
    `-- minimist 1.2.x           # 修正版を採用
```

`mkdirp`を`0.5.6`に上げると、`minimist`も修正版を選べるようになります。
プロジェクトの`mkdirp ^0.5.1`という指定は変えません。

`minimist 1.2.8`を採用する場合、Slackには次のように表示します。

```text
minimist 0.0.8 → 1.2.8（mkdirp 0.5.1 → 0.5.6 も更新）
```

再解決の結果は、次の表示で読み分けます。

| 表示 | 意味 |
| --- | --- |
| `mkdirp 0.5.1 → 0.5.6 も更新` | `minimist`を直すために依存元の`mkdirp`も更新した |
| `starlette 0.32.0.post1 を修正版の 1.3.1 に上げられない（依存元の fastapi 0.108.0 が starlette の版を制限）` | 依存元の指定が修正版への更新を妨げている |
| `今回の再解決では修正版に届かなかった` | 依存元を選び直しても、修正計画で行った再解決では修正版に上がらなかった |
| `更新も必要だが、…ため採用しない` | 検査に通らないなどの理由で更新を採用しなかった |
| `…の更新を試していない` | 扱える入力や処理上限などの理由で更新を見送った |
| `公開から72時間経っていないため … 以降に再試行する` | 表示された日時より前は更新を保留した |

依存元の制約を示す行は、プロジェクトの指定範囲内で依存元を更新しても修正版に届かなかった結果（`not_fixed`）で表示します。
依存元が複数なら名前と版を列挙し、対象パッケージへの依存元の指定を記録できていなければ「今回の再解決では修正版に届かなかった」と表示します。

uvでは、修正版を指定した再解決が成立しなかった場合（`no_resolution`）にも、依存元の制約を示す行を表示します。
公開後の待機では、表示日時以降のサイクルでKestreLynxが再試行の対象に戻します。

再解決を採用しなくても、検査を通る通常更新はPRに含めることがあります。
「修正版に届かなかった」は、ほかの方法でも直せないという意味ではありません。

PR本文の「あわせて更新したパッケージ」には、版が変わった直接依存を載せます。
この例では、変更前後の版と、更新を妨げていた指定を次のように表示します。

> - `mkdirp`: `0.5.1` から `0.5.6` へ（`minimist` `0.0.8` を要求していた）

再解決に伴って別のパッケージの版が変わっても、依存関係の同じ位置に同じ脆弱性が残る場合があります。
条件を満たす場合は「持ち越し」として扱い、その脆弱性はこの更新では直りません。

次は、`A`が使う`Y`の版が変わっても、同じ`CVE-2`が残る架空の例です。

| 段階 | 依存関係 | 残る脆弱性 |
| --- | --- | --- |
| 更新前 | `project → A 1.0 → Y 1.0` | `Y`の`CVE-2` |
| 更新後 | `project → A 2.0 → Y 1.1` | `Y`の`CVE-2` |

`A`が使う`Y`という位置に同じ脆弱性が残っており、別のパッケージに新しい脆弱性が生じたという意味ではありません。
PR本文には、持ち越した脆弱性の件数と、CVE ID・パッケージ名・変更前後の版の例を表示します。

持ち越しとして扱える条件は[脆弱性の持ち越し](remediation-reresolution-logic.md#dependent-reresolution-carried-findings)を参照してください。

Webhookを受け取っている場合は、次のフィールドで詳細を確認できます。

| 確認したい内容 | `language_items[]`からの確認先 |
| --- | --- |
| あわせて更新した依存元 | `packages[].through` |
| 採用・見送りなどの結果と理由 | `update.chain.outcome`・`update.chain.reason`・`update.chain.detail` |
| 持ち越した脆弱性 | `source_check.chain_carried` |
| 再試行可能な日時 | `retry_after` |

npm・pnpm・uvでの処理は[依存元からの再解決](remediation-reresolution-logic.md#dependent-reresolution)を参照してください。
そのほかのフィールドは、[依存元からの再解決の結果](webhook-remediation-update-reference.md#language-chain-fields)と[再解決のスキャン比較](webhook-remediation-check-reference.md#language-chain-scan-fields)を参照してください。

### 再取得の案内 {#repull-guidance}

再取得の案内は、稼働イメージと、同じタグが現在レジストリで指す内容を比較して改善を確認した結果です。
Slackでは「再pull」と表示します。

タグの文字列を変更しないため、この案内だけでCompose・Kubernetesマニフェスト・Kustomize・Helmのvaluesのタグ更新PRは作りません。
`所見4件中3件が解消`なら、比較対象の4件のうち3件が候補では検出されなくなったことを示します。

稼働中のコンテナが候補の内容へ置き換わったことは示しません。
Kubernetesでの再取得方法は通知の「pullポリシー」と[Kubernetesのイメージ名と再取得](remediation-kubernetes-logic.md#kubernetes-image-references)を参照してください。

### 再ビルドの案内 {#rebuild-guidance}

再ビルドの案内は、再ビルドによる変化の見込みと、再ビルドを勧める場合の手順を示します。
案内が出る理由は、次のように分かれます。

| 理由 | どんな場合か |
| --- | --- |
| pipの依存範囲 | 現在の依存範囲が修正版を許す場合 |
| Goの標準ライブラリ | 新しいGoでビルドし直す必要がある場合 |
| マージ済みのベース更新が未反映 | 稼働イメージがPR作成時のままの場合 |
| 浮動タグのベースが変化 | 現在のベースのレイヤーが稼働イメージの先頭と一致しない場合 |

pipの`再ビルドで … 以上が入る見込み`は、依存範囲から修正版が入ると見込んだ結果です。
Goの`stdlib`の所見はPRを作らず、修正計画の別項目で、全CVEを直せるGoの版以上での再ビルドを案内します。

マージ済みのベース更新が未反映の場合は、次の案内を表示します。

```text
再ビルド: PR #…（ベースイメージ … … → …）はマージ済みだが、稼働中のイメージはまだ … から作られている
```

マージ後のDockerfileで作ったイメージをデプロイすると、ベース更新が反映されます。

浮動タグの案内にある`稼働中のイメージの先頭のレイヤーが現在の … と一致しない`は、現在のベースと稼働イメージの不一致を示します。
KestreLynxは現在のベースをレジストリからスキャンし、稼働イメージの所見とパッケージの場所・CVEで突き合わせます。

イメージはビルドしません。
Slackとメールでは、突き合わせの結果に応じて次のように表示します。

```text
現在のベースとの突き合わせ
├─ すべての所見を判定できた（checked）
│  ├─ 消える見込みの所見がある
│  │  └─ 再ビルド: 手順を表示し、要約の「再ビルド」に数える
│  └─ 消える見込みの所見がない
│     └─ 何も出さない
├─ 比較したが一部の所見を判定できなかった（partial）
│  └─ 再ビルド: 手順を表示し、要約の「再ビルド」に数える
│     「(一部の所見は確認できなかった)」を付ける
└─ イメージを比較できなかった（not_checked）
   └─ 再ビルド: 手順を表示し、要約の「再ビルド」に数える
      「(消える所見は確認できなかった)」を付ける
```

「消える見込みの所見がある」は、パッケージまたは実行環境の見込みに、消える所見がある場合です。
行を出さない場合は要約の「再ビルド」にも数えませんが、Webhookの`rebuild_check`で結果を確認できます。

フィールドの仕様は[ベースイメージのフィールド](webhook-remediation-dockerfile-reference.md#remediation-dockerfile-fields)を参照してください。

再ビルドの手順を表示する場合、Dockerfileを見つけた方法によって案内するコマンドが異なります。

| Dockerfileを見つけた方法 | 案内する操作 |
| --- | --- |
| Composeの`build` | `docker compose build --pull`で現在のベースを再取得して再ビルド |
| 設定の対応付けのみ | `docker build --pull`などで現在のベースを再取得し、再ビルド・再デプロイ |

設定の対応付けによる案内は、CIなどでビルドしたイメージにも適用します。
`docker build --pull`は、ベースを再取得するためのオプションを示しており、そのまま実行できる完全なコマンドではありません。

使用するDockerfile、ビルドコンテキスト、作成するイメージ名は、通知の案内だけでは確定できません。
次は、パッケージ名と版を使った架空の表示例です。

```text
再ビルド: 稼働中のイメージの先頭のレイヤーが現在の node:24-alpine と一致しない。ベースを取り直して再ビルドし(`docker build --pull` など)、デプロイし直す
  • 現在のベースの版を引き継げば消える見込み: package-a 1.0.0 → 1.0.1
  • 現在のベースにも残る: package-b 2.0.0
  • 現在のベースで新しく出る: package-c 3.0.0
```

表示行とWebhookのフィールドの関係は、次のとおりです。
パッケージの詳細は「再ビルド」の行の下に表示します。

| 表示・見込み | フィールド | 意味 |
| --- | --- | --- |
| 現在のベースの版を引き継げば消える見込み | `rebuild_check.gone` | ベースの同じ場所に別の版があり、対象のCVEがない結果 |
| 現在のベースにも残る | `rebuild_check.remaining` | ベースの同じ場所にも対象のCVEがある結果 |
| 現在のベースにない | `rebuild_check.not_in_base` | 対象のOSパッケージやグローバルな`node_modules`がベースの同じ場所にない結果 |
| 現在のベースで新しく出る | `rebuild_check.only_in_base` | 現在のベースにだけ対象の所見がある結果 |
| 実行環境の版を引き継ぐ場合の見込み | `rebuild_runtimes` | Node.jsやPythonの版を引き継ぐ場合のCVEの見込み |

実行環境については、現在のベースの版を引き継ぐ場合の見込みを次のように表示します。

```text
現在の … の Node.js は …。この版を引き継げば、検出中の Node.js … の … 件のうち … 件は出なくなる見込み(再ビルド後のイメージは未確認)
```

件数は検出中の実行環境のCVEを対象とし、新しい版で増えるCVEは含めません。
Pythonでは`Python runtime`と表示し、残る所見だけの場合も見込みを表示します。

Slackのパッケージ一覧には、次の表示規則があります。

- パッケージ名と版を表示し、CVEのIDは出さない
- 「現在のベースにない」に含まれるグローバルな`node_modules`のパッケージは、それを内側の`node_modules`に含む外側のパッケージごとにまとめる
- 1行に表示するのは10件までとし、超える分は件数にする

次は、グローバルに配置された`npm`の内側に`undici`がある例です。

```text
/usr/local/lib/node_modules/
`-- npm/                         # 外側のパッケージ
    `-- node_modules/
        `-- undici/package.json  # npmに含まれるパッケージ
```

「現在のベースにない」に含まれるこの`undici`は、個別の名前ではなく、`npm`に含まれるパッケージの件数にまとめて表示します。
再ビルドの見込みには、次の制約があります。

- Dockerfileの`RUN`の効果は判定しないため、`apk upgrade`などで「残る」の所見が消えることがある
- Dockerfileが古い版を同じ場所に入れ直すと、「消える見込み」の所見も残ることがある
- 「現在のベースにない」は、ベースから消えたものとDockerfileで足したものを区別できない
- 「現在のベースで新しく出る」には、Dockerfileの手順で完成イメージから消す所見も含む
- Webhookの結果フィールド`dockerfile_items[].final_image_verified`は`false`で、再ビルド後の完成イメージを検証していないことを示す

再ビルド後に実際に入る版や、配置後の稼働イメージでの解消を確認した結果ではありません。
判定の詳細は[直接依存の版指定](remediation-node-python-logic.md#direct-dependencies)、[ベースレイヤーの照合](remediation-base-image-logic.md#base-layer-matching)、[標準ライブラリの再ビルド案内](remediation-go-logic.md#go-stdlib-rebuild)を参照してください。
