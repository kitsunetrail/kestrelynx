# Slackの読み方

## レポートの確認場所 {#slack-display}

Slackでは、チャンネルの通知から変化や未解決状態を確認し、Botのスレッドから詳細を確認できます。
修正計画の表示は[Slackの修正計画](remediation-results.md#reading-results-in-slack-and-webhooks)を参照してください。

### チャンネルのレポート {#channel-display}

チャンネルに表示するレポートの見出しと内容を次に示します。

| レポート | 見出しの表示 | 表示する内容 |
| --- | --- | --- |
| `diff`モード（変化あり） | `前回のスキャンからの変化` | 前回からの変化と現在の未解決状態 |
| `diff`モード（変化なし） | `前回のスキャンから変化なし` | 変化がないことと現在の未解決状態 |
| `full`モード | `未解決の所見の全体` | 最新のスキャンで確認した未解決の所見 |
| 週次レポート | `📋 週次全体レポート — 未解決の所見の全体` | 差分通知に加える、最新のスキャンで確認した未解決の所見の全体 |

`未解決の所見の全体`を見出しとする`full`モードの通知と、週次レポートで差分通知に加わる`📋 週次全体レポート — 未解決の所見の全体`の部分を、全体レポートと呼びます。

表示には次の共通の決まりを適用します。

- 空の区分は表示しない
- トリアージ有効時の低優先度は、全体レポートでも件数だけを表示

汎用Webhookを設定している場合だけ、次の案内を表示します。

| 表示 | 表示する場所 | 条件 |
| --- | --- | --- |
| `詳細は汎用Webhookのペイロードに記載` | diffモード（週次レポートを除く）の現在の未解決の行の下 | 最新のスキャンのレポートに所見がある場合 |
| `詳細は汎用Webhookのペイロードに記載` | fullモードと週次レポートの低優先度の件数の行の下 | トリアージ有効時に低優先度の項目がある場合 |
| `低リスクの修正N件を集約 — 全件は汎用Webhookのペイロードに記載` | fullモードと週次レポート | トリアージ無効時に低リスクの修正をまとめた場合 |

低優先度の全件の詳細は[汎用Webhook](webhook-reference.md#generic-webhook)で確認できます。

通知の送信タイミングは[スキャン通知の送信条件](notification-conditions.md#notification-conditions)を参照してください。

### スレッドのレポート {#thread-display}

Botのスレッドは、`📊 未解決の所見の全体 — 日時`の見出しで、そのレポート時点の詳細を表示します。

チャンネル本文1通目の末尾には、次の案内を表示します。

| チャンネル本文1通目の末尾 | 確認先 |
| --- | --- |
| `📊 未解決の所見の全体はこのメッセージのスレッド ↓` | 最新のスキャンのレポートを投稿したスレッド |
| `🔗 前回のレポート時点の未解決の所見の全体 → スレッド` | 前回投稿したレポートのスレッド |

有効なリンクがない場合やリンクを表示できない場合は、末尾の案内を省略します。

スレッドの投稿と確認には、次の決まりを適用します。

- チャンネル本文が複数のメッセージに分かれても、スレッドは1通目に付く
- 前回のレポートへのリンク先は、そのレポートを作成した時点の内容
- 最新のスキャン後の未解決状態は、チャンネルの[現在の未解決件数](#open-now)で確認する

長い通知は複数のメッセージに分割し、続きには次の表示を付けます。

| 分かれたメッセージ | 付く表示 |
| --- | --- |
| スレッドの続き | 見出しに`(続き)` |
| チャンネルの続き | `(続き 2/3)`のような表示 |

未解決の所見の全体を返信として投稿する条件は[Slackスレッドの投稿条件](notification-conditions.md#slack-thread-delivery)を参照してください。

## 通知の言語 {#notification-language}

Slackの定型文は、設定した通知言語で表示します。
言語の設定値と適用範囲は[設定](configuration.md)を参照してください。

日本語の通知でも、深刻度（`CRITICAL`・`HIGH`など）、脆弱性の説明文、議論リンクのラベルは元の英語のまま表示します。

## 区分の並び順 {#section-order}

レポートの種類によって、変化を先に示す場合と、現在の未解決項目を区分別に示す場合があります。

### 差分レポートの並び順 {#diff-order}

次の例は、変化がある回の差分レポートです。

```text
🛡️ KestreLynx — 2026-06-24 09:00のスキャン結果
イメージ3件をスキャン、2件に影響あり
前回のスキャンからの変化

🆕 前回のスキャンからの新規検出 (4件)
イメージ: api:2.0
◆ libxml2
…

✅ 前回のスキャンからの解消 (1件)
• web:1.0: old-pkg

⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
• 原因を分類できなかった（詳細はログ）
…

📌 現在の未解決: 🚨 今すぐ対応3件 / 👀 要監視1件 / 🔕 低優先度3件
⏰ 今すぐ対応/要監視の未解決の最長期間20日
📊 未解決の所見の全体はこのメッセージのスレッド ↓
```

変化がある回と週次レポートでは、次の順に表示します。
該当する内容がない区分は省略します。

| 順序 | 内容 | 見出しの表示 |
| --- | --- | --- |
| 先頭 | ヘッダー、イメージ件数、Sensorの警告 | `🛡️ KestreLynx — 日時のスキャン結果`など |
| 変化の前 | 脅威情報源を利用できない警告 | `⚠️ EPSSデータが利用できない — KEVと深刻度のみで優先度を判定`など |
| イメージの変化 | digestの変更、イメージ名の更新 | `🔄 イメージの内容が変化 (N件)`など |
| EOLの変化 | 新規EOLのベースOS、EOLパッケージの変化 | `⛔ 新規: ベースOSのサポート終了(EOL) (最優先)`など |
| パッケージの変化 | 通常の新規検出・変化、解消・EOL解除 | `🆕 前回のスキャンからの新規検出 (N件)`、`✅ 前回のスキャンからの解消 (N件)` |
| 末尾 | 週次の全体レポート、またはスキャン失敗と現在の未解決状態 | `📋 週次全体レポート — 未解決の所見の全体`、`⚠️ スキャンできなかったイメージ N件（脆弱性は確認できていない）`など |

週次レポートではない変化なしの通知は、`前回のスキャンから変化なし`に続けて、スキャン失敗や現在の未解決状態を表示します。
保持の注釈は、未解決状態や全体レポートの後に付きます。

トリアージ有効時の通常の新規検出・変化は、優先度、イメージ名、パッケージ名の順です。

### 全体レポートの並び順 {#current-order}

次の例は、トリアージ有効時の全体レポートです。

```text
未解決の所見の全体
優先度: ⛔ EOLのベースOS1件 · 🚨 今すぐ対応3件 · 👀 要監視1件 · 🔕 低優先度4件

⛔ ベースOSのサポート終了(EOL) (最優先)
イメージ: web:1.0
状態: ベースOSがEOL (今後のセキュリティ更新なし)

🚨 今すぐ対応 (3件) — 悪用あり、または悪用の可能性が高い
◆ openssl
…

👀 要監視 (1件) — 緊急性は低いが継続監視
◆ e2fsprogs
…

🔕 低優先度 (4件) — イメージ2件で所見4件、悪用の兆候なし (KEV未掲載、EPSSはしきい値未満)

⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
…
📊 未解決の所見の全体はこのメッセージのスレッド ↓
```

トリアージ有効時は、チャンネルに次の見出しと順序で未解決項目を表示します。
Botのスレッドも同じ区分順です。

| 順序 | 見出しの表示 |
| --- | --- |
| 先頭 | `⛔ ベースOSのサポート終了(EOL) (最優先)` |
| 続き | `⛔ パッケージのサポート終了(EOL) (N件) — …` |
| 優先度順 | `🚨 今すぐ対応 (N件) — …` → `👀 要監視 (N件) — …` → `🔕 低優先度 (N件) — …` |

CISA KEVやEPSSの脅威情報源を利用できない警告は、`full`モードでは`優先度:`の行の直後、EOL区分より前に表示します。
週次レポートでは、この警告を通知冒頭のヘッダー（ヘッダー行・イメージ件数・Sensorの警告）の直後に1回だけ表示し、後ろの`📋 週次全体レポート — 未解決の所見の全体`の部分では`優先度:`の後に表示しません。

トリアージ有効時のチャンネルの全体レポートでは、EOL・今すぐ対応・要監視の区分の後に、該当する行だけを次の順に表示します。

| 順序 | 表示 |
| --- | --- |
| 1 | `🔕 低優先度 (N件) — …` |
| 2 | `🔇 通知オフ — 修正版がなく7日以上使用が確認されない: N件` |
| 3 | `⚠️ スキャンできなかったイメージ N件（脆弱性は確認できていない）` |
| 4 | `脅威情報はN日前のもの (配信元に接続できない)` |
| 5 | `🔎 稼働時の使用状況: ▶ 使用中N件 · …` |

KestreLynxはKEVやEPSSのデータの取得に失敗すると、取得から7日以内の保存済みデータで優先度を判定します。
トリアージ有効時は、使ったデータが1日以上前のものなら、`脅威情報はN日前のもの (配信元に接続できない)`と表示します。
`N`は、使ったデータのうち最も古いものを取得してからの日数です。
どちらのデータも使えない場合は、この注記の代わりに、脅威情報源を利用できない警告を前述の位置に表示します。

### トリアージ無効時の並び順 {#triage-disabled-display}

次の例は、トリアージ無効時の全体レポートです。

```text
未解決の所見の全体
優先度: 🔴 CRITICAL 3件 · 🟠 要注意1件 · 🟢 安全1件

✅ 今すぐ対応可能 (fixed)
◆ openssl
…

ℹ️ 修正版なし (affected / 上流の対応待ち)
◆ e2fsprogs
…

🔕 このOSリリースでは修正予定なし (will_not_fix)
◆ gcc-12-base
…

⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
…
低リスクの修正1件を集約
📊 未解決の所見の全体はこのメッセージのスレッド ↓
```

トリアージ無効時は、EOL区分に続いて、修正状態別に表示します。

| 順序 | 表示する区分 |
| --- | --- |
| 修正版あり | `✅ 今すぐ対応可能 (fixed)` |
| 修正版なし | `ℹ️ 修正版なし (affected / 上流の対応待ち)` |
| 修正予定なし | `🔕 このOSリリースでは修正予定なし (will_not_fix)` |

`今すぐ対応可能`は修正版がある区分で、トリアージの`今すぐ対応`とは意味が異なります。
修正状態の意味は[修正状態](scan-logic.md#status)を参照してください。

チャンネルでは、修正版ありのうち注意が必要な項目を個別に表示し、残りをイメージごとにまとめます。

### 区分の中の並び順 {#within-section-order}

全体レポートとスレッドでは、トリアージの有効・無効にかかわらず、各区分の中のイメージと各イメージの中のパッケージを次の基本の順で並べます。
イメージ同士・パッケージ同士を2つずつ比べ、前の条件で差がつかないときだけ次の条件で比べます。

イメージは次の順で比べます。

1. CRITICALの件数が多いほうが先
2. HIGHを含むほうが先
3. すべての深刻度を合わせたCVEの件数（合計）が多いほうが先
4. イメージ名の順

各イメージの中のパッケージは次の順で比べます。

1. CRITICALを含むもの → HIGHを含むもの → それ以外の順
2. すべての深刻度を合わせたCVEの件数（合計）が多いほうが先
3. パッケージ名の順

次の例は、Sensorによる並べ替え前の、1つの区分に含まれるイメージ4件の順です。

| 順 | イメージ | CRITICAL | HIGH | MEDIUM以下 | 合計 | 先になった理由 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `api:2.0` | 2 | 0 | 0 | 2 | CRITICALが最多 |
| 2 | `web:1.0` | 1 | 1 | 0 | 2 | 残る3件で唯一HIGHあり |
| 3 | `worker:1.0` | 1 | 0 | 4 | 5 | batchより合計が多い |
| 4 | `batch:1.0` | 1 | 0 | 2 | 3 | — |

トリアージ有効時にSensorの情報がある場合は、同じ優先度の区分内で次の条件を基本の順より先に適用し、差がないものは基本の順を保ちます。

イメージは次の順で比べます。

1. 使用中のパッケージを含むほうが先
2. 基本の順

各イメージの中のパッケージは次の順で比べます。

1. 使用中のほうが先
2. 使用中同士は、ポートの公開範囲が広いほうが先
    - 全インターフェースに公開
    - ループバックのみに公開
    - 待ち受け中 (未公開)
3. 高い権限で実行しているほうが先
4. 基本の順

使用中でないもの同士は、基本の順のままです。

`▶ 使用中`は、Sensorが稼働中のコンテナでパッケージの実行や読み込みなどを確認した状態を示します（詳しくは[使用状況のラベル](#usage-labels)）。
公開範囲と権限はそのパッケージを使っているコンテナのもので、表示は[観測根拠の表示](#runtime-evidence)で確認できます。
この並べ替えで優先度の区分をまたいで動かすことはなく、トリアージ無効時は適用しません。

## 件数の読み方 {#counts}

イメージ、パッケージ、CVEでは集計単位が異なります。
同じ通知内でも、件数が一致するとは限りません。

件数は深刻度ごとに分け、認識できない深刻度は`UNKNOWN`として数えます。
`MEDIUM`・`LOW`・`UNKNOWN`の件数は、`scan.severity`にそれぞれの深刻度を含めた場合だけ表示します。
既定の`[HIGH, CRITICAL]`では、これらの深刻度は検出対象外のため、件数を表示しません。
パッケージカードの「検出件数」、イメージの見出し、まとめて表示する行、トリアージ無効時の現在の未解決の行では、0でない件数を`HIGH`の後に`MEDIUM`・`LOW`・`UNKNOWN`の順で追加します（例: `CRITICAL 1 / HIGH 2 / MEDIUM 3`）。

### イメージ件数 {#image-counts}

ヘッダーの`イメージN件をスキャン、M件に影響あり`は、次の単位で数えます。

| 表示 | 英語 | 集計単位 |
| --- | --- | --- |
| スキャンした件数 | images scanned | 失敗を含む、イメージ名・digest・必要な場合のプラットフォームの組み合わせ |
| 影響ありの件数 | affected | 対象の脆弱性またはEOLのベースOSがあるイメージ名 |

registry digestで識別する場合は、同じイメージ名・digestでもOS・アーキテクチャが異なれば別件として数えます。
別のイメージ名が同じスキャン結果を共有していても、スキャンした件数では別件として数えます。
スキャン失敗だけのイメージ名は、影響ありの件数には含めません。

### 現在の未解決件数 {#open-now}

`📌 現在の未解決:`は、最新のスキャン後に残っている未解決の件数を示します。
トリアージ有効時は、次のように表示します。

```text
📌 現在の未解決: ⛔ EOLのベースOS2件 / ⛔ EOLのパッケージ4件 / 🚨 今すぐ対応2件 / 👀 要監視1件 / 🔕 低優先度1件
```

EOLのベースOSはイメージ名1つを1件、それ以外はイメージ名とパッケージの組み合わせ1つを1件として数えます。
0件の項目は表示しません。

各項目では、次のものを数えます。

| 表示 | 数えるもの |
| --- | --- |
| `⛔ EOLのベースOSN件` | ベースOSがEOLと記録されたイメージ |
| `⛔ EOLのパッケージN件` | EOLの検出結果がある組み合わせ |
| `🚨 今すぐ対応N件` | 今すぐ対応の組み合わせ |
| `👀 要監視N件`・`🔕 低優先度N件` | 要監視・低優先度の組み合わせ |

数え方には、次の決まりがあります。

- イメージのベースOSがEOLの場合は、次のように数える
    - そのイメージを`⛔ EOLのベースOSN件`に1件として数える
    - そのイメージで見つかったEOLのパッケージは、`⛔ EOLのパッケージN件`には数えない
- 優先度の件数では、同じイメージ名とパッケージの組み合わせを1回だけ数える
- 通常の検出結果とEOLの検出結果のどちらかが今すぐ対応なら、今すぐ対応に数える
- 今すぐ対応でない組み合わせは、通常の検出結果の優先度に従って要監視・低優先度に数える
- 検出結果がEOLだけで、優先度が要監視・低優先度の場合は、その組み合わせを優先度の件数に数えない
- EOLのパッケージに数えた組み合わせが今すぐ対応なら、今すぐ対応にも数える
- [通知オフ](#muted-display)の組み合わせは、優先度の件数に数えない

EOLと優先度の件数は保存している履歴から数えるため、スキャンに失敗したイメージなどの前回の記録も含みます（[保持中の履歴](diff-logic.md#retained-findings)）。
通常の検出結果とEOLの検出結果の区別は、[パッケージのEOL](scan-logic.md#eol-package)を参照してください。

トリアージ無効時は、次のように表示します。

```text
📌 現在の未解決: ⛔ EOLのベースOS1件 / CRITICAL 3件 / HIGH 6件、イメージ2件
```

トリアージ無効時の件数は、次のように数えます。

- EOLの項目は、トリアージ有効時と同じ数え方
- 深刻度別の件数は、最新のスキャンのレポートのパッケージごとのCVE件数を深刻度ごとに合計
- 同じCVEが別のパッケージにあれば、それぞれに数える
- イメージの件数は、所見のあるイメージの数
- `scan.severity`に含めた場合は、`HIGH`の後に`MEDIUM`・`LOW`・`UNKNOWN`の0でない件数を順に表示

最新のスキャンのレポートに検出項目がない場合は、件数の代わりに次の状態を表示します。

| 状態 | 表示 |
| --- | --- |
| Kubernetesでdigestを確認できずパッケージ履歴を保持 | `📌 現在の未解決: 未確認 — 再確認まで前回の所見を保持` |
| 上記以外で前回の履歴を保持 | `📌 現在の未解決: 未再スキャン — 次のスキャン成功まで前回の所見を保持` |
| 保持中の履歴もなし | `🎉 現在の未解決: なし — 問題なし` |

### 優先度の行の件数 {#priority-counts}

全体レポートの`優先度:`は、最新のスキャンのレポートに含まれるEOLや対応の優先度を件数で示します。
トリアージ有効時は、次のように表示します。

```text
優先度: ⛔ EOLのベースOS1件 · 🚨 今すぐ対応3件 · 👀 要監視1件 · 🔕 低優先度4件
```

`優先度:`の行では、パッケージをカード1枚に当たる単位で数えます。
低優先度など、カードを個別に表示しない場合も、同じ単位で数えます。

同じイメージの同じパッケージで見つかったCVEを、修正状態ごとに1枚のカードにまとめます。
api:2.0のopensslを例に、カードの枚数と件数を示します。

| 検出結果 | カードの枚数 | 件数 |
| --- | --- | --- |
| 修正版のあるCVEが3つ | 1枚 | 1件 |
| 修正版のあるCVEが2つ、修正版のないCVEが1つ | 修正状態が違うため2枚 | 2件 |

同じパッケージ名でも、エコシステムやインストールされている版が違えば別のカードになります。
詳しくは[パッケージカードの読み方](#package-card)を参照してください。

同じイメージ名でもdigestが異なれば、分けて数えます。
EOLのベースOSだけは、イメージ名1つを1件として数えます。

トリアージ有効時の各項目では、次のものを数えます。
0件の項目は表示しません。

| 表示 | 数えるもの |
| --- | --- |
| `⛔ EOLのベースOSN件` | ベースOSがEOLと判定されたイメージ |
| `⛔ EOLのパッケージN件` | EOLの検出結果があるカード |
| `🚨 今すぐ対応N件` | 今すぐ対応のカード（EOLの検出結果で今すぐ対応のものも含む） |
| `👀 要監視N件`・`🔕 低優先度N件` | 通常の検出結果のカード（要監視・低優先度） |

EOLと通知オフには、次の決まりがあります。

- イメージのベースOSがEOLの場合は、そのイメージのEOLパッケージをEOLのパッケージの件数には数えない
- EOLパッケージが今すぐ対応なら、ベースOSのEOLにかかわらず今すぐ対応にも数える
- [通知オフ](#muted-display)のカードは、優先度の件数に数えない

トリアージ無効時は、次のように表示します。

```text
優先度: 🔴 CRITICAL 3件 · 🟠 要注意1件 · 🟢 安全1件
```

EOLの件数はトリアージ有効時と同じ対象で数え、それ以外は次のように数えます。

| 表示 | 数えるもの |
| --- | --- |
| `🔴 CRITICAL N件` | 通知オフを除くCRITICALのCVE件数 |
| `🟠 要注意N件` | 修正版への更新でメジャーバージョンが上がるカード |
| `🟢 安全N件` | 修正版があり、CRITICALもメジャー更新もないカード |

CRITICALと安全の件数には、次の決まりがあります。

- CRITICALは、修正版あり・修正版なし・修正予定なし・EOLパッケージの各区分の件数を合計
- 安全には、更新の注意度が分からないカードも含める

安全という分類は、更新の安全性や互換性を保証するものではありません。
表示の意味は[更新の注意度](#upgrade-risk)も参照してください。

トリアージ有効時の今すぐ対応・要監視・低優先度について、[現在の未解決の行](#open-now)との数え方の違いを示します。

| 行 | 元にするもの | 1件の単位 |
| --- | --- | --- |
| 優先度の行 | 最新のスキャンのレポート | 修正状態ごとに分けたカード |
| 現在の未解決の行 | 保存している履歴 | イメージ名とパッケージの組み合わせ |

### 未解決の経過日数 {#unresolved-age}

未解決の経過日数は、チャンネルでは対象全体の最長期間、スレッドのカードではそのイメージ名とパッケージの組み合わせの期間を示します。

表示する場所と日数による違いを次に示します。
表のNには経過日数が入ります。

| 場所・条件 | 表示 | 意味 |
| --- | --- | --- |
| チャンネル・トリアージ有効・1〜13日 | `今すぐ対応/要監視の未解決の最長期間N日` | EOLも含めた対象全体の最長期間 |
| チャンネル・トリアージ無効・1〜13日 | `未解決の最長期間N日` | すべての優先度を含む最長期間 |
| チャンネル・トリアージ有効・14日以上 | `⏰ 今すぐ対応/要監視の未解決の最長期間N日` | 長期間未解決であることを示す表示 |
| チャンネル・トリアージ無効・14日以上 | `⏰ 未解決の最長期間N日` | 長期間未解決であることを示す表示 |
| スレッドのカード・1日以上 | `⏱ 未解決N日 · 初回検出2026-06-04` | その組み合わせの経過日数と初回検出日 |
| スレッドのカード・0日 | `⏱ 本日初検出` | 初回検出から1日未満の表示 |

チャンネルの最長期間は、対象となる履歴の最も古い初回検出日時から数えます。
1日以上で表示し、14日以上で`⏰`を付けます。

最長期間の対象は、トリアージの設定によって異なります。

| トリアージ | 最長期間の対象 |
| --- | --- |
| 有効 | 通常の今すぐ対応・要監視の検出結果と、EOLのベースOS・パッケージ |
| 無効 | 通常のすべての検出結果と、EOLのベースOS・パッケージ |

EOLや履歴の扱いには、次の決まりがあります。

- イメージのベースOSがEOLの場合は、EOLのパッケージの期間をベースOSの初回EOL検出日で数える
- EOLのパッケージが今すぐ対応の場合は、ベースOSのEOLにかかわらず、パッケージ自身の初回EOL検出日を対象に含める
- イメージのベースOSがEOLでない場合は、EOLのパッケージ自身の初回EOL検出日で数える
- スキャン失敗などで[保持している履歴](diff-logic.md#retained-findings)も対象に含める
- トリアージ有効時は、最新のスキャンで[通知オフ](#muted-display)と判定した通常の検出結果を対象から除く

スレッドのカードは、通常の検出結果ならその初回検出日、EOLの検出結果なら初回EOL検出日から数えます。
初回検出日の記録がないカードでは、期間を表示しません。

汎用Webhookは低優先度や通知オフも含めるため、Slackのトリアージ有効時とは集計対象が異なります（[未解決の最長期間](webhook-reference.md#oldest-open-days)）。

## パッケージカードの読み方 {#package-card}

パッケージカードは、パッケージ名に続けて、現在の版・修正版・検出件数などを表示します。
チャンネルの今すぐ対応では、次の詳細カードを使います。

```text
◆ openssl
現在: 3.0.7
修正版: 3.0.11
更新の注意度: 🟢 ディストリのセキュリティパッチ
検出件数: CRITICAL 1 / HIGH 0
代表CVE: CVE-2031-0001 · CRITICAL · EPSS 94%
悪用情報: CISA KEV (実際の攻撃で悪用あり) · 🧨 ランサムウェア攻撃
参照: アドバイザリ · ベンダーのアドバイザリ
```

チャンネルの要監視では、次の簡略カードを使います。

```text
◆ e2fsprogs
現在: 1.47.0-2 · 修正版: なし
検出件数: CRITICAL 1 / HIGH 0
代表CVE: CVE-2031-0003 · EPSS 3%
```

カードの使い分けを次に示します。
チャンネルの全体レポートには、週次レポートに加わる全体レポートも含みます。

表の「注意が必要な修正版あり」は、CRITICALを含むかメジャー更新が必要なパッケージを指します。

| 場所 | 詳細カード | 簡略カード | カードなし（件数やまとめ） |
| --- | --- | --- | --- |
| チャンネルの全体レポート（トリアージ有効） | 今すぐ対応 | 要監視・EOL | 低優先度 |
| チャンネルの全体レポート（トリアージ無効） | — | 注意が必要な修正版あり・修正版なし・修正予定なし・EOL | それ以外の修正版あり |
| スレッド（トリアージ有効） | 今すぐ対応・要監視・EOL | EOL区分の参照案内 | 低優先度 |
| スレッド（トリアージ無効） | すべての修正状態 | — | — |
| チャンネルの差分 | トリアージ有効時の今すぐ対応 | それ以外の個別表示するパッケージ | — |

EOLと通知オフには、次の例外があります。

- ベースOSがEOLの場合は、そのイメージのEOLパッケージをベースOSの表示にまとめる
- トリアージが有効で、EOLのパッケージが今すぐ対応の場合は、今すぐ対応の区分に詳細カードを表示
- 全体レポートやスレッドのEOL区分に`詳細: 🚨 今すぐ対応を参照`がある場合は、そのパッケージの詳細を今すぐ対応の区分で確認する
- [通知オフ](#muted-display)のパッケージは、個別カードの対象外

各項目を表示する場合の書式を次に示します。
この比較は、チャンネルとスレッドのカードに共通です。

| 項目 | 詳細カード | 簡略カード |
| --- | --- | --- |
| 現在の版・修正版 | それぞれ別の行 | 同じ行 |
| 更新の注意度 | `更新の注意度:`の行 | 修正版の後の括弧内 |
| 検出件数 | 深刻度別のCVE件数 | 深刻度別のCVE件数 |
| 対応 | [イメージの更新による解消と新しい版待ち](#base-image-wait) | [イメージの更新による解消と新しい版待ち](#base-image-wait) |
| CVE | 代表CVE・悪用情報・参照 | 代表CVEの短い表示 |
| 使用状況 | 観測根拠を含む表示 | 使用中の短い表示 |

`検出件数:`は、そのカードに含まれるCVE IDを重複なく数えた件数です。
カードを分ける単位は[優先度の行の件数](#priority-counts)、代表CVEの表示条件は[CVEの表示](#cve-details)を参照してください。

使用状況は、チャンネルでは使用中の情報を表示し、スレッドの詳細カードでは使用が確認されない場合や判定できない場合も表示します。
詳しくは[使用状況のラベル](#usage-labels)を参照してください。

修正版がない場合は`修正版: なし`と表示します。
詳細カードには、修正状態に応じて次の案内を添えます。

| 修正状態 | 表示 |
| --- | --- |
| 修正版なし | `修正版: なし — 緩和策を検討` |
| このOSリリースでは修正予定なし | `修正版: なし — このOSリリースでは修正予定なし、置き換えを検討` |

EOLのカードに添える案内は、[EOLの表示](#eol-display)を参照してください。

カードの前にあるイメージの見出しは、後に続くパッケージがどのイメージで見つかったかを示します。
次は、その見出しの例です。

```text
イメージ: api:2.0
```

同じイメージ名に複数のdigestがある場合は、短縮したdigestを付けて区別します。
必要に応じて、OS・CPUアーキテクチャも添えます。

### CVEの表示 {#cve-details}

`代表CVE:`は、そのカードに含まれるCVEのうち、優先度とEPSSを基に選んだ1件を示します。
次は、代表CVEのほかに1件のCVEがある詳細カードの表示例です。

```text
代表CVE: CVE-2031-0006 · HIGH · EPSS 20% (このパッケージにほか +1件のCVE)
```

代表CVEは、次の順で比べて選びます。
前の条件で差がつかない場合だけ、次の条件を使います。

1. 優先度が今すぐ対応 → 要監視 → 低優先度の順
2. EPSSのスコアがあるCVEを、スコアがないCVEより先に選ぶ
3. EPSSのスコアが高いCVEを先に選ぶ
4. CVE IDを文字列の昇順で比べ、先になるCVEを選ぶ

簡略カードでの代表CVEの表示には、次の決まりがあります。

- 全体レポートの要監視とEOLの簡略カードでは、トリアージ有効時にKEVまたはEPSSを利用できる場合、代表CVEを表示
- トリアージ無効時、またはKEVとEPSSの両方を利用できない場合は、全体レポートの簡略カードの代表CVEを省略
- 差分の簡略カードでは、新しく追加されたCVEのIDを表示する場合は代表CVEを省略し、それ以外は代表CVEを表示

代表CVE以外のCVEは、表示場所に応じて次のように示します。

| 表示場所 | ほかのCVEの扱い |
| --- | --- |
| チャンネルの詳細カード | `代表CVE:`に`(このパッケージにほか +N件のCVE)`を添える |
| スレッドの詳細カード | `ほかのCVE:`にIDを並べ、省略分を`(ほか +N件)`で示す |
| チャンネルの差分カード | `変化:`に新しく追加されたCVEのIDを表示 |

ほかのCVEの件数は、そのカードに含まれるCVEを対象とします。
詳細カードの`EPSS n/a`はスコアがないことを示し、非常に小さい値は`<0.1%`、非常に大きい値は`>99%`と表示します。

`悪用情報:`は、代表CVEについて確認できた悪用の情報を示します。
次の例は、実際の攻撃での悪用とランサムウェア攻撃の情報がある場合です。

```text
悪用情報: CISA KEV (実際の攻撃で悪用あり) · 🧨 ランサムウェア攻撃
```

悪用情報の各表示は、次の意味です。

| 表示 | 意味 |
| --- | --- |
| `CISA KEV (実際の攻撃で悪用あり)` | 代表CVEがCISA KEVに掲載され、実際の攻撃で悪用されている |
| `🧨 ランサムウェア攻撃` | 代表CVEについて、ランサムウェア攻撃での悪用情報がある |

優先度の判断は[悪用情報による優先度](scan-logic.md#triage)を参照してください。

スレッドの`説明:`には、代表CVEの説明文を表示します。
説明文の出どころは、次のとおりです。

| 検出結果 | 説明文の出どころ |
| --- | --- |
| Trivyの所見 | Trivyの説明文 |
| Node.js・Python本体の所見 | 各ランタイムの脆弱性情報 |

省略されていないCVEの全データは[脆弱性のフィールド](webhook-reference.md#vulnerability-fields)で確認できます。

### イメージの更新による解消と新しい版待ち {#base-image-wait}

カードの`対応:`行は、そのパッケージの脆弱性が、イメージや元イメージを新しい版に上げると消えるかどうかを調べた結果です。
チャンネルの詳細カード・簡略カード、スレッド、差分カードの`検出件数:`の次に表示します。

系列は、3.11と3.13のように、版の先頭2つの数字で区別するまとまりです。

元イメージを新しい系列に上げると解消する場合は、次のように表示します。

```text
対応: 元イメージ python 3.11.9 → 3.13.1 で解消（minor の更新、同じ系列に新しい版なし、ベースの比較）
```

行の各部分と、結果に応じて付く補足の意味を次に示します。
表中の脆弱性は、そのカードに含まれる修正版のある所見を指します。

| 表示の部分 | 意味 |
| --- | --- |
| `元イメージ` | Dockerfileで指定した、イメージを作る土台となるイメージ |
| `イメージ` | 配布されているイメージそのもの |
| `python` | 更新対象のイメージ名の末尾で、レジストリのホスト名や途中のパスは省略 |
| `3.11.9 → 3.13.1` | 左が現在のイメージの版、右が比較した候補の版 |
| `で解消` | 候補では、カードの対象の脆弱性がすべて消える |
| `で一部解消` | 候補では、カードの対象の脆弱性の一部が消え、残りは解消しない |
| `の新しい版待ち` | 確認した範囲では、カードの対象の脆弱性を解消できる版が見つかっていない |
| `2件中1件` | カード内の修正版がある脆弱性をIDごとに数え、2件中1件が候補で解消 |
| `minor の更新` | 版の先頭の数字は同じで、2番目の数字が増える更新 |
| `major の更新` | 版の先頭の数字が増える更新 |
| `同じ系列に新しい版なし` | 現在と同じ系列には、より新しい版がない |
| `同じ系列の新しい版では未解消` | 現在と同じ系列の新しい版では、対象の脆弱性が解消しない |
| `ベースの比較` | 現在と候補の元イメージを比べた結果で、再ビルド後の完成イメージは未確認 |
| `新たな所見あり` | 候補への更新には、新たな所見も伴う |
| `確認した 1.27.3 と 2.0.1 でも未解消` | 記載された候補でも対象の脆弱性が残り、ほかの版での解消は未確認 |

結果ごとの行の例を次に示します。

| 結果 | 表示例 |
| --- | --- |
| 元イメージで解消 | `対応: 元イメージ python 3.11.9 → 3.13.1 で解消（minor の更新、同じ系列に新しい版なし、ベースの比較）` |
| イメージで一部解消 | `対応: イメージ nginx 1.24.1 → 1.27.3 で一部解消（2件中1件、minor の更新、同じ系列に新しい版なし）` |
| 確認した新しい系列でも未解消 | `対応: イメージ nginx 1.24.1 の新しい版待ち（確認した 1.27.3 と 2.0.1 でも未解消）` |
| 同じ系列と新しい系列で未解消 | `対応: イメージ nginx の新しい版待ち（同じ系列の新しい版と、確認した 2.0.1 で未解消）` |
| 条件に合う新しい版なし | `対応: 元イメージ python 3.11.9 の新しい版待ち（同じ系列にも、条件に合う新しい系列にも新しい版なし）` |
| 同じ系列に新しい版なし | `対応: 元イメージ python 3.11.9 の新しい版待ち（同じ系列に新しい版なし）` |

解消するか判断できない所見を含むカードなどでは、`対応:`行を省略することがあります。
ただし、元イメージに同じ系列の新しい版がないと分かっている場合は、その情報だけを表示することもあります。

カードの`対応:`行だけが変わっても、スレッドの全体レポートは送り直しません。
再投稿の条件は[Slackスレッドの投稿条件](notification-conditions.md#slack-thread-delivery)を参照してください。

細かな表示条件は[Slackのカードに出す行](remediation-logic.md#newer-series-slack-cards)、候補の選び方は[調べる版](remediation-logic.md#newer-series-versions)を参照してください。
修正計画メッセージの読み方は[表示項目](remediation-results.md#slack-fields)で確認できます。

### 更新の注意度 {#upgrade-risk}

更新の注意度は、現在の版から修正版へのバージョン変更の種類を示します。
詳細カードでは、次のように表示します。

```text
更新の注意度: 🟢 ディストリのセキュリティパッチ
```

各表示の意味を次に示します。

| 表示 | 意味 |
| --- | --- |
| `🟢 ディストリのセキュリティパッチ` | OSパッケージの修正版で、「ディストリ」はOSの配布元であるディストリビューションを指す |
| `🟢 低リスク` | 言語パッケージでメジャーバージョンが増えない変更 |
| `🟠 メジャーバージョン更新 — 要注意` | 言語パッケージでメジャーバージョンが増える変更 |
| `⚪ リスク不明` | バージョンを比較できない変更 |

緑色の表示は、更新の安全性や互換性を保証するものではありません。

### エコシステムの表示 {#ecosystem-labels}

エコシステムの表示は、パッケージ名の後の角括弧で、言語パッケージの種類を示します。
次は、Pythonパッケージの表示例です。

```text
◆ setuptools [python-pkg]
```

角括弧内の表示と対象を次に示します。

| 表示 | 対象 |
| --- | --- |
| `[python-pkg]` | Pythonパッケージ |
| `[node-pkg]` | Node.jsのパッケージ |
| `[gobinary]` | Goバイナリに含まれるパッケージ |
| `[jar]` | JavaのJARファイルに含まれるパッケージ |
| `[node-runtime]` | Node.js本体の所見 |
| `[python-runtime]` | Python本体の所見 |
| `[lang]` | 種類を特定できない言語パッケージ |
| 角括弧の表示なし | OSパッケージ |

Trivyが識別した言語パッケージには、この表以外の種類も表示します。
Node.js・Python本体の所見は、各ランタイムの脆弱性情報から作成します。

Node.js・Python本体を示す表示は、パッケージの種類を表すもので、稼働中のコンテナで使用を確認したという意味ではありません。
使用の確認結果は[使用状況のラベル](#usage-labels)で確認できます。

### 参照リンク {#reference-links}

`参照:`には、代表CVEに関連するリンクを表示します。
次の例では、脆弱性の案内とベンダーの情報へのリンクを表示しています。

```text
参照: アドバイザリ · ベンダーのアドバイザリ
```

リンクの表示と行き先を次に示します。

| 表示 | リンク先 |
| --- | --- |
| `アドバイザリ` | Trivyまたは各ランタイムの脆弱性情報が示す主要なアドバイザリー |
| `ベンダーのアドバイザリ` | KEVの注記にあるベンダーやCISAの情報 |
| `💬 HN (N pts)` | 関連するHacker Newsの議論（Nはポイント数） |

`代表CVE:`・`ほかのCVE:`・`変化:`に表示するCVE IDは、NVDへのリンクです。
GHSAやDLAなど、CVE以外のIDは通常のテキストで表示します。

## 変化の表示 {#change-labels}

差分通知では、イメージ、パッケージ、EOLの変化をそれぞれ表示します。
差分を成立させる規則は[差分と履歴の判定](diff-logic.md#comparison-baseline)を参照してください。

### イメージの変化 {#image-change-labels}

イメージの変化には、同じイメージ名で内容が変わった場合と、イメージ名が更新された場合の2種類の表示があります。
digestは、イメージの内容を識別する値です。

同じイメージ名でdigestが変わると、次の見出しの下にイメージ名と変更前後の短縮したdigestを表示します。

```text
🔄 イメージの内容が変化 (1件)
```

見出しの下の行は、次の書式です。
イメージ名と短縮したdigestが入る位置を示しています。

```text
• イメージ名: イメージ更新 (変更前の短縮したdigest → 変更後の短縮したdigest)
```

見出しの件数は、内容が変わったイメージ名の数です。
変更前後に複数のdigestがある場合は、それぞれをカンマで区切って表示します。

イメージ名が更新され、検出履歴を引き継いだ場合は、次のように表示します。
1行目の`sha-aaaa`と`sha-bbbb`はタグ、2行目の`0123456789ab`は短縮したdigestです。

```text
🔄 イメージ参照の更新: ghcr.io/acme/web sha-aaaa → sha-bbbb(検出履歴を引き継ぎ)
🔄 イメージ参照の更新: registry.example:5000/team/api 0123456789ab → 1.4(検出履歴を引き継ぎ)
```

矢印の前後には、更新前と更新後それぞれのイメージ名の指定に応じて、次の値を表示します。

| イメージ名の指定 | 矢印の前後に表示する値 |
| --- | --- |
| タグあり | タグ |
| タグがなく、digestで固定 | 短縮したdigest |
| タグもdigestもなし | `latest` |

履歴を引き継ぐ条件は、[イメージ名の更新](diff-logic.md#reference-changes)を参照してください。

### パッケージの変化 {#package-change-labels}

パッケージの変化は、区分の見出しと、カード内の`変化:`の行で示します。
同じイメージ名とパッケージの組み合わせについて、保存した履歴と最新のスキャンの結果を比べます。

次の例は、修正版が利用できるようになったパッケージの差分カードです。

```text
◆ dpkg
変化: 修正版が利用可能
現在: 1.21.22 · 修正版: 1.21.23 (🟢 ディストリのセキュリティパッチ)
検出件数: CRITICAL 0 / HIGH 1
代表CVE: CVE-2031-0004 · EPSS <0.1%
```

区分の見出しは、次の内容をまとめます。
新規検出の区分には、初めて検出したパッケージだけでなく、検出済みのパッケージの変化も含みます。

| 見出しの表示 | 含まれる内容 |
| --- | --- |
| `🆕 前回のスキャンからの新規検出 (N件)` | 初めての検出、優先度の上昇、CVEの追加、修正版の公開、通知の再開 |
| `✅ 前回のスキャンからの解消 (N件)` | パッケージの検出結果の解消と、パッケージ・ベースOSのEOL解除 |

見出しのNは、次のように数えます。

- 新規検出では、表示対象のイメージ名とパッケージの組み合わせを1件として数える
- 解消では、解消またはEOL解除となったイメージ名とパッケージの組み合わせを1件として数え、ベースOSのEOLが解消したイメージ名の数を加える

新規検出では、同じ組み合わせでも修正版の有無などでカードが分かれるため、見出しの件数とカードの数が一致しない場合があります。

カード内の`変化:`の行は、次の変化を示します。

| 表示 | 出る場面 |
| --- | --- |
| `変化: ⬆️ 今すぐ対応に優先度昇格` | 要監視または低優先度だった組み合わせが、今すぐ対応になった場合 |
| `変化: ⬆️ 要監視に優先度昇格` | 低優先度だった組み合わせが、要監視になった場合 |
| `変化: 新しいCVE CVE-2031-0007` | 保存した履歴にないCVEが、その組み合わせで検出された場合 |
| `変化: 修正版が利用可能` | 修正版がなかった組み合わせで、修正版のある検出結果が見つかった場合 |

保存した履歴にない組み合わせを初めて検出したカードには、`変化:`の行を付けません。
CVEの追加で複数のカードを表示する場合も、追加されたCVEを含まないカードでは、この行を省略します。

複数の変化がある場合の判定順は、[通常のパッケージの変化](diff-logic.md#normal-changes)を参照してください。
通知オフからの再開表示は、[通知オフの表示](#muted-display)を参照してください。

### EOLの表示 {#eol-display}

EOL（サポート終了）の表示には、ベースOSがEOLのイメージの表示と、EOLのパッケージの表示があります。
パッケージのEOLは、対象リリースでサポート範囲外とされたCVEの検出結果を示します（[パッケージのEOL](scan-logic.md#eol-package)）。

次の例は、全体レポートでベースOSがEOLのイメージを表示した部分です。

```text
⛔ ベースOSのサポート終了(EOL) (最優先)
イメージ: legacy:1
状態: ベースOSがEOL (今後のセキュリティ更新なし)
サポート終了(EOL)のパッケージ2件を含む
```

全体レポートとスレッドでは、ベースOSがEOLのイメージについて、次のように表示します。

- そのイメージのEOLパッケージは個別のカードにせず、ベースOSの行に件数で示す
- トリアージ有効時は、そのうち今すぐ対応のパッケージだけ、今すぐ対応の区分にも詳細カードを表示する

全体レポートでは、EOLパッケージの件数や詳細の確認先を次の文言で示します。

| 表示 | 読み方 |
| --- | --- |
| `サポート終了(EOL)のパッケージN件を含む` | このイメージのベースOSの行にまとめたEOLパッケージの件数 |
| `詳細: 🚨 今すぐ対応を参照` | このパッケージの詳細は今すぐ対応の区分に表示 |

差分では、新たなEOL検出、CVEの追加、EOL解除を次の文言で示します。

| 表示 | 読み方 |
| --- | --- |
| `新たにサポート終了(EOL)となったパッケージN件を含む` | 新たにEOLと判定したベースOSの行にまとめた、新たなEOLパッケージの件数 |
| `パッケージN件が新たにサポート終了(EOL)` | EOLのベースOSの下に件数で示す、新たなEOLパッケージ |
| `新規CVEのあるサポート終了(EOL)のパッケージN件` | EOLのベースOSの下に件数で示す、CVEが追加されたEOLパッケージ |
| `ベースOSのEOLが解消` | そのイメージ名が、ベースOSのEOLの記録からなくなったこと |
| `サポート終了(EOL)が解消` | そのパッケージのEOLの検出結果がなくなり、通常の検出結果が残っていること |

`⛔ 新規: パッケージのサポート終了(EOL) (N件) — ベンダーがこれらのCVEをこのリリースのサポート対象外と報告`のNは、変化があったイメージ名とパッケージの組み合わせを数えます。
新たなEOL検出だけでなく、今すぐ対応への優先度上昇やCVEの追加も対象です。

この見出しの件数に含めるものと、含めないものは次のとおりです。

- 個別のカードで表示するEOLパッケージの変化は数える
- ベースOSが既にEOLのイメージでは、件数にまとめた新たなEOL検出やCVE追加も数える
- ベースOSを新たにEOLと判定したイメージでも、検出済みのEOLパッケージへのCVE追加は数える
- ベースOSとパッケージを同時に新たなEOLと判定した場合、今すぐ対応以外のパッケージはベースOSの行にまとめ、この見出しには数えない

カードの修正版の案内は、パッケージの種類と表示場所によって次のように異なります。
表の「通常のEOLパッケージ」は、Node.js・Python本体以外のEOLパッケージです。

| カードの種類と場所 | 修正版の表示 |
| --- | --- |
| 通常のEOLパッケージの簡略カード（チャンネル、スレッドの今すぐ対応への案内） | `修正版: なし — サポート終了(EOL): このリリースでは修正予定なし` |
| 通常のEOLパッケージの詳細カード（チャンネルの今すぐ対応、スレッド） | `修正版: なし — サポート終了(EOL): このリリースでは修正予定なし、サポート中のバージョンを検討` |
| Node.js・Python本体のカード（チャンネル、スレッド） | `修正版: なし — サポート終了(EOL): この系列には修正版が出ないため、系列を上げる必要がある(手動)` |

EOLではなくなっても、脆弱性は通常の検出結果として残ることがあります。
EOLの意味は[検出結果の分類](scan-logic.md#finding-classification)、解除の判断は[解消の判定](diff-logic.md#resolved-findings)を参照してください。

## 稼働時の使用状況の表示 {#runtime-display}

Sensorの情報がある場合、パッケージに使用状況を表示します。
Sensorは、稼働中のコンテナでパッケージが使われているかを観測する仕組みです。

使用判定や観測の限界は[稼働時の使用状況](runtime-usage.md)を参照してください。

### 使用状況のラベル {#usage-labels}

使用状況のラベルは、カードに表示するパッケージについて、次の状態を示します。

| 表示 | 意味 |
| --- | --- |
| `▶ 使用中` | 使用を確認したパッケージ |
| `▷ 使用が確認されない` | 観測期間内に使用を確認していないパッケージ |
| `▷ 稼働時の使用状況を判定できない` | 判定に必要な情報を利用できないパッケージ |

使用が確認されないことは、未使用であることを意味しません。
判定できない場合は、括弧内に理由を表示します。

次の例は、別々のパッケージに付く使用状況の行を抜粋したものです。

```text
使用状況: ▶ 使用中 (実行中)
使用状況: ▷ 使用が確認されない
使用状況: ▷ 稼働時の使用状況を判定できない (Sensorの報告なし)
```

使用状況の表示は、通知の場所とカードの種類によって異なります。

| 表示する場所 | 表示する内容 |
| --- | --- |
| チャンネルの詳細カード | 使用中の場合に、使用状況と観測根拠を表示 |
| チャンネルの簡略カード | 使用中の場合に、動作を括弧内に短く表示 |
| スレッドの詳細カード | 使用中・使用が確認されない・判定できない状態を表示 |
| 全体レポートとスレッドの低優先度 | 個別カードを出さず、区分の件数に使用中の件数を添える |
| チャンネルの差分にある低優先度 | 新規検出やCVE追加を簡略カードで表示 |

チャンネルの全体レポートでは、低優先度のうち使用中の件数を見出しの末尾に添えます。
次の例では、低優先度2件のうち1件が使用中です。

```text
🔕 低優先度 (2件) — イメージ2件で所見2件、悪用の兆候なし (KEV未掲載、EPSSはしきい値未満) · ▶ 使用中1件
```

スレッドでは、同じ件数を次のように別の行で示します。
どちらの場所でも、使用中が0件なら使用中の件数は表示しません。

```text
🔕 低優先度 (2件) — 悪用の兆候なし
▶ 低優先度のうち使用中: 1件
```

判定できない理由のうち、Sensorからの情報の取得と、観測の準備・継続に関する表示は次のとおりです。

| 理由の表示 | 意味 |
| --- | --- |
| `Sensorの報告なし` | Sensorの観測結果のファイルがまだない |
| `Sensorの報告が古い` | Sensorの報告や対象コンテナの確認から時間がたち、使用が確認されないと判断できない |
| `証拠が無効` | Sensorの観測結果を読み取り、内容を検証する処理に失敗している |
| `Sensorの隔離失敗` | Sensorに読み取り以外の操作を制限する設定ができず、観測を始めていない |
| `権限不足` | Sensorがコンテナのプロセス情報やファイルを読む操作を拒否されている |
| `索引が未構築` | パッケージとファイルを対応付けるための準備ができていない |
| `ワーカーの処理が停滞` | 対象コンテナを調べる処理が制限時間内に終わっていない |
| `証拠の切り詰め` | 読み取り量などの上限に達し、観測に必要な情報の一部を取得できていない |
| `証拠が不完全` | 観測結果の一部を利用できず、その部分での使用を確認できない |

コンテナと観測結果の対応に関する表示は次のとおりです。

| 理由の表示 | 意味 |
| --- | --- |
| `コンテナの世代が未確認` | 観測結果が、現在のコンテナの起動状態とスキャン対象のイメージに対応するか確認できない |
| `コンテナが未観測` | 対象コンテナについて、判定に使える観測結果がない |

パッケージの管理情報や、そのファイルとの対応に関する表示は次のとおりです。

| 理由の表示 | 意味 |
| --- | --- |
| `パッケージデータベースの解析失敗` | コンテナ内のパッケージ管理情報を解析できない |
| `パッケージデータベースなし` | コンテナ内に、利用できるパッケージ管理情報が見つかっていない |
| `パッケージデータベースのエラー` | パッケージ管理情報の読み取りか解析に失敗している |
| `パッケージデータベースが未対応` | コンテナ内のパッケージ管理情報が、Sensorの対応していない形式 |
| `このパッケージのファイル一覧なし` | パッケージ管理情報から、そのパッケージに属するファイルの一覧を取得できない |
| `所有元が複数` | 観測したファイルが複数のパッケージに属し、どのパッケージの使用か特定できない |
| `ファイルが置き換えられている` | 観測したファイルが削除・置換され、パッケージとの対応を確定できない |
| `バージョン不一致` | Sensorが使用を確認したパッケージの版が、スキャンで検出した版と異なる |

言語パッケージとの対応に関する表示と、理由を特定できない場合の表示は次のとおりです。

| 理由の表示 | 意味 |
| --- | --- |
| `エコシステムの対応付けなし` | その言語パッケージの種類について、使用判定に使う実行環境が対応付けられていない |
| `バイナリのパス不明` | パッケージの使用判定に必要な実行ファイルの場所が、スキャン結果にない |
| `不明` | 判定できない理由を特定できない |

### 観測根拠の表示 {#runtime-evidence}

使用中の詳細カードは、使用を確認した動作と、その観測に関する情報を示します。
次の例では、nginxの実行を根拠に使用中と判定しています。

```text
使用状況: ▶ 使用中
観測根拠: 実行中 /usr/sbin/nginx
公開状態: 全インターフェースに公開 · 高い権限で実行 · 最終確認06-24 09:00
```

例の各行は、次の内容を示します。

| 行 | 読み方 |
| --- | --- |
| `使用状況:` | カードのパッケージを使用中と判定した結果 |
| `観測根拠:` | 使用を確認した動作とプログラム |
| `公開状態:` | ポートの公開範囲、実行時の権限、観測の最終確認時刻 |

これらの情報は、そのパッケージを使用している1つのコンテナの観測から表示します。
複数のコンテナで使用している場合は、公開範囲が広いものを優先し、同じ範囲なら権限が高いものを選びます。

観測根拠には、定期的な確認で見つけた実行状態と、起動・読み込みの出来事として捉えた動作があります。
プログラムのパスの前に付く文言は、次の意味です。

| 表示 | 意味 |
| --- | --- |
| `実行中` | 定期的な確認で、そのパッケージのファイルが実行中だった |
| `読み込んだプログラム` | 定期的な確認で、そのパッケージのライブラリを読み込んだプログラムが動いていた |
| `実行を観測` | そのパッケージのファイルが実行される出来事を捉えた |
| `ライブラリ読み込みを観測` | そのパッケージのライブラリが読み込まれる出来事を捉えた |
| `組み込み先の実行中バイナリ` | 定期的な確認で、言語パッケージを組み込んだ実行ファイルが動いていた |
| `バイナリの実行を観測` | 言語パッケージを組み込んだ実行ファイルが起動する出来事を捉えた |
| `稼働中の実行環境` | 定期的な確認で、言語パッケージに対応する実行環境が動いていた |
| `実行環境の実行を観測` | 言語パッケージに対応する実行環境が起動する出来事を捉えた |

実行環境を根拠とする表示は、その環境に対応する言語パッケージをまとめて使用中とみなした結果です。
個々のパッケージの読み込みを確認した結果ではありません（[使用判定の説明](runtime-usage.md)）。

`実行中`も観測した時点の状態を示すため、通知を読んでいる時点で動いているとは限りません。
観測した時刻は、`最終確認`で確認できます。

複数のプログラムで異なる動作を確認し、動作とプログラムを対応付けられない場合は、次のように一覧を分けます。

```text
観測根拠: 実行中; ライブラリとして読み込み済み; プロセス: /usr/bin/helper, /app/server
```

この例は、実行とライブラリの読み込みを確認したことを示します。
`プロセス:`は観測したプログラムの一覧で、前に並ぶ動作と順番に対応するものではありません。

公開範囲・権限・最終確認は、利用できる情報を`公開状態:`の1行にまとめて表示します。
それぞれの表示の意味は次のとおりです。

| 表示 | 意味 |
| --- | --- |
| `全インターフェースに公開` | 使用を確認したプログラムのポートを、ホストの全インターフェースに公開 |
| `ループバックのみに公開` | 使用を確認したプログラムのポートを、ホスト自身から接続するアドレスだけに公開 |
| `待ち受け中 (未公開)` | 使用を確認したプログラムが、ホストにポートを公開せずに接続を待ち受けている |
| `高い権限で実行` | 使用を確認したプログラムが、下記の強い権限のいずれかを持つ |
| `最終確認` | 表示している観測を最後に確認した時刻 |

`高い権限で実行`は、次のいずれかに該当する場合に表示します。

- 特権モードのコンテナで実行
- システム管理やファイルアクセス制限の回避などに使える強い権限を持つ
- ホストとユーザー権限を分離していないrootのプロセスとして実行

公開範囲が分からず、権限の情報がある場合は、`権限:`の行に権限と最終確認を表示します。
どちらも表示できない場合は、`最終確認:`の行に時刻だけを表示します。

### 通知オフの表示 {#muted-display}

通知オフは、修正版がなく、7日以上使用が確認されないパッケージを個別に通知しない機能です。
この機能を有効にした場合に適用し、今すぐ対応やEOLのパッケージは対象にしません。

通知オフのパッケージは、チャンネル・スレッド・差分の個別カードから除き、件数で示します。
件数は非表示にしたカードに相当する数で、同じイメージ名とパッケージの組み合わせでも、版や修正状態が異なれば別件です。

次の例では、通知オフの1件が、稼働時の使用状況の「使用が確認されない1件」にも含まれています。

```text
🔇 通知オフ — 修正版がなく7日以上使用が確認されない: 1件
🔎 稼働時の使用状況: ▶ 使用中1件 · 使用が確認されない1件 · 判定できない0件
```

今回のスキャンで通知オフと判定したパッケージは、ほかの件数で次のように扱います。

- `優先度:`の件数と、現在の未解決の優先度件数から除外
- トリアージ無効時の現在の未解決の深刻度別件数から除外
- 稼働時の使用状況では「使用が確認されない」に含めるため、通知オフの件数と重複

スキャンに失敗すると、前回のスキャンの記録を使う場合があります。
その記録について今回の通知オフを判定できない場合は、現在の未解決の優先度件数に含めます。

スキャン失敗だけを理由に、通知再開の表示を出すことはありません。

通知を再開したパッケージには、次のように変化を表示します。

```text
変化: ↩️ 通知を再開 (使用中になった)
```

通知再開の理由と、それぞれの表示は次のとおりです。

| 再開の理由 | 表示 |
| --- | --- |
| パッケージの使用を確認した | `変化: ↩️ 通知を再開 (使用中になった)` |
| パッケージが今すぐ対応に該当する | `変化: ↩️ 通知を再開 (今すぐ対応)` |
| パッケージに修正版がある | `変化: ↩️ 通知を再開 (修正版あり)` |
| パッケージがサポート終了となった | `変化: ↩️ 通知を再開 (サポート終了(EOL)となった)` |
| 使用状況を判定できないか、必要な観測期間に満たない | `変化: ↩️ 通知を再開 (観測不足)` |
| パッケージの修正状態が通知オフの対象から外れた | `変化: ↩️ 通知を再開 (対象外の状態)` |

通知を再開したパッケージに修正版の公開や優先度の上昇などもある場合、KestreLynxは[その変化の表示](#package-change-labels)を優先します。

通知オフの条件と再開理由は[修正版がない所見の通知オフ](runtime-usage.md#muting-findings-without-a-fix)を参照してください。

## 警告の読み方 {#warnings}

警告は、脆弱性の確認や優先度の判定、稼働時の観測で利用できなかった情報を知らせます。
種類ごとの対象と表示場所を次に示します。

| 種類 | 何を知らせるか | 出る場所 |
| --- | --- | --- |
| [スキャン](#scan-warnings) | 脆弱性を確認できなかったイメージや本体 | 全体レポートの後半、または差分レポートの末尾 |
| [脅威情報](#intel-warnings) | 優先度の判定に使う情報の不足や古さ | 情報源の警告は所見の前、古さの注記は全体レポートの後半 |
| [Sensor](#sensor-warnings) | 稼働時の使用状況を観測する機能の問題 | チャンネル通知のヘッダーの直後 |

### スキャンの警告 {#scan-warnings}

スキャンの警告は、イメージの脆弱性やNode.js・Python本体の脆弱性を確認できなかったことを知らせます。
スキャンできなかったイメージがある場合は、次のように表示します。

```text
⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
```

表示ごとの意味を次に示します。

| 表示 | 意味 |
| --- | --- |
| `⚠️ スキャンできなかったイメージ N件（脆弱性は確認できていない）` | スキャンやイメージの一致確認に失敗 |
| `⏳ 今回は未確認、前回の所見を保持 — イメージ名一覧` | 稼働中のイメージを確認できず、前回の所見を保持 |
| `ℹ️ Node.js の脆弱性情報を取得できなかったため、N 件のイメージの本体を照合していません。` | 脆弱性情報を利用できず、本体の照合を見送り |

スキャンできなかったイメージの件数と確認先は、次のとおりです。

- Nはスキャンに失敗したイメージ名を重複なく数えた件数
- 原因と対象のイメージは、[スキャンできなかったイメージの表示](#scan-failure-causes)で確認

前回の所見を保持する注記は、Kubernetesで動いているイメージのdigest（内容を識別する値）を確認できなかった場合に表示します。
イメージ名によるスキャンに成功しても、稼働中のイメージと同じ内容を調べたと確認できないため、前回の所見があれば残します。

この保持の注記には、次の決まりがあります。

- 前回の所見がなくても、今回は確認できなかったことを示すために表示
- 同じイメージ名のスキャンがすべて失敗した場合は、この一覧には含めず、スキャン失敗の警告に表示
- イメージ名によるスキャンかどうかは、Webhookの[イメージの識別情報](webhook-reference.md#image-identity)の`identity_resolved`と`scan_target_kind`で確認

一覧にないイメージでも、スキャン失敗によって前回の所見を保持している場合があります。
保持する結果の扱いは[スキャン失敗時の扱い](scan-logic.md#scan-failures)を参照してください。

本体を照合しなかった注記は、照合を見送った対象を次のように示します。

- 名前は対象に応じて`Node.js`または`Python runtime`、両方なら`Node.js・Python runtime`
- Nは照合しなかったイメージ名を重複なく数えた件数

照合を見送る条件と前回の所見の扱いは、[言語ランタイムのセキュリティ情報の利用不能時の扱い](scan-logic.md#node-runtime-unavailable)を参照してください。

#### スキャンできなかったイメージの表示 {#scan-failure-causes}

スキャンできなかったイメージは、原因の行の下に、そのイメージを使うワークロードとイメージ名を表示します。
次の例は、ワークロードが分からず、イメージ名だけを表示する場合です。

```text
⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
• 原因を分類できなかった（詳細はログ）
  • broken:1
```

ワークロードは、そのイメージを使って動くアプリケーションや処理の単位です。
表示は次のようにまとめます。

- 同じ原因のイメージをまとめ、レジストリに関する原因は取得元ごとに分ける
- 原因の行の下に、ワークロードとイメージ名を「 — 」で区切って並べる
- 同じイメージを複数のワークロードが使う場合は、ワークロードごとに1行ずつ表示
- ワークロードが分からないイメージは、同じ原因・取得元のまとまりの最後にイメージ名だけを表示

ワークロードは、実行環境に応じて次の形で表示します。

| 実行環境 | ワークロードの表記 |
| --- | --- |
| Kubernetes | 種類 名前空間/名前 |
| Compose | Compose プロジェクト/サービス |
| コンテナ名が分かる場合 | コンテナ 名前 |

原因の表示と、その表示になる場合を次に示します。
表中の「ホスト」は取得元のレジストリを指し、ローカルレジストリはKestreLynxが動く環境から見てlocalhostなどの自分自身を指すアドレスにあるレジストリです。

| 原因の表示 | この表示になる場合 |
| --- | --- |
| `ローカルレジストリ（ホスト）のイメージは KestreLynx から取得できない` | ローカルレジストリへの接続に失敗した場合 |
| `レジストリ（ホスト）のログイン情報が無い、または違うため、イメージを取得できない` | 認証の要求やアクセス拒否などで取得できない場合 |
| `レジストリ（ホスト）にイメージが見つからない` | 取得先がイメージの不在を示した場合 |
| `レジストリ（ホスト）の取得回数の制限にかかり、イメージを取得できなかった` | 取得先がリクエスト数の上限を理由に拒否した場合 |
| `レジストリ（ホスト）に接続できず、イメージを取得できなかった` | ローカル以外のレジストリに、接続拒否やタイムアウトなどで接続できない場合 |
| `脆弱性データベースを取得できなかった` | 脆弱性データベースの取得や初期化に失敗した場合 |
| `スキャンしたイメージが、動いているイメージと一致しなかった` | digestやOS・CPUの種類が稼働中のイメージと一致しない、または一致を確認できない場合 |
| `原因を分類できなかった（詳細はログ）` | 原因を分類できないか、レジストリのホストが分からない場合 |

エラーが複数の原因に当てはまる場合は、次の順で優先します。
レジストリに関する原因は、レジストリからイメージを取得するスキャンで判定します。

1. 脆弱性データベースのエラー
2. 認証のエラー
3. イメージの不在
4. 取得回数の制限
5. 接続の失敗

エラー文そのものは、ログとWebhookの[`scan_errors`](webhook-reference.md#scan-errors)で確認できます。

### 脅威情報の警告 {#intel-warnings}

脅威情報の警告は、優先度の判定に使うKEVやEPSSの情報が利用できないことや、保存済みの古い情報を使っていることを知らせます。
両方の情報を利用できない場合は、次の警告を表示します。

```text
⚠️ 脅威情報 (KEV/EPSS) が利用できない — 深刻度のみで優先度を判定、低優先度への引き下げなし
```

表示ごとの意味を次に示します。

| 表示 | 意味 |
| --- | --- |
| `⚠️ 脅威情報 (KEV/EPSS) が利用できない — 深刻度のみで優先度を判定、低優先度への引き下げなし` | KEVとEPSSの両方を利用できない |
| `⚠️ CISA KEVデータが利用できない — 今すぐ対応の検出に漏れの可能性あり` | KEVを利用できず、EPSSと深刻度で判定 |
| `⚠️ EPSSデータが利用できない — KEVと深刻度のみで優先度を判定` | EPSSを利用できず、KEVと深刻度で判定 |
| `脅威情報はN日前のもの (配信元に接続できない)` | トリアージ有効時に、使ったデータが1日以上前のもの |

古さを知らせる注記については、次のように読みます。

- 取得に失敗した場合は、取得から7日以内の保存済みデータで優先度を判定
- Nは、使ったデータのうち最も古いものを取得してからの日数
- 片方の情報を利用できず、もう片方に古いデータを使う場合は、情報源の警告と古さの注記の両方が出ることがある
- 両方の情報を利用できない場合は、古さの注記を出さず、両方を利用できない警告を表示

表示位置は[全体レポートの並び順](#current-order)、判定への影響は[脅威情報を利用できない場合](scan-logic.md#degraded-triage)を参照してください。

### Sensorの警告 {#sensor-warnings}

Sensorの警告は、稼働時の使用状況を観測する機能や、その観測結果に問題があることを知らせます。
チャンネル通知では、日時・イメージ件数・レポートの種類を示すヘッダーの直後に表示します。

Sensorから観測結果が届いていない場合は、次のように表示します。

```text
⚠️ 稼働時の証拠が利用できない: Sensorからの報告がまだない
```

この警告に続く理由の意味を次に示します。
「証拠ファイル」はSensorが観測結果を保存したファイル、「サンドボックス」はSensorによる読み取り以外の操作を制限する仕組みです。

| 理由の表示 | 意味 |
| --- | --- |
| `Sensorからの報告がまだない` | Sensorの観測結果を保存したファイルがまだない |
| `証拠ファイルの検証失敗` | KestreLynxが観測結果のファイルを読み取れないか、内容の検証を通らない |
| `Sensorの最終報告が古い` | Sensorの最後の報告から時間が経ち、観測結果の新しさを確認できない |
| `Sensorの読み取りが拒否されている` | Sensorがコンテナのプロセス情報などを読み取る権限を利用できない |
| `Sensorのサンドボックス起動失敗` | 操作の制限を確認できず、Sensorが観測を始めていない |
| `Sensorのサンドボックスが一部制限の効かない状態で稼働中` | Sensorによる操作の制限が一部効いていない |
| `Sensorの一部機能が利用できない` | 処理の停滞などにより、観測や結果の保存に支障がある |

Sensorは、定期的な確認に加えて、eBPFというカーネルの機能でプログラムの実行などを観測します。
Sensorの状態が正常でも、このイベント観測を利用できない場合は、次のように表示します。

```text
⚠️ 短命なプログラムは観測できない (eBPFが利用できない: BTFなし); サンプリングのみ使用
```

`サンプリングのみ使用`は、定期的な確認だけで観測するため、短い時間だけ動くプログラムを見逃すことがあるという意味です。

eBPFを利用できない理由の意味を次に示します。

| 理由の表示 | 意味 |
| --- | --- |
| `カーネルが未対応` | カーネルがイベント観測に対応していない |
| `BTFなし` | イベント観測に必要な、カーネルの型情報を読み取れない |
| `権限不足` | eBPFによる観測に必要な権限を利用できない |
| `アタッチ失敗` | イベント観測の準備や開始に失敗した |
| `cgroup v1` | ホストのコンテナ管理の仕組みが、観測に必要なcgroup v2ではない |
| `不明` | イベント観測を利用できない理由を分類できない |

警告中も、`▶ 使用中`は確認できた使用を示します。
使用が確認されない場合や判定できない場合は、未使用とは判断できません。

各パッケージの表示は[使用状況のラベル](#usage-labels)、観測の仕組みと限界は[稼働時の使用状況](runtime-usage.md)を参照してください。
