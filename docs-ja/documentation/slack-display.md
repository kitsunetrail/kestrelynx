# Slackのレポートの構成と件数

Slackに届くレポートの読み方を4ページで説明し、このページではレポートの確認場所・通知の言語・区分の並び順・件数の読み方を扱います。

パッケージごとの表示、使用状況、警告は、次のページを参照してください。

| 内容 | ページ |
| --- | --- |
| パッケージ1件ごとの表示と前回からの変化の表示 | [Slackのパッケージカードと変化の表示](slack-package-display.md) |
| Sensorを使う場合の使用状況の表示 | [Slackの稼働時の使用状況の表示](slack-runtime-display.md) |
| 警告 | [Slackの警告の読み方](slack-warnings-display.md) |

## レポートの確認場所 {#slack-display}

Slackでは、チャンネルの通知から変化や未解決状態を確認し、Botのスレッドから詳細を確認できます。
修正計画の表示は[Slackの修正計画](remediation-results.md#reading-results-in-slack-and-webhooks)を参照してください。

### チャンネルのレポート {#channel-display}

チャンネルに表示するレポートの見出しと内容を次に示します。

| レポート | 見出しの表示 | 表示する内容 |
| --- | --- | --- |
| `diff`モード（変化あり） | `前回のスキャンからの変化` | 前回からの変化と現在の未解決状態 |
| `diff`モード（変化なし） | `前回のスキャンから変化なし` | 変化がないことと現在の未解決状態 |
| `full`モード | `未解決の所見の全体` | 最新のスキャンで確認した未解決の所見 |
| 週次レポート | `📋 週次全体レポート — 未解決の所見の全体` | 差分通知に加える、最新のスキャンで確認した未解決の所見の全体 |

`未解決の所見の全体`を見出しとする`full`モードの通知と、週次レポートで差分通知に加わる`📋 週次全体レポート — 未解決の所見の全体`の部分を、全体レポートと呼びます。

表示には次の共通の決まりを適用します。

- 空の区分は表示しない
- トリアージ有効時の低優先度は、全体レポートでも件数だけを表示

汎用Webhookを設定している場合だけ、次の案内を表示します。

| 表示 | 表示する場所 | 条件 |
| --- | --- | --- |
| `詳細は汎用Webhookのペイロードに記載` | diffモード（週次レポートを除く）の現在の未解決の行の下 | 最新のスキャンのレポートに所見がある場合 |
| `詳細は汎用Webhookのペイロードに記載` | fullモードと週次レポートの低優先度の件数の行の下 | トリアージ有効時に低優先度の項目がある場合 |
| `低リスクの修正N件を集約 — 全件は汎用Webhookのペイロードに記載` | fullモードと週次レポート | トリアージ無効時に低リスクの修正をまとめた場合 |

低優先度の全件の詳細は[汎用Webhook](webhook-reference.md#generic-webhook)で確認できます。

通知の送信タイミングは[スキャン通知の送信条件](notification-conditions.md#notification-conditions)を参照してください。

### スレッドのレポート {#thread-display}

Botのスレッドは、`📊 未解決の所見の全体 — 日時`の見出しで、そのレポート時点の詳細を表示します。

チャンネル本文1通目の末尾には、次の案内を表示します。

| チャンネル本文1通目の末尾 | 確認先 |
| --- | --- |
| `📊 未解決の所見の全体はこのメッセージのスレッド ↓` | 最新のスキャンのレポートを投稿したスレッド |
| `🔗 前回のレポート時点の未解決の所見の全体 → スレッド` | 前回投稿したレポートのスレッド |

有効なリンクがない場合やリンクを表示できない場合は、末尾の案内を省略します。

スレッドの投稿と確認には、次の決まりを適用します。

- チャンネル本文が複数のメッセージに分かれても、スレッドは1通目に付く
- 前回のレポートへのリンク先は、そのレポートを作成した時点の内容
- 最新のスキャン後の未解決状態は、チャンネルの[現在の未解決件数](#open-now)で確認する

長い通知は複数のメッセージに分割し、続きには次の表示を付けます。

| 分かれたメッセージ | 付く表示 |
| --- | --- |
| スレッドの続き | 見出しに`(続き)` |
| チャンネルの続き | `(続き 2/3)`のような表示 |

未解決の所見の全体を返信として投稿する条件は[Slackスレッドの投稿条件](notification-conditions.md#slack-thread-delivery)を参照してください。

## 通知の言語 {#notification-language}

Slackの定型文は、設定した通知言語で表示します。
言語の設定値と適用範囲は[設定](configuration.md)を参照してください。

日本語の通知でも、深刻度（`CRITICAL`・`HIGH`など）、脆弱性の説明文、議論リンクのラベルは元の英語のまま表示します。

## 区分の並び順 {#section-order}

レポートの種類によって、変化を先に示す場合と、現在の未解決項目を区分別に示す場合があります。

### 差分レポートの並び順 {#diff-order}

次の例は、変化がある回の差分レポートです。

```text
🛡️ KestreLynx — 2026-06-24 09:00のスキャン結果
イメージ3件をスキャン、2件に影響あり
前回のスキャンからの変化

🆕 前回のスキャンからの新規検出 (4件)
イメージ: api:2.0
◆ libxml2
…

✅ 前回のスキャンからの解消 (1件)
• web:1.0: old-pkg

⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
• 原因を分類できなかった（詳細はログ）
…

📌 現在の未解決: 🚨 今すぐ対応3件 / 👀 要監視1件 / 🔕 低優先度3件
⏰ 今すぐ対応/要監視の未解決の最長期間20日
📊 未解決の所見の全体はこのメッセージのスレッド ↓
```

変化がある回と週次レポートでは、次の順に表示します。
該当する内容がない区分は省略します。

| 順序 | 内容 | 見出しの表示 |
| --- | --- | --- |
| 先頭 | ヘッダー、イメージ件数、Sensorの警告 | `🛡️ KestreLynx — 日時のスキャン結果`など |
| 変化の前 | 脅威情報源を利用できない警告 | `⚠️ EPSSデータが利用できない — KEVと深刻度のみで優先度を判定`など |
| イメージの変化 | digestの変更、イメージ名の更新 | `🔄 イメージの内容が変化 (N件)`など |
| EOLの変化 | 新規EOLのベースOS、EOLパッケージの変化 | `⛔ 新規: ベースOSのサポート終了(EOL) (最優先)`など |
| パッケージの変化 | 通常の新規検出・変化、解消・EOL解除 | `🆕 前回のスキャンからの新規検出 (N件)`、`✅ 前回のスキャンからの解消 (N件)` |
| 末尾 | 週次の全体レポート、またはスキャン失敗と現在の未解決状態 | `📋 週次全体レポート — 未解決の所見の全体`、`⚠️ スキャンできなかったイメージ N件（脆弱性は確認できていない）`など |

週次レポートではない変化なしの通知は、`前回のスキャンから変化なし`に続けて、スキャン失敗や現在の未解決状態を表示します。
保持の注釈は、未解決状態や全体レポートの後に付きます。

トリアージ有効時の通常の新規検出・変化は、優先度、イメージ名、パッケージ名の順です。

### 全体レポートの並び順 {#current-order}

次の例は、トリアージ有効時の全体レポートです。

```text
未解決の所見の全体
優先度: ⛔ EOLのベースOS1件 · 🚨 今すぐ対応3件 · 👀 要監視1件 · 🔕 低優先度4件

⛔ ベースOSのサポート終了(EOL) (最優先)
イメージ: web:1.0
状態: ベースOSがEOL (今後のセキュリティ更新なし)

🚨 今すぐ対応 (3件) — 悪用あり、または悪用の可能性が高い
◆ openssl
…

👀 要監視 (1件) — 緊急性は低いが継続監視
◆ e2fsprogs
…

🔕 低優先度 (4件) — イメージ2件で所見4件、悪用の兆候なし (KEV未掲載、EPSSはしきい値未満)

⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
…
📊 未解決の所見の全体はこのメッセージのスレッド ↓
```

トリアージ有効時は、チャンネルに次の見出しと順序で未解決項目を表示します。
Botのスレッドも同じ区分順です。

| 順序 | 見出しの表示 |
| --- | --- |
| 先頭 | `⛔ ベースOSのサポート終了(EOL) (最優先)` |
| 続き | `⛔ パッケージのサポート終了(EOL) (N件) — …` |
| 優先度順 | `🚨 今すぐ対応 (N件) — …` → `👀 要監視 (N件) — …` → `🔕 低優先度 (N件) — …` |

CISA KEVやEPSSの脅威情報源を利用できない警告は、`full`モードでは`優先度:`の行の直後、EOL区分より前に表示します。
週次レポートでは、この警告を通知冒頭のヘッダー（ヘッダー行・イメージ件数・Sensorの警告）の直後に1回だけ表示し、後ろの`📋 週次全体レポート — 未解決の所見の全体`の部分では`優先度:`の後に表示しません。

トリアージ有効時のチャンネルの全体レポートでは、EOL・今すぐ対応・要監視の区分の後に、該当する行だけを次の順に表示します。

| 順序 | 表示 |
| --- | --- |
| 1 | `🔕 低優先度 (N件) — …` |
| 2 | `🔇 通知オフ — 修正版がなく7日以上使用が確認されない: N件` |
| 3 | `⚠️ スキャンできなかったイメージ N件（脆弱性は確認できていない）` |
| 4 | `脅威情報はN日前のもの (配信元に接続できない)` |
| 5 | `🔎 稼働時の使用状況: ▶ 使用中N件 · …` |

KestreLynxはKEVやEPSSのデータの取得に失敗すると、取得から7日以内の保存済みデータで優先度を判定します。
トリアージ有効時は、使ったデータが1日以上前のものなら、`脅威情報はN日前のもの (配信元に接続できない)`と表示します。
`N`は、使ったデータのうち最も古いものを取得してからの日数です。
どちらのデータも使えない場合は、この注記の代わりに、脅威情報源を利用できない警告を前述の位置に表示します。

### トリアージ無効時の並び順 {#triage-disabled-display}

次の例は、トリアージ無効時の全体レポートです。

```text
未解決の所見の全体
優先度: 🔴 CRITICAL 3件 · 🟠 要注意1件 · 🟢 安全1件

✅ 今すぐ対応可能 (fixed)
◆ openssl
…

ℹ️ 修正版なし (affected / 上流の対応待ち)
◆ e2fsprogs
…

🔕 このOSリリースでは修正予定なし (will_not_fix)
◆ gcc-12-base
…

⚠️ スキャンできなかったイメージ 1件（脆弱性は確認できていない）
…
低リスクの修正1件を集約
📊 未解決の所見の全体はこのメッセージのスレッド ↓
```

トリアージ無効時は、EOL区分に続いて、修正状態別に表示します。

| 順序 | 表示する区分 |
| --- | --- |
| 修正版あり | `✅ 今すぐ対応可能 (fixed)` |
| 修正版なし | `ℹ️ 修正版なし (affected / 上流の対応待ち)` |
| 修正予定なし | `🔕 このOSリリースでは修正予定なし (will_not_fix)` |

`今すぐ対応可能`は修正版がある区分で、トリアージの`今すぐ対応`とは意味が異なります。
修正状態の意味は[修正状態](scan-logic.md#status)を参照してください。

チャンネルでは、修正版ありのうち注意が必要な項目を個別に表示し、残りをイメージごとにまとめます。

### 区分の中の並び順 {#within-section-order}

全体レポートとスレッドでは、トリアージの有効・無効にかかわらず、各区分の中のイメージと各イメージの中のパッケージを次の基本の順で並べます。
イメージ同士・パッケージ同士を2つずつ比べ、前の条件で差がつかないときだけ次の条件で比べます。

イメージは次の順で比べます。

1. CRITICALの件数が多いほうが先
2. HIGHを含むほうが先
3. すべての深刻度を合わせたCVEの件数（合計）が多いほうが先
4. イメージ名の順

各イメージの中のパッケージは次の順で比べます。

1. CRITICALを含むもの → HIGHを含むもの → それ以外の順
2. すべての深刻度を合わせたCVEの件数（合計）が多いほうが先
3. パッケージ名の順

次の例は、Sensorによる並べ替え前の、1つの区分に含まれるイメージ4件の順です。

| 順 | イメージ | CRITICAL | HIGH | MEDIUM以下 | 合計 | 先になった理由 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `api:2.0` | 2 | 0 | 0 | 2 | CRITICALが最多 |
| 2 | `web:1.0` | 1 | 1 | 0 | 2 | 残る3件で唯一HIGHあり |
| 3 | `worker:1.0` | 1 | 0 | 4 | 5 | batchより合計が多い |
| 4 | `batch:1.0` | 1 | 0 | 2 | 3 | — |

トリアージ有効時にSensorの情報がある場合は、同じ優先度の区分内で次の条件を基本の順より先に適用し、差がないものは基本の順を保ちます。

イメージは次の順で比べます。

1. 使用中のパッケージを含むほうが先
2. 基本の順

各イメージの中のパッケージは次の順で比べます。

1. 使用中のほうが先
2. 使用中同士は、ポートの公開範囲が広いほうが先
    - 全インターフェースに公開
    - ループバックのみに公開
    - 待ち受け中 (未公開)
3. 高い権限で実行しているほうが先
4. 基本の順

使用中でないもの同士は、基本の順のままです。

`▶ 使用中`は、Sensorが稼働中のコンテナでパッケージの実行や読み込みなどを確認した状態を示します（詳しくは[使用状況のラベル](slack-runtime-display.md#usage-labels)）。
公開範囲と権限はそのパッケージを使っているコンテナのもので、表示は[観測根拠の表示](slack-runtime-display.md#runtime-evidence)で確認できます。
この並べ替えで優先度の区分をまたいで動かすことはなく、トリアージ無効時は適用しません。

## 件数の読み方 {#counts}

イメージ、パッケージ、CVEでは集計単位が異なります。
同じ通知内でも、件数が一致するとは限りません。

件数は深刻度ごとに分け、認識できない深刻度は`UNKNOWN`として数えます。
`MEDIUM`・`LOW`・`UNKNOWN`の件数は、`scan.severity`にそれぞれの深刻度を含めた場合だけ表示します。
既定の`[HIGH, CRITICAL]`では、これらの深刻度は検出対象外のため、件数を表示しません。
パッケージカードの「検出件数」、イメージの見出し、まとめて表示する行、トリアージ無効時の現在の未解決の行では、0でない件数を`HIGH`の後に`MEDIUM`・`LOW`・`UNKNOWN`の順で追加します（例: `CRITICAL 1 / HIGH 2 / MEDIUM 3`）。

### イメージ件数 {#image-counts}

ヘッダーの`イメージN件をスキャン、M件に影響あり`は、次の単位で数えます。

| 表示 | 英語 | 集計単位 |
| --- | --- | --- |
| スキャンした件数 | images scanned | 失敗を含む、イメージ名・digest・必要な場合のプラットフォームの組み合わせ |
| 影響ありの件数 | affected | 対象の脆弱性またはEOLのベースOSがあるイメージ名 |

registry digestで識別する場合は、同じイメージ名・digestでもOS・アーキテクチャが異なれば別件として数えます。
別のイメージ名が同じスキャン結果を共有していても、スキャンした件数では別件として数えます。
スキャン失敗だけのイメージ名は、影響ありの件数には含めません。

### 現在の未解決件数 {#open-now}

`📌 現在の未解決:`は、最新のスキャン後に残っている未解決の件数を示します。
トリアージ有効時は、次のように表示します。

```text
📌 現在の未解決: ⛔ EOLのベースOS2件 / ⛔ EOLのパッケージ4件 / 🚨 今すぐ対応2件 / 👀 要監視1件 / 🔕 低優先度1件
```

EOLのベースOSはイメージ名1つを1件、それ以外はイメージ名とパッケージの組み合わせ1つを1件として数えます。
0件の項目は表示しません。

各項目では、次のものを数えます。

| 表示 | 数えるもの |
| --- | --- |
| `⛔ EOLのベースOSN件` | ベースOSがEOLと記録されたイメージ |
| `⛔ EOLのパッケージN件` | EOLの検出結果がある組み合わせ |
| `🚨 今すぐ対応N件` | 今すぐ対応の組み合わせ |
| `👀 要監視N件`・`🔕 低優先度N件` | 要監視・低優先度の組み合わせ |

数え方には、次の決まりがあります。

- イメージのベースOSがEOLの場合は、次のように数える
    - そのイメージを`⛔ EOLのベースOSN件`に1件として数える
    - そのイメージで見つかったEOLのパッケージは、`⛔ EOLのパッケージN件`には数えない
- 優先度の件数では、同じイメージ名とパッケージの組み合わせを1回だけ数える
- 通常の検出結果とEOLの検出結果のどちらかが今すぐ対応なら、今すぐ対応に数える
- 今すぐ対応でない組み合わせは、通常の検出結果の優先度に従って要監視・低優先度に数える
- 検出結果がEOLだけで、優先度が要監視・低優先度の場合は、その組み合わせを優先度の件数に数えない
- EOLのパッケージに数えた組み合わせが今すぐ対応なら、今すぐ対応にも数える
- [通知オフ](slack-runtime-display.md#muted-display)の組み合わせは、優先度の件数に数えない

EOLと優先度の件数は保存している履歴から数えるため、スキャンに失敗したイメージなどの前回の記録も含みます（[保持中の履歴](diff-logic.md#retained-findings)）。
通常の検出結果とEOLの検出結果の区別は、[パッケージのEOL](scan-logic.md#eol-package)を参照してください。

トリアージ無効時は、次のように表示します。

```text
📌 現在の未解決: ⛔ EOLのベースOS1件 / CRITICAL 3件 / HIGH 6件、イメージ2件
```

トリアージ無効時の件数は、次のように数えます。

- EOLの項目は、トリアージ有効時と同じ数え方
- 深刻度別の件数は、最新のスキャンのレポートのパッケージごとのCVE件数を深刻度ごとに合計
- 同じCVEが別のパッケージにあれば、それぞれに数える
- イメージの件数は、所見のあるイメージの数
- `scan.severity`に含めた場合は、`HIGH`の後に`MEDIUM`・`LOW`・`UNKNOWN`の0でない件数を順に表示

最新のスキャンのレポートに検出項目がない場合は、件数の代わりに次の状態を表示します。

| 状態 | 表示 |
| --- | --- |
| Kubernetesでdigestを確認できずパッケージ履歴を保持 | `📌 現在の未解決: 未確認 — 再確認まで前回の所見を保持` |
| 上記以外で前回の履歴を保持 | `📌 現在の未解決: 未再スキャン — 次のスキャン成功まで前回の所見を保持` |
| 保持中の履歴もなし | `🎉 現在の未解決: なし — 問題なし` |

### 優先度の行の件数 {#priority-counts}

全体レポートの`優先度:`は、最新のスキャンのレポートに含まれるEOLや対応の優先度を件数で示します。
トリアージ有効時は、次のように表示します。

```text
優先度: ⛔ EOLのベースOS1件 · 🚨 今すぐ対応3件 · 👀 要監視1件 · 🔕 低優先度4件
```

`優先度:`の行では、パッケージをカード1枚に当たる単位で数えます。
低優先度など、カードを個別に表示しない場合も、同じ単位で数えます。

同じイメージの同じパッケージで見つかったCVEを、修正状態ごとに1枚のカードにまとめます。
api:2.0のopensslを例に、カードの枚数と件数を示します。

| 検出結果 | カードの枚数 | 件数 |
| --- | --- | --- |
| 修正版のあるCVEが3つ | 1枚 | 1件 |
| 修正版のあるCVEが2つ、修正版のないCVEが1つ | 修正状態が違うため2枚 | 2件 |

同じパッケージ名でも、エコシステムやインストールされている版が違えば別のカードになります。
詳しくは[パッケージカードの読み方](slack-package-display.md#package-card)を参照してください。

同じイメージ名でもdigestが異なれば、分けて数えます。
EOLのベースOSだけは、イメージ名1つを1件として数えます。

トリアージ有効時の各項目では、次のものを数えます。
0件の項目は表示しません。

| 表示 | 数えるもの |
| --- | --- |
| `⛔ EOLのベースOSN件` | ベースOSがEOLと判定されたイメージ |
| `⛔ EOLのパッケージN件` | EOLの検出結果があるカード |
| `🚨 今すぐ対応N件` | 今すぐ対応のカード（EOLの検出結果で今すぐ対応のものも含む） |
| `👀 要監視N件`・`🔕 低優先度N件` | 通常の検出結果のカード（要監視・低優先度） |

EOLと通知オフには、次の決まりがあります。

- イメージのベースOSがEOLの場合は、そのイメージのEOLパッケージをEOLのパッケージの件数には数えない
- EOLパッケージが今すぐ対応なら、ベースOSのEOLにかかわらず今すぐ対応にも数える
- [通知オフ](slack-runtime-display.md#muted-display)のカードは、優先度の件数に数えない

トリアージ無効時は、次のように表示します。

```text
優先度: 🔴 CRITICAL 3件 · 🟠 要注意1件 · 🟢 安全1件
```

EOLの件数はトリアージ有効時と同じ対象で数え、それ以外は次のように数えます。

| 表示 | 数えるもの |
| --- | --- |
| `🔴 CRITICAL N件` | 通知オフを除くCRITICALのCVE件数 |
| `🟠 要注意N件` | 修正版への更新でメジャーバージョンが上がるカード |
| `🟢 安全N件` | 修正版があり、CRITICALもメジャー更新もないカード |

CRITICALと安全の件数には、次の決まりがあります。

- CRITICALは、修正版あり・修正版なし・修正予定なし・EOLパッケージの各区分の件数を合計
- 安全には、更新の注意度が分からないカードも含める

安全という分類は、更新の安全性や互換性を保証するものではありません。
表示の意味は[更新の注意度](slack-package-display.md#upgrade-risk)も参照してください。

トリアージ有効時の今すぐ対応・要監視・低優先度について、[現在の未解決の行](#open-now)との数え方の違いを示します。

| 行 | 元にするもの | 1件の単位 |
| --- | --- | --- |
| 優先度の行 | 最新のスキャンのレポート | 修正状態ごとに分けたカード |
| 現在の未解決の行 | 保存している履歴 | イメージ名とパッケージの組み合わせ |

### 未解決の経過日数 {#unresolved-age}

未解決の経過日数は、チャンネルでは対象全体の最長期間、スレッドのカードではそのイメージ名とパッケージの組み合わせの期間を示します。

表示する場所と日数による違いを次に示します。
表のNには経過日数が入ります。

| 場所・条件 | 表示 | 意味 |
| --- | --- | --- |
| チャンネル・トリアージ有効・1〜13日 | `今すぐ対応/要監視の未解決の最長期間N日` | EOLも含めた対象全体の最長期間 |
| チャンネル・トリアージ無効・1〜13日 | `未解決の最長期間N日` | すべての優先度を含む最長期間 |
| チャンネル・トリアージ有効・14日以上 | `⏰ 今すぐ対応/要監視の未解決の最長期間N日` | 長期間未解決であることを示す表示 |
| チャンネル・トリアージ無効・14日以上 | `⏰ 未解決の最長期間N日` | 長期間未解決であることを示す表示 |
| スレッドのカード・1日以上 | `⏱ 未解決N日 · 初回検出2026-06-04` | その組み合わせの経過日数と初回検出日 |
| スレッドのカード・0日 | `⏱ 本日初検出` | 初回検出から1日未満の表示 |

チャンネルの最長期間は、対象となる履歴の最も古い初回検出日時から数えます。
1日以上で表示し、14日以上で`⏰`を付けます。

最長期間の対象は、トリアージの設定によって異なります。

| トリアージ | 最長期間の対象 |
| --- | --- |
| 有効 | 通常の今すぐ対応・要監視の検出結果と、EOLのベースOS・パッケージ |
| 無効 | 通常のすべての検出結果と、EOLのベースOS・パッケージ |

EOLや履歴の扱いには、次の決まりがあります。

- イメージのベースOSがEOLの場合は、EOLのパッケージの期間をベースOSの初回EOL検出日で数える
- EOLのパッケージが今すぐ対応の場合は、ベースOSのEOLにかかわらず、パッケージ自身の初回EOL検出日を対象に含める
- イメージのベースOSがEOLでない場合は、EOLのパッケージ自身の初回EOL検出日で数える
- スキャン失敗などで[保持している履歴](diff-logic.md#retained-findings)も対象に含める
- トリアージ有効時は、最新のスキャンで[通知オフ](slack-runtime-display.md#muted-display)と判定した通常の検出結果を対象から除く

スレッドのカードは、通常の検出結果ならその初回検出日、EOLの検出結果なら初回EOL検出日から数えます。
初回検出日の記録がないカードでは、期間を表示しません。

汎用Webhookは低優先度や通知オフも含めるため、Slackのトリアージ有効時とは集計対象が異なります（[未解決の最長期間](webhook-diff-reference.md#oldest-open-days)）。
