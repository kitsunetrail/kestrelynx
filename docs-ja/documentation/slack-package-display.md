# Slackのパッケージカードと変化の表示

このページでは、パッケージカードの各部分の読み方と、差分レポートに出る変化の表示を説明します。
レポート全体の構成と件数は[Slackのレポートの構成と件数](slack-display.md)を参照してください。

## パッケージカードの読み方 {#package-card}

パッケージカードは、パッケージ名に続けて、現在の版・修正版・検出件数などを表示します。
チャンネルの今すぐ対応では、次の詳細カードを使います。

```text
◆ openssl
現在: 3.0.7
修正版: 3.0.11
更新の注意度: 🟢 ディストリのセキュリティパッチ
検出件数: CRITICAL 1 / HIGH 0
CVE:
• CVE-2031-0001 · CRITICAL · EPSS 94% · CISA KEV (実際の攻撃で悪用あり) · 🧨 ランサムウェア攻撃 · openssl: buffer overread · ベンダーのアドバイザリ
```

チャンネルの要監視では、次の簡略カードを使います。

```text
◆ e2fsprogs
現在: 1.47.0-2 · 修正版: なし
検出件数: CRITICAL 1 / HIGH 0
CVE: CVE-2031-0003 (EPSS 3%)
```

カードの使い分けを次に示します。
チャンネルの全体レポートには、週次レポートに加わる全体レポートも含みます。

表の「注意が必要な修正版あり」は、CRITICALを含むかメジャー更新が必要なパッケージを指します。

| 場所 | 詳細カード | 簡略カード | カードなし（件数やまとめ） |
| --- | --- | --- | --- |
| チャンネルの全体レポート（トリアージ有効） | 今すぐ対応 | 要監視・EOL | 低優先度 |
| チャンネルの全体レポート（トリアージ無効） | — | 注意が必要な修正版あり・修正版なし・修正予定なし・EOL | それ以外の修正版あり |
| スレッド（トリアージ有効） | 今すぐ対応・要監視・EOL | EOL区分の参照案内 | 低優先度 |
| スレッド（トリアージ無効） | すべての修正状態 | — | — |
| チャンネルの差分 | トリアージ有効時の今すぐ対応 | それ以外の個別表示するパッケージ | — |

EOLと通知オフには、次の例外があります。

- ベースOSがEOLの場合は、そのイメージのEOLパッケージをベースOSの表示にまとめる
- トリアージが有効で、EOLのパッケージが今すぐ対応の場合は、今すぐ対応の区分に詳細カードを表示
- 全体レポートやスレッドのEOL区分に`詳細: 🚨 今すぐ対応を参照`がある場合は、そのパッケージの詳細を今すぐ対応の区分で確認する
- [通知オフ](slack-runtime-display.md#muted-display)のパッケージは、個別カードの対象外

各項目を表示する場合の書式を次に示します。
この比較は、チャンネルとスレッドのカードに共通です。

| 項目 | 詳細カード | 簡略カード |
| --- | --- | --- |
| 現在の版・修正版 | それぞれ別の行 | 同じ行 |
| 更新の注意度 | `更新の注意度:`の行 | 修正版の後の括弧内 |
| 検出件数 | 深刻度別のCVE件数 | 深刻度別のCVE件数 |
| 対応 | [カードの対応行](#base-image-wait) | [カードの対応行](#base-image-wait) |
| CVE | CVEごとに1行 | CVE IDを1行に並べる |
| 使用状況 | 観測根拠を含む表示 | 使用中の短い表示 |

`検出件数:`は、そのカードに含まれるCVE IDを重複なく数えた件数です。
カードを分ける単位は[優先度の行の件数](slack-display.md#priority-counts)、CVEの表示内容と並び順は[CVEの表示](#cve-details)を参照してください。

使用状況は、チャンネルでは使用中の情報を表示し、スレッドの詳細カードでは使用が確認されない場合や判定できない場合も表示します。
詳しくは[使用状況のラベル](slack-runtime-display.md#usage-labels)を参照してください。

修正版がない場合は`修正版: なし`と表示します。
詳細カードには、修正状態に応じて次の案内を添えます。

| 修正状態 | 表示 |
| --- | --- |
| 修正版なし | `修正版: なし — 緩和策を検討` |
| このOSリリースでは修正予定なし | `修正版: なし — このOSリリースでは修正予定なし、置き換えを検討` |

EOLのカードに添える案内は、[EOLの表示](#eol-display)を参照してください。

カードの前にあるイメージの見出しは、後に続くパッケージがどのイメージで見つかったかを示します。
次は、その見出しの例です。

```text
イメージ: api:2.0
```

同じイメージ名に複数のdigestがある場合は、短縮したdigestを付けて区別します。
必要に応じて、OS・CPUアーキテクチャも添えます。

### CVEの表示 {#cve-details}

カードに含まれるCVEを`CVE:`に並べ、詳細カードは1件1行、簡略カードは1行で示します。
詳細カードでは、`CVE:`の行の下に次のように並べます。

```text
CVE:
• CVE-2031-0001 · CRITICAL · EPSS 94% · CISA KEV (実際の攻撃で悪用あり) · 🧨 ランサムウェア攻撃 · openssl: buffer overread · ベンダーのアドバイザリ
• CVE-2031-0006 · HIGH · EPSS 20% · libxml2: use-after-free
```

各行の項目を左から順に示します。
情報がない項目は省略します。

| 項目 | 表示の例 | 意味 |
| --- | --- | --- |
| CVE ID | `CVE-2031-0001` | 脆弱性のIDで、リンク先はこの節の最後の表を参照 |
| 深刻度 | `CRITICAL` | CVEの深刻度 |
| EPSS | `EPSS 94%` | 悪用される可能性を示すスコア |
| KEV | `CISA KEV (実際の攻撃で悪用あり)` | CISA KEVに掲載され、実際の攻撃で悪用されている |
| ランサムウェア | `🧨 ランサムウェア攻撃` | ランサムウェア攻撃での悪用情報がある |
| 説明文 | `openssl: buffer overread` | Trivyの所見はTrivyの説明文、Node.js・Python本体の所見は各ランタイムの脆弱性情報を表示 |
| ベンダーの情報 | `ベンダーのアドバイザリ` | KEVの注記にあるベンダーやCISAの情報へのリンク |

詳細カードの`EPSS n/a`はスコアがないことを示し、非常に小さい値は`<0.1%`、非常に大きい値は`>99%`と表示します。

EPSS・KEV・ランサムウェアの情報は、トリアージが有効で、KEVまたはEPSSを利用できるときに表示します。
トリアージが有効で、KEVとEPSSのどちらも利用できないときは、`CVE:`の行にそのことを表示します。

```text
CVE: 深刻度のみ (脅威情報が利用できない)
• CVE-2031-0003 · CRITICAL · e2fsprogs: out-of-bounds write
```

簡略カードは、CVE IDを次のように1行に並べます。

```text
CVE: CVE-2031-0007 (EPSS 0.4%), CVE-2031-0008, CVE-2031-0009
```

- EPSSのスコアがあるCVEには、IDの後ろに`(EPSS 3%)`の形でスコアを添える
- トリアージが無効のとき、またはKEVとEPSSのどちらも利用できないときは、スコアの代わりに深刻度を`(HIGH)`の形で添える

すべてのカードで、CVEを次の順に並べます。
前の条件で差がつかない場合だけ、次の条件を使います。

1. 優先度が今すぐ対応 → 要監視 → 低優先度の順
2. EPSSのスコアがあるCVEを、スコアがないCVEより先に並べる
3. EPSSのスコアが高いCVEを先に並べる
4. CVE IDを文字列の昇順に並べる

並べるCVEは20件までで、残りは件数で示します。

- 簡略カードは、行末に`(ほか +N件)`を表示
- 詳細カードは、最後の行に`• ほか +N件`を表示

検出済みのパッケージにCVEが増えたカードは、増えたCVE IDを`変化:`の行に表示し、`CVE:`には増えた分も含めて並べます。
`詳細: 🚨 今すぐ対応を参照`のカードだけは、CVEを表示しません。

`CVE:`と`変化:`に表示するCVE IDのリンク先は、次のとおりです。

| 条件 | リンク先 |
| --- | --- |
| Trivyまたは各ランタイムの脆弱性情報にアドバイザリーのURLがある | そのアドバイザリー |
| URLがなく、IDがCVEの形式 | NVD |
| URLがなく、GHSAやDLAなどCVE以外のID | リンクなしの通常のテキスト |

省略されていないCVEの全データは[脆弱性のフィールド](webhook-reference.md#vulnerability-fields)で確認できます。

### カードの対応行 {#base-image-wait}

カードの`対応:`行は、イメージや依存ファイルの更新、再pull・再ビルドによる解消の見込み、PRの状態、判断が必要な理由や更新・確認ができない理由を示します。
チャンネルの詳細カード・簡略カード、スレッド、差分カードの`検出件数:`の次に表示し、メールに含まれるカードにも同じ行を出します。

系列は、3.11と3.13のように、版の先頭2つの数字で区別するまとまりです。

#### 新しい系列での解消と版待ち

元イメージを新しい系列に上げると解消する場合は、次のように表示します。

```text
対応: 元イメージ python 3.11.9 → 3.13.1 で解消（minor の更新、同じ系列に新しい版なし、ベースの比較）
```

行の各部分と、結果に応じて付く補足の意味を次に示します。
表中の脆弱性は、そのカードに含まれる修正版のある所見を指します。

| 表示の部分 | 意味 |
| --- | --- |
| `元イメージ` | Dockerfileで指定した、イメージを作る土台となるイメージ |
| `イメージ` | 配布されているイメージそのもの |
| `python` | 更新対象のイメージ名の末尾で、レジストリのホスト名や途中のパスは省略 |
| `3.11.9 → 3.13.1` | 左が現在のイメージの版、右が比較した候補の版 |
| `で解消` | 候補では、カードの対象の脆弱性がすべて消える |
| `で一部解消` | 候補では、カードの対象の脆弱性の一部が消え、残りは解消しない |
| `の新しい版待ち` | 確認した範囲では、カードの対象の脆弱性を解消できる版が見つかっていない |
| `2件中1件` | カード内の修正版がある脆弱性をIDごとに数え、2件中1件が候補で解消 |
| `minor の更新` | 版の先頭の数字は同じで、2番目の数字が増える更新 |
| `major の更新` | 版の先頭の数字が増える更新 |
| `同じ系列に新しい版なし` | 現在と同じ系列には、より新しい版がない |
| `同じ系列の新しい版では未解消` | 現在と同じ系列の新しい版では、対象の脆弱性が解消しない |
| `同じ系列の新しいタグも内容は同じ` | 現在と同じ系列の新しいタグは、稼働中と同じ内容を指している |
| `ベースの比較` | 現在と候補の元イメージを比べた結果で、再ビルド後の完成イメージは未確認 |
| `新たな所見あり` | 候補への更新には、新たな所見も伴う |
| `確認した 1.27.3 と 2.0.1 でも未解消` | 記載された候補でも対象の脆弱性が残り、ほかの版での解消は未確認 |

結果ごとの行の例を次に示します。

| 結果 | 表示例 |
| --- | --- |
| 元イメージで解消 | `対応: 元イメージ python 3.11.9 → 3.13.1 で解消（minor の更新、同じ系列に新しい版なし、ベースの比較）` |
| イメージで一部解消 | `対応: イメージ nginx 1.24.1 → 1.27.3 で一部解消（2件中1件、minor の更新、同じ系列に新しい版なし）` |
| 確認した新しい系列でも未解消 | `対応: イメージ nginx 1.24.1 の新しい版待ち（確認した 1.27.3 と 2.0.1 でも未解消）` |
| 同じ系列と新しい系列で未解消 | `対応: イメージ nginx の新しい版待ち（同じ系列の新しい版と、確認した 2.0.1 で未解消）` |
| 同じ系列の新しい版でも直らず、条件に合う新しい系列もなし | `対応: イメージ nginx の新しい版待ち（同じ系列の新しい版では未解消）` |
| 条件に合う新しい版なし | `対応: 元イメージ python 3.11.9 の新しい版待ち（同じ系列にも、条件に合う新しい系列にも新しい版なし）` |
| 同じ系列に新しい版なし | `対応: 元イメージ python 3.11.9 の新しい版待ち（同じ系列に新しい版なし）` |
| 同じ系列に新しいタグあり、中身は今のタグと同じ | `対応: 元イメージ python 3.11.9 の新しい版待ち（同じ系列の新しいタグも内容は同じ）` |
| 元イメージ：同じ系列の新しい版でも直らず、条件に合う新しい系列もなし | `対応: 元イメージ python の新しい版待ち（同じ系列の新しい版では未解消、ベースの比較）` |

解消するか判断できない所見を含むカードなどでは、`対応:`行を省略することがあります。
ただし、元イメージに同じ系列の新しい版がないと分かっている場合は、その情報だけを表示することもあります。

#### 同じ系列の更新候補 {#action-same-series}

配布イメージに同じ系列の更新候補があり、修正計画の分類が`pr_candidate`の場合は、カード内の修正版がある所見の比較結果を示します。

結果ごとの表示例は次のとおりです。

| 結果 | 表示例 |
| --- | --- |
| すべて解消 | `対応: イメージ nginx 1.27.2 → 1.27.3 で解消` |
| 一部解消 | `対応: イメージ nginx 1.27.2 → 1.27.3 で一部解消（2件中1件）` |
| すべて残る | `対応: イメージ nginx 1.27.2 の新しい版待ち（同じ系列の 1.27.3 では未解消）` |
| 判定できない所見を含む | `対応: イメージ nginx 1.27.2 → 1.27.3 で解消するか確認できない` |

PR作成が有効な場合、解消・一部解消の行の末尾に、PRの状態をかっこで付けます。
すべて残る場合と判定できない場合、PR作成が無効な場合は付けません。

| 結果 | 表示例 |
| --- | --- |
| すべて解消 | `対応: イメージ nginx 1.27.2 → 1.27.3 で解消（Pull Request #12）` |
| 一部解消 | `対応: イメージ nginx 1.27.2 → 1.27.3 で一部解消（2件中1件、Pull Request #12）` |

次の表は、PRの状態ごとの表示例です。

| 状態 | PRの状態の表示例 |
| --- | --- |
| 作成済み・オープン中 | `Pull Request #12` |
| マージ済み | `Pull Request #12 はマージ済み、稼働中のイメージは未更新` |
| 未マージでクローズ | `Pull Request #12 は未マージでクローズ` |
| 別のPRに置き換え | `Pull Request #12 は未マージでクローズ、#13 に置き換え` |
| 利用者が内容を変更 | `Pull Request #12 の内容は作成時と異なる` |
| 未作成・処理未開始 | `Pull Request は未作成: Pull Request の記録を保存できなかった` |
| 書き込みの結果が不明 | `Pull Request の作成結果は未確認: GitHub への書き込みの結果が分からない` |
| 対応付けなし | `Pull Request は作成しない: ソースの対応付けがない` |
| `docker run`のコンテナ | `Pull Request は作成しない: docker run のコンテナのイメージタグは Pull Request の対象外である` |

PR番号はPRへのリンクになり、複数のオープン中のPRは`Pull Request #12、#14`のように並びます。
利用者が内容を変えたPRは、マージ済みでも内容変更の表示を優先します。

`Pull Request は未作成:`、`Pull Request の作成結果は未確認:`、`Pull Request は作成しない:`の後ろに理由が入ります。
理由の一覧は[PR処理の理由](remediation-update-reason-codes.md#pr-reasons)を参照してください。

#### 元イメージの同じ系列の更新候補 {#action-base-candidate}

Dockerfileの対応付けがあるイメージで、所見が固定タグの元イメージのレイヤーにある場合の表示例です。

| 結果 | 表示例 |
| --- | --- |
| すべて解消 | `対応: 元イメージ python 3.11.9 → 3.11.10 で解消（ベースの比較）` |
| 一部解消 | `対応: 元イメージ python 3.11.9 → 3.11.10 で一部解消（2件中1件、ベースの比較）` |
| すべて残る | `対応: 元イメージ python 3.11.9 の新しい版待ち（同じ系列の 3.11.10 では未解消、ベースの比較）` |
| 判定できない所見を含む | `対応: 元イメージ python 3.11.9 → 3.11.10 で解消するか確認できない（ベースの比較）` |
| すべて解消し、PR作成済み | `対応: 元イメージ python 3.11.9 → 3.11.10 で解消（Pull Request #12、ベースの比較）` |
| PRをマージ後、イメージの再ビルド待ち | `対応: Pull Request #13 はマージ済み、イメージの再ビルド待ち` |

PR作成が有効な場合、解消・一部解消の行に、[同じ系列の更新候補](#action-same-series)と同じ決まりでPRの状態が付きます。
元イメージのPRがマージ済みの場合は、PRの状態に`Pull Request #12 はマージ済み、イメージの再ビルド待ち`を表示します。

#### 同じタグの再pull {#action-pull-again}

`latest`のように版を固定しないタグのイメージでは、同じタグを取り直した（再pull）ときに所見が解消するかを示します。

| 結果 | 表示例 |
| --- | --- |
| すべて解消 | `対応: イメージ nginx latest の再pullで解消` |
| 一部解消 | `対応: イメージ nginx latest の再pullで一部解消（2件中1件）` |
| すべて残る | `対応: イメージ nginx latest の新しい内容待ち（再pullでも未解消）` |
| タグの内容が稼働中と同じ | `対応: イメージ nginx latest の新しい内容待ち（タグの内容は稼働中と同じ）` |
| コミットごとのタグで、内容が稼働中と同じ | `対応: イメージ app sha-5cf2d7b は新しいタグへの変更が必要（コミットごとのタグで、新しいタグを自動で選べない）` |
| 判定できない所見を含む | `対応: イメージ nginx latest の再pullで解消するか確認できない` |

[コミットごとのタグ](remediation-image-logic.md#published-image-tags)で新しいタグへの変更が必要と表示された場合は、Composeやマニフェストのイメージ名のタグを新しいタグへ書き換えてください。

#### 元イメージの同じタグでの再ビルド {#action-base-floating}

Dockerfileの対応付けがあるイメージで、元イメージに`node:24-alpine`のような版を固定しないタグを使う場合は、元イメージのレイヤーにある所見について次のように表示します。

| 表示例 | 意味 | 利用者がすること |
| --- | --- | --- |
| `対応: 元イメージ node 24-alpine の新しい内容待ち（タグの内容は作成時から変わっていない）` | タグが指す内容が、イメージを作ったときから変わっていない | 配布元がタグの内容を更新するのを待つ |
| `対応: 元イメージ app sha-5cf2d7b は新しいタグへの変更が必要（コミットごとのタグで、新しいタグを自動で選べない）` | コミットごとのタグで、内容がイメージの作成時から変わっていない | `FROM`のタグを新しいタグへ書き換えてビルドし直す |
| `対応: 再ビルドで解消する見込み（現在の元イメージ node 24-alpine では修正済み）` | タグの内容が更新されていて、現在の内容では修正済み | イメージをビルドし直してデプロイする |
| `対応: 再ビルドで一部解消する見込み（2件中1件、現在の元イメージ node 24-alpine との比較）` | 現在の内容で一部だけ修正済み | ビルドし直してデプロイし、残りは配布元の更新を待つ |
| `対応: 元イメージ node 24-alpine の新しい内容待ち（現在の内容にも残る）` | タグの内容は更新されたが、現在の内容にも残っている | 配布元の更新を待つ |
| `対応: 再ビルドで解消するか確認できない（現在の元イメージに同じ場所のパッケージがない）` | 現在の元イメージの同じ場所に、そのパッケージがない | そのパッケージをDockerfileの手順で入れていないかを確認する |

「見込み」は、稼働中のイメージと現在の元イメージのスキャン結果を比べたもので、ビルド後のイメージは確認していません。
詳しくは[見込みの制約](remediation-base-image-logic.md#rebuild-check-limits)を参照してください。

#### 要判断の更新 {#action-decision}

更新先の版や同じタグの新しい内容が見つかっていても、切り替えると別の問題が起きる場合や、切り替えてよいかをKestreLynxが確かめられない場合は、行に`要判断:`が付きます。
その後ろに、問題や確認できない事情が理由として表示されます。

| 場合 | 表示例 |
| --- | --- |
| 候補で解消する | `対応: イメージ nginx 1.27.2 → 1.27.3 で解消（要判断: 候補で新たな所見が入る）` |
| 候補で一部解消する | `対応: イメージ nginx 1.27.2 → 1.27.3 で一部解消（2件中1件、要判断: 候補で新たな所見が入る）` |
| 再pullで解消する | `対応: イメージ nginx latest の再pullで解消（要判断: 候補で新たな所見が入る）` |
| 解消するか分からない | `対応: イメージ nginx の更新は要判断（サービスのビルド方法を判断できない）` |
| 元イメージの候補で解消する | `対応: 元イメージ python 3.11.9 → 3.11.10 で解消（要判断: 候補で新たな所見が入る、ベースの比較）` |
| 元イメージの更新で解消するか分からない | `対応: 元イメージの更新は要判断（同じ Dockerfile を使うワークロードの間で候補が一致しない）` |

この行の更新にはPRが作られないため、理由を確認し、更新するかを自分で決めてください。
理由の一覧は[タグと候補の判定](remediation-image-reason-codes.md#image-candidate-reasons)と[Compose](remediation-image-reason-codes.md#source-compose-reasons)を参照してください。

#### 新しい版を確認できない場合 {#action-not-checked}

イメージの新しい版を調べていない、または調べられなかった場合は、その理由を示します。

| 表示例 | 意味 | 利用者がすること |
| --- | --- | --- |
| `対応: イメージの新しい版は確認していない（タグがなく digest だけで指定されている）` | イメージの指定の形が、新しい版を調べる対象外 | かっこ内の理由を確認する |
| `対応: イメージの新しい版を確認できなかった（レジストリへのログインが必要である）` | 新しい版の取得や比較に失敗した | かっこ内の理由の原因を取り除く |
| `対応: イメージの新しい版は次回以降に確認（実行時間の上限に達した）` | 上限や時間切れで今回は調べなかった | 次回のスキャンを待つ |
| `対応: 元イメージの新しい版を確認できなかった（イメージの解析が不完全だった）` | イメージの解析が不完全で、新しい版を確認できなかった | かっこ内の理由の原因を取り除く |
| `対応: 元イメージの新しい版は次回以降に確認（1回の実行でスキャンできる候補数の上限に達した）` | 候補のスキャン件数の上限で今回は調べなかった | 次回のスキャンを待つ |

かっこ内の理由の一覧は[イメージとソースの理由コード](remediation-image-reason-codes.md)を参照してください。

#### 依存ファイルによる言語パッケージの更新 {#action-dependency-files}

依存ファイルの対応付けがあるイメージでは、依存ファイルと照合できた言語パッケージについて次のように表示します。

| 表示例 | 意味 | 利用者がすること |
| --- | --- | --- |
| `対応: Pull Request #12 で 2.0.4 に更新` | 依存ファイルを更新するPRがあり、このパッケージを2.0.4に上げる | PRをマージし、イメージをビルドし直してデプロイする |
| `対応: Pull Request #12 で 2.0.4 に更新、マージ済み、稼働中のイメージには未反映` | PRはマージ済みだが、稼働中のイメージにはまだ古い版が入っている | イメージをビルドし直してデプロイする |
| `対応: Pull Request #12 で 2.0.4 に更新する変更は未マージでクローズ` | PRがマージされずに閉じられた | 自分で更新するかを決める |
| `対応: Pull Request #12 で 2.0.4 に更新する変更は未マージでクローズ、#13 に置き換え` | #12 は閉じられ、新しいPRの #13 が同じ修正を引き継いだ | #13 を確認する |
| `対応: pnpm-lock.yaml の更新で 2.0.4 に上げる候補（Pull Request は未作成: 更新したファイルをそのまま書き込めない）` | 依存ファイルを更新して2.0.4に上がることを確かめたが、PRは作られていない | かっこ内の理由を確認する |
| `対応: pnpm-lock.yaml の更新で 2.0.3 以上に上げる候補（Pull Request は未作成: 依存ファイルの更新結果は未確認）` | 依存ファイルにこのパッケージがあり、修正版の下限が2.0.3と分かっているが、更新はまだ実行していない | 依存ファイルを自分で更新するか、言語パッケージの更新を有効にする |
| `対応: 再ビルドで 2.0.3 以上が入る見込み` | 依存ファイルで版の範囲が指定されていて、修正版がその範囲に入っている | イメージをビルドし直してデプロイする |
| `対応: pnpm-lock.yaml では自動修正できない（候補または更新後の版が依存関係の制約を満たさない）` | このパッケージは自動では更新できなかった | かっこ内の理由を確認し、依存ファイルを自分で直すかを決める |
| `対応: pnpm-lock.yaml を更新できない（更新の実行に失敗した）` | 依存ファイル全体の更新が成立しなかった | かっこ内の理由の原因を取り除く |
| `対応: pnpm-lock.yaml の更新は次回以降（実行時間の上限に達した）` | 上限や時間切れで今回は更新しなかった | 次回のスキャンを待つ |
| `対応: pnpm-lock.yaml の更新内容を確認できない（Pull Request が作成時の状態と異なる）` | PRはあるが、このパッケージを更新する内容かどうかを確かめられない | PRの内容を確認する |
| `対応: pnpm-lock.yaml の更新では直せない（依存関係ファイルに稼働中の版のパッケージが載っていない）` | 依存ファイルを更新しても、このパッケージには届かない | かっこ内の理由を確認する |

- PR作成が無効な場合は、候補の行にかっこ内が付かない
- 行に出るファイル名は、対応付けたパッケージマネージャーに応じて`package-lock.json`・`pnpm-lock.yaml`・`uv.lock`・`requirements.txt`・`go.mod`・`pom.xml`・`gradle.lockfile`になる
- かっこ内の理由の一覧は[更新とPR処理の理由コード](remediation-update-reason-codes.md)を参照する

#### グローバルな node_modules {#action-global-node-modules}

修正計画の理由が`global_node_modules`のパッケージは、依存ファイルの更新では直らないことを示します。
持ち主は、グローバルな`node_modules`直下に入っているnpmやpnpmなどのパッケージです。

持ち主とパッケージの関係に応じた表示例は次のとおりです。

| 関係 | 表示例 |
| --- | --- |
| 同梱物で持ち主の版が分かる | `対応: pnpm 10.34.4 の同梱物（/usr/local/lib/node_modules）で、pnpm-lock.yaml の更新では直らない` |
| 同梱物で持ち主の版が分からない | `対応: npm の同梱物（/usr/local/lib/node_modules）で、pnpm-lock.yaml の更新では直らない` |
| グローバルに入っているパッケージ自身 | `対応: /usr/local/lib/node_modules に入っている pnpm 本体で、pnpm-lock.yaml の更新では直らない` |

上の例は、依存ファイルの対応付けがpnpmの場合です。
npmの場合は、ファイル名が`package-lock.json`になります。

この行が出たパッケージは、依存ファイルを更新しても直らないため、持ち主（npmやpnpm）の版を上げて直します。

- 持ち主をDockerfileで入れている場合は、その箇所の版を変える
- 持ち主がベースイメージに含まれている場合は、ベースイメージを更新する

持ち主のどの版で直るかは、行に表示しません。

カードの`対応:`行だけが変わっても、スレッドの全体レポートは送り直しません。
再投稿の条件は[Slackスレッドの投稿条件](notification-conditions.md#slack-thread-delivery)を参照してください。

イメージの細かな表示条件は[Slackのカードに出す行](remediation-image-logic.md#newer-series-slack-cards)、候補の選び方は[調べる版](remediation-image-logic.md#newer-series-versions)を参照してください。
言語パッケージの行の決め方は[カードの対応行](remediation-package-logic.md#card-action-line)を参照してください。

修正計画メッセージの読み方は[表示項目](remediation-results.md#slack-fields)で確認できます。

### 更新の注意度 {#upgrade-risk}

更新の注意度は、現在の版から修正版へのバージョン変更の種類を示します。
詳細カードでは、次のように表示します。

```text
更新の注意度: 🟢 ディストリのセキュリティパッチ
```

各表示の意味を次に示します。

| 表示 | 意味 |
| --- | --- |
| `🟢 ディストリのセキュリティパッチ` | OSパッケージの修正版で、「ディストリ」はOSの配布元であるディストリビューションを指す |
| `🟢 低リスク` | 言語パッケージでメジャーバージョンが増えない変更 |
| `🟠 メジャーバージョン更新 — 要注意` | 言語パッケージでメジャーバージョンが増える変更 |
| `⚪ リスク不明` | バージョンを比較できない変更 |

緑色の表示は、更新の安全性や互換性を保証するものではありません。

### エコシステムの表示 {#ecosystem-labels}

エコシステムの表示は、パッケージ名の後の角括弧で、言語パッケージの種類を示します。
次は、Pythonパッケージの表示例です。

```text
◆ setuptools [python-pkg]
```

角括弧内の表示と対象を次に示します。

| 表示 | 対象 |
| --- | --- |
| `[python-pkg]` | Pythonパッケージ |
| `[node-pkg]` | Node.jsのパッケージ |
| `[gobinary]` | Goバイナリに含まれるパッケージ |
| `[jar]` | JavaのJARファイルに含まれるパッケージ |
| `[node-runtime]` | Node.js本体の所見 |
| `[python-runtime]` | Python本体の所見 |
| `[lang]` | 種類を特定できない言語パッケージ |
| 角括弧の表示なし | OSパッケージ |

Trivyが識別した言語パッケージには、この表以外の種類も表示します。
Node.js・Python本体の所見は、各ランタイムの脆弱性情報から作成します。

Node.js・Python本体を示す表示は、パッケージの種類を表すもので、稼働中のコンテナで使用を確認したという意味ではありません。
使用の確認結果は[使用状況のラベル](slack-runtime-display.md#usage-labels)で確認できます。

## 変化の表示 {#change-labels}

差分通知では、イメージ、パッケージ、EOLの変化をそれぞれ表示します。
差分を成立させる規則は[差分と履歴の判定](diff-logic.md#comparison-baseline)を参照してください。

### イメージの変化 {#image-change-labels}

イメージの変化には、同じイメージ名で内容が変わった場合と、イメージ名が更新された場合の2種類の表示があります。
digestは、イメージの内容を識別する値です。

同じイメージ名でdigestが変わると、次の見出しの下にイメージ名と変更前後の短縮したdigestを表示します。

```text
🔄 イメージの内容が変化 (1件)
```

見出しの下の行は、次の書式です。
イメージ名と短縮したdigestが入る位置を示しています。

```text
• イメージ名: イメージ更新 (変更前の短縮したdigest → 変更後の短縮したdigest)
```

見出しの件数は、内容が変わったイメージ名の数です。
変更前後に複数のdigestがある場合は、それぞれをカンマで区切って表示します。

イメージ名が更新され、検出履歴を引き継いだ場合は、次のように表示します。
1行目の`sha-aaaa`と`sha-bbbb`はタグ、2行目の`0123456789ab`は短縮したdigestです。

```text
🔄 イメージ参照の更新: ghcr.io/acme/web sha-aaaa → sha-bbbb(検出履歴を引き継ぎ)
🔄 イメージ参照の更新: registry.example:5000/team/api 0123456789ab → 1.4(検出履歴を引き継ぎ)
```

矢印の前後には、更新前と更新後それぞれのイメージ名の指定に応じて、次の値を表示します。

| イメージ名の指定 | 矢印の前後に表示する値 |
| --- | --- |
| タグあり | タグ |
| タグがなく、digestで固定 | 短縮したdigest |
| タグもdigestもなし | `latest` |

履歴を引き継ぐ条件は、[イメージ名の更新](diff-logic.md#reference-changes)を参照してください。

### パッケージの変化 {#package-change-labels}

パッケージの変化は、区分の見出しと、カード内の`変化:`の行で示します。
同じイメージ名とパッケージの組み合わせについて、保存した履歴と最新のスキャンの結果を比べます。

次の例は、修正版が利用できるようになったパッケージの差分カードです。

```text
◆ dpkg
変化: 修正版が利用可能
現在: 1.21.22 · 修正版: 1.21.23 (🟢 ディストリのセキュリティパッチ)
検出件数: CRITICAL 0 / HIGH 1
CVE: CVE-2031-0004 (EPSS <0.1%)
```

区分の見出しは、次の内容をまとめます。
新規検出の区分には、初めて検出したパッケージだけでなく、検出済みのパッケージの変化も含みます。

| 見出しの表示 | 含まれる内容 |
| --- | --- |
| `🆕 前回のスキャンからの新規検出 (N件)` | 初めての検出、優先度の上昇、CVEの追加、修正版の公開、通知の再開 |
| `✅ 前回のスキャンからの解消 (N件)` | パッケージの所見の解消と、パッケージ・ベースOSのEOL解除 |

見出しのNは、次のように数えます。

- 新規検出では、表示対象のイメージ名とパッケージの組み合わせを1件として数える
- 解消では、解消またはEOL解除となったイメージ名とパッケージの組み合わせを1件として数え、ベースOSのEOLが解消したイメージ名の数を加える

新規検出では、同じ組み合わせでも修正版の有無などでカードが分かれるため、見出しの件数とカードの数が一致しない場合があります。

カード内の`変化:`の行は、次の変化を示します。

| 表示 | 出る場面 |
| --- | --- |
| `変化: ⬆️ 今すぐ対応に優先度昇格` | 要監視または低優先度だった組み合わせが、今すぐ対応になった場合 |
| `変化: ⬆️ 要監視に優先度昇格` | 低優先度だった組み合わせが、要監視になった場合 |
| `変化: 新しいCVE CVE-2031-0007` | 保存した履歴にないCVEが、その組み合わせで検出された場合 |
| `変化: 修正版が利用可能` | 修正版がなかった組み合わせで、修正版のある所見が見つかった場合 |

保存した履歴にない組み合わせを初めて検出したカードには、`変化:`の行を付けません。
CVEの追加で複数のカードを表示する場合も、追加されたCVEを含まないカードでは、この行を省略します。

複数の変化がある場合の判定順は、[通常のパッケージの変化](diff-logic.md#normal-changes)を参照してください。
通知オフからの再開表示は、[通知オフの表示](slack-runtime-display.md#muted-display)を参照してください。

### EOLの表示 {#eol-display}

EOL（サポート終了）の表示には、ベースOSがEOLのイメージの表示と、EOLのパッケージの表示があります。
パッケージのEOLは、対象リリースでサポート範囲外とされたCVEの所見を示します（[パッケージのEOL](scan-logic.md#eol-package)）。

次の例は、全体レポートでベースOSがEOLのイメージを表示した部分です。

```text
⛔ ベースOSのサポート終了(EOL) (最優先)
イメージ: legacy:1
状態: ベースOSがEOL (今後のセキュリティ更新なし)
サポート終了(EOL)のパッケージ2件を含む
```

全体レポートとスレッドでは、ベースOSがEOLのイメージについて、次のように表示します。

- そのイメージのEOLパッケージは個別のカードにせず、ベースOSの行に件数で示す
- トリアージ有効時は、そのうち今すぐ対応のパッケージだけ、今すぐ対応の区分にも詳細カードを表示する

全体レポートでは、EOLパッケージの件数や詳細の確認先を次の文言で示します。

| 表示 | 読み方 |
| --- | --- |
| `サポート終了(EOL)のパッケージN件を含む` | このイメージのベースOSの行にまとめたEOLパッケージの件数 |
| `詳細: 🚨 今すぐ対応を参照` | このパッケージの詳細は今すぐ対応の区分に表示 |

差分では、新たなEOL検出、CVEの追加、EOL解除を次の文言で示します。

| 表示 | 読み方 |
| --- | --- |
| `新たにサポート終了(EOL)となったパッケージN件を含む` | 新たにEOLと判定したベースOSの行にまとめた、新たなEOLパッケージの件数 |
| `パッケージN件が新たにサポート終了(EOL)` | EOLのベースOSの下に件数で示す、新たなEOLパッケージ |
| `新規CVEのあるサポート終了(EOL)のパッケージN件` | EOLのベースOSの下に件数で示す、CVEが追加されたEOLパッケージ |
| `ベースOSのEOLが解消` | そのイメージ名が、ベースOSのEOLの記録からなくなったこと |
| `サポート終了(EOL)が解消` | そのパッケージのEOLの所見がなくなり、通常の所見が残っていること |

`⛔ 新規: パッケージのサポート終了(EOL) (N件) — ベンダーがこれらのCVEをこのリリースのサポート対象外と報告`のNは、変化があったイメージ名とパッケージの組み合わせを数えます。
新たなEOL検出だけでなく、今すぐ対応への優先度上昇やCVEの追加も対象です。

この見出しの件数に含めるものと、含めないものは次のとおりです。

- 個別のカードで表示するEOLパッケージの変化は数える
- ベースOSが既にEOLのイメージでは、件数にまとめた新たなEOL検出やCVE追加も数える
- ベースOSを新たにEOLと判定したイメージでも、検出済みのEOLパッケージへのCVE追加は数える
- ベースOSとパッケージを同時に新たなEOLと判定した場合、今すぐ対応以外のパッケージはベースOSの行にまとめ、この見出しには数えない

カードの修正版の案内は、パッケージの種類と表示場所によって次のように異なります。
表の「通常のEOLパッケージ」は、Node.js・Python本体以外のEOLパッケージです。

| カードの種類と場所 | 修正版の表示 |
| --- | --- |
| 通常のEOLパッケージの簡略カード（チャンネル、スレッドの今すぐ対応への案内） | `修正版: なし — サポート終了(EOL): このリリースでは修正予定なし` |
| 通常のEOLパッケージの詳細カード（チャンネルの今すぐ対応、スレッド） | `修正版: なし — サポート終了(EOL): このリリースでは修正予定なし、サポート中のバージョンを検討` |
| Node.js・Python本体のカード（チャンネル、スレッド） | `修正版: なし — サポート終了(EOL): この系列には修正版が出ないため、系列を上げる必要がある(手動)` |

EOLではなくなっても、脆弱性は通常の所見として残ることがあります。
EOLの意味は[所見の分類](scan-logic.md#finding-classification)、解除の判断は[解消の判定](diff-logic.md#resolved-findings)を参照してください。
